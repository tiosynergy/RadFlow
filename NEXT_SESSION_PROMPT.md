Тему обирає власник. Нижче — пріоритети в порядку, який пропонує попередня сесія.

### 2. Компонентних тестів немає (jsdom не налаштований)

Найдорожча прогалина, підтверджена і аудитом (L-2). с24 показала ціну: усі фікси
жили в компонентах, і 528 тестів лишались зеленими на зламаній реалізації. Тепер
додався свіжий привід: **гонку `useRoomBusy` с26 полагодила, але зловити регрес
нема чим** — потрібні тести з deferred-промісами на зміну кабінету/дати.
Болить у SearchScreen, JournalScreen, обох дошках, `ImportPriceModal`,
`useQueueSounds`/`SoundToggle`.

### 3. Хвости зовнішнього аудиту (за спаданням користі)

- **H-2 — machine-verifiable історія міграцій.** Прод-схема застосовувалась
  вручну, `supabase_migrations.schema_migrations` не існує, `list_migrations`
  порожній. Аудит пропонує зафіксувати baseline `0130` і перейти на
  forward-only через CI. ⚠️ Це **процесне рішення власника**: воно змінює
  ритуал «міграції накочую руками». Спершу обговорити, потім кодити.
- **M-2 — lost update у графіку дня.** `saveScheduleOverride` робить upsert
  цілого JSONB `rooms` без CAS: два адміни, що правлять РІЗНІ кабінети на одну
  дату, мовчки перезаписують одне одного. Фікс — `version`/expected `updated_at`
  + CAS-RPC, або нормалізація per-room у окремі рядки.
- **M-3 — ACL-hardening.** 30 anon-executable і 68 authenticated-executable
  `SECURITY DEFINER`, 5 mutable `search_path`, у client-ролей успадковані
  `TRUNCATE`/`TRIGGER`/`REFERENCES`, вимкнений leaked-password protection.
  Прямого експлойта не знайдено (бізнес-RPC мають внутрішні гейти), але це зайва
  API-поверхня. Одна міграція-прибирання.
- **M-4 — індекси й RLS перед зростанням.** 5 неіндексованих FK
  (`ceo_access.granted_by`, `patient_cases.created_by`, `radiologist_rooms.room_id`,
  `referral_access.initiated_by`, `waitlist_entries.referrer_id`), 12
  `auth_rls_initplan` (замінити `auth.uid()` на `(select auth.uid())`),
  92 multiple permissive policies.
- **Операційні алерти (P1.10 аудиту):** залиплий `in_progress`, вік активного
  інциденту, outbox pending/dead, падіння cron, помилка запису важливої події.
- **M-5 (DST-модель) і M-6 (PII в `audit_log`)** — до міжнародного/24×7 режиму.

### 4. Хвости ТЗ логування (якщо власник захоче добити)

## Правила, які не можна порушувати

Повний список — в `AGENTS.md`. Найважливіше з першої хвилини:

- **Міграції застосовує власник вручну**; номер — наступний за максимальним
  ЗАСТОСОВАНИМ по прод-БД (зараз `0130` → наступна `0131`). Смоук НЕ в тілі
  міграції — в `supabase/smoke/`. Ідемпотентність обовʼязкова. **Комітить власник.**
- **Порядок викатки: СПЕРШУ міграція в БД, ПОТІМ клієнт.** У с26 це дало вікно,
  де нові гарди вже живі, а старий клієнт показував менш точні формулювання —
  нормально, але вікно треба закривати швидко.
- **⚠️ Dry-run гоняй РЕАЛЬНИМИ БАЙТАМИ файла** (урок с25). З с26 додай `pglast`
  (справжній парсер Postgres) і репетицію «міграція + смоук + `raise exception`»
  через `execute_sql`; ПІСЛЯ накату прожени смоук ще раз — тоді він перевіряє вже
  застосовану схему. `execute_sql` НЕ віддає NOTICE — видно лише фінальний `SMOKE_OK`.
- **Будь-яка зміна RLS / RPC / тригерів / серверних роутів → ревʼю субагентом,
  і другий раунд — по САМИХ фіксах.** Статистика с15–с26: окупається щоразу.
  У с26 перший раунд знайшов, що новий DB-гард СТРОГІШИЙ за клієнтську
  специфікацію і зламав би щоденний потік; другий — що фікс закрив половину випадків.
- **⚠️ Переносиш інваріант з UI у БД — спершу випиши правило, яке вже працює на
  клієнті, і доведи еквівалентність.** Інакше «посилення» ламає робочий сценарій
  (урок с26, H-R1).
- **⚠️ РЕВʼЮ НЕ ЗАМІНЮЄ ЖИВОЇ ПЕРЕВІРКИ** (урок с22, підтверджено с25).
  **Новий екран → перевір імпорти `styles/prototype/*.css` І ВІДКРИЙ у браузері.**
- **Перевіряй сторожів навмисною поломкою.**
- **PII не тягни в сесію агента:** розбираєш таблиці з ПІБ/телефонами — працюй
  агрегатами (count / count distinct / шаблони), а не вибіркою рядків (урок с26).
- **Журнал подій:** актор — лише з перевіреної сесії, `clinic_id` події — з
  РЯДКА БД (з 0129 — із повернення RPC з-під лока), PII — чотири лінії захисту,
  новий шлях мутації → додай емісію туди ж.
- **Зайнятість кабінету: план і факт — різні питання** (с26). «Вільний слот» —
  планове вікно (`check_no_overlap`, `room_busy_slots`); «чи можна викликати
  ЗАРАЗ» — фактичне вікно від настінного часу центру (`queue_set_status_rpc`).
- **Зміна даних прода — лише за явним списком ID** зі свіжого знімка, зі звіркою
  before-образу, dry-run і перевіркою сліду в `audit_log`. Статус запису черги
  міняє тільки `queue_set_status_rpc`.
- **Синій акцент — три ролі, роль обирає ВЛАСТИВІСТЬ** (с23). **Чіпав кольори —
  прожени `npm run audit:contrast`** (він же в `npm test`).
- **Інваріант БД без дати + UI зі зрізом по даті = вічне блокування** (урок с24).
- **Два запити в одному `reload` — це гонка.** Лічильник поколінь перед кожним
  `setState` — і в дошках, і в ХУКАХ (с26: `useRoomBusy` жив без нього).
- **`tsc`/`eslint` НЕ парсять CSS** — чіпав `.css` → `npm run build` обовʼязковий.
- **Нова модалка → додай її в гард гарячих клавіш `anyModalOpen`.**

## Середовище: що працює і що ні

- **⚠️ Шелла на пристрої НЕМАЄ.** `device_bash` віддає «Workspace unavailable».
  Живі `device_stage_files` / `device_commit_files` (шляхи Windows-абсолютні).
  Git робить власник — готуй команди.
- **Доставка: пиши файли ПРЯМО в папку** (`device_request_folder_access("D:\RadFlowDev")`
  один раз за сесію). Безпечний порядок: `device_stage_files` тих самих шляхів →
  `diff` із `git show HEAD:<файл>` (переконатись, що власник їх не правив) →
  `device_commit_files` з `expectedMtimeMs` зі стейджа. У с26 так доставлено
  14 файлів без жодного конфлікту. Тарбол не потрібен.
- **Тулчейн — на клоні з GitHub:**
  `git clone --depth 1 -b main https://github.com/tiosynergy/RadFlow.git /tmp/radflow`
  → `npm ci` → `typecheck && lint && test && build`.
- **`execute_sql` при ПОМИЛЦІ відкочує все** — це дешевий dry-run. ⚠️ При УСПІХУ
  комітить, тож зонд мусить закінчуватись `raise exception`. Імперсонація:
  `set_config('request.jwt.claims', json_build_object('sub',uid,'role','authenticated')::text, true)`;
  `set_config('role','authenticated')` назад не перемикається — став його ВСЕРЕДИНІ
  sub-блоку, перехоплений виняток відкотить роль сам.
- **Смоук-фікстури в проді бʼються об живі тригери:** модальність (0088),
  `rooms.active` (0123), графік `ROOM_CLOSED`/`OFF_SCHEDULE` (0084 —
  `off_schedule=true` дає ≤120 хв після закриття), минуле (0063), сітка 5 хв (0125),
  один `in_progress` на кабінет (0018). Кабінет обирай data-driven по ВСІХ
  клініках, день — перебором `+28..+34`.
- **У хмарному контейнері є Chromium + Playwright** (`/opt/pw-browsers/chromium`)
  і `pip install pglast`. У с25 так перевірявся новий екран БЕЗ входу в прод:
  справжній компонент забандлено esbuild-ом із реальним CSS прототипу,
  `next/navigation` і supabase-клієнт застаблено, `fetch` замокано.
  ⚠️ Прибери харнес-файли з репо і відкоти `package.json` після.
- **Міграцій у БД не відстежує жодна таблиця** — номер звіряй по
  `supabase/migrations/` у репо і по факту наявності обʼєктів (аудит H-2).
- **dev і prod — ОДИН проєкт Supabase**: фіксуй вихідний стан, явні id, прибирай
  за собою.
- **Мердж-цикл:** `compare/dev...main` (має бути 0 файлів!) →
  `compare/main...dev?expand=1` → PR → «Merge» тисне ВЛАСНИК →
  `git fetch` + `git merge --ff-only origin/main` + `git push origin dev`.
- **Живий UI** — Claude-in-Chrome проти `npm run dev` на пристрої. Вузькі екрани —
  iframe; вкладка зазвичай `hidden` (`AudioContext` suspended).
- **Планувальник** — лише `mcp__claude-code-remote__*`, не локальний cron.
- Решта пасток — в `AGENTS.md` і в `claude/radflow-handoff.md`.
