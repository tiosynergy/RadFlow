## Состояние на конец сессии 2026-07-14

**Прод-БД: миграции 0061–0075 применены. Следующая новая = 0076.**
Первым делом убедись, что 0074–0075 действительно в проде (их накатывали последними):

```sql
-- 0074: room_busy_slots должна возвращать 9 колонок (start_min / end_study_min / end_min)
select pg_get_function_result(oid) from pg_proc where proname = 'room_busy_slots';

-- 0075: FOR UPDATE реально в телах трёх RPC
select proname from pg_proc
 where proname in ('queue_set_status_rpc','queue_set_call_rpc','queue_reschedule_rpc')
   and prosrc ilike '%for update%';
-- ожидаем 3 строки
```

### Что закрыто за последнюю сессию

- **M-4 — единая модель времени.** Добавлен `wallToday0(tz)`; `clinics.timezone` приходит **пропом `clinicTz`
  с сервера** (клиентский fetch прилетал ПОСЛЕ монтирования, и инициализаторы `useState` фиксировали день
  браузера). `today0()` / «завтра» по браузеру вычищены из досок и модалок; `LiveClock` и `MiniCalendar` —
  по времени центра.
- **M-12 + M-14 — валидация на границах.** `lib/validation.ts` (примитивы zod) + `lib/validationHttp.ts`
  (`parseBody`/`parseJson` — отдельно, чтобы тесты не тянули `next/server`). Схемы на входе **всех**
  Server Actions и 12 API-роутов. `safeDbError()` — сырые ошибки БД клиенту не летят, **коды не менялись**.
  Побочно закрыт **M-1** на уровне приложения (`zTime` = строго `HH:MM`) и частично **L-2**.
- **0074 — занятость сквозь полночь.** `room_busy_slots` выбирала строки по `scheduled_date`, а время для
  `in_progress` брала от фактического старта → «зелёный, но незаписываемый слот». Теперь единственный
  критерий — фактическое окно пересекает сутки; окно обрезается по суткам (`start_min`/`end_study_min`/`end_min`).
  Серверный `hasSlotClash` переписан на абсолютные настенные интервалы (`wallInstantOf`).
- **0075 — атомарный CAS.** Статусные RPC читали статус без блокировки → две параллельные транзакции обе
  проходили проверку и обе рапортовали `updated = true`. Теперь `SELECT … FOR UPDATE` до проверок.
  Попутно: `queue_set_call_rpc` больше не упоминает `status` в `SET` без нужды — из-за этого в кабинете
  с активным простоем **нельзя было обзвонить пострадавших от аварии**.
- **UX:** ошибка сервера показывается **в самой модалке** (`.dlg-err`), а не тостом под оверлеем; кнопка
  блокируется на время запроса → закрыт **M-6** (двойной клик больше не дублирует запись и не портит
  `reschedule_origin`).

## Правила работы (не нарушать)

- **Миграции применяет владелец вручную** через Supabase SQL Editor. Ты пишешь файл и даёшь порядок накатки.
  Номер — следующий за максимальным в `supabase/migrations/`. Идемпотентность обязательна.
- **Мультитенантность (clinic_id / RLS) критична.** Любое изменение RLS, политик, RPC или триггеров →
  **обязательно ревью субагентом**. Оно ловило блокер практически каждый раз — в том числе в моих же фиксах.
- **`create or replace` — всегда диффай с ПОСЛЕДНЕЙ действующей редакцией функции** (0060 так «потеряла»
  буфер и `not_held`). Найди grep'ом, где функция определена последний раз, и правь от неё.
- **Порядок блокировок один:** сначала строка `queue_entries` (`for update`), потом advisory-lock кабинета
  (его берёт `check_no_overlap` внутри триггера). Функция, которая возьмёт advisory ПЕРЕД строками, даст **дедлок**.
- **Триггер `UPDATE OF col` срабатывает от УПОМИНАНИЯ колонки в `SET`, а не от изменения значения.**
- **Занятость кабинета** считается **абсолютными настенными интервалами** и **никогда не фильтруется по
  `scheduled_date`** (для `in_progress` окно привязано к `in_progress_at`). Один критерий в трёх местах:
  `check_no_overlap` ↔ `room_busy_slots` ↔ `hasSlotClash` — они обязаны совпадать.
- **Каждая НОВАЯ колонка `queue_entries`** требует `grant update (col) on public.queue_entries to authenticated;`
  — иначе UI молча получит 42501 (следствие 0070).
- **Время:** «сейчас» — только `wallNow(clinics.timezone)` / `wallDayKey(tz)` / `wallToday0(tz)`.
  `new Date()` — только для реальных инстантов (`updated_at`, `in_progress_at`).
- **Валидация:** каждый новый Server Action и API-роут начинается со схемы из `lib/validation.ts`.
  В **патчах** все поля `.optional()` — иначе отсутствующий ключ затрёт колонку в `null`.
- `npm run typecheck && npm run lint && npm test` перед каждым коммитом. **Коммитит владелец.**
- Bash-песочница агента отдаёт **устаревшие копии файлов** — доверяй только Read/Edit/Write.
- Браузерные проверки — Claude-in-Chrome против `npm run dev` (localhost:3000). Пароли вводит владелец.
  Dev и prod смотрят в **один** проект Supabase — тестовые действия меняют реальные данные, **убирай за собой**.

## Открытые пункты (по приоритету)

1. **`emergency_stop_rpc` — гонка двух остановок.** `insert … where not exists (active incident)`: две
   параллельные аварийки ловят `23505` по частичному уникальному индексу → **откатывается вся аварийная
   остановка** (регрессия H-3, сузившаяся до окна конкурентности). Фикс дешёвый: `on conflict do nothing`.
   **Это следующее, что я бы взял.**
2. **Инциденты не сериализованы с бронированием** — бронь может лечь внутрь только что созданного простоя
   (триггер читает ещё не закоммиченный инцидент). Фикс сложнее и **обязан соблюдать порядок блокировок**
   (сначала строки очереди, потом `incidents`; advisory-lock кабинета в начале incident-RPC = дедлок).
3. **Cron доставки outbox** — джоб `outbox-deliver` в `supabase/cron_jobs.sql` закомментирован: роут
   `/api/outbox/deliver` — no-op, пока пуст `N8N_WEBHOOK_URL`. Включить вместе с n8n. Доставка fail-closed:
   без HMAC-секрета и без https события не летят (в payload — ФИО и телефоны пациентов).
4. **Апгрейд зависимостей (`npm audit`).** `npm audit fix --force` **запускать нельзя** — он предлагает откат
   `next@9.3.3`. Правильно: `next` в пределах 15.x (тянет уязвимый `postcss`) и `vitest` → 3.x (тянет
   `esbuild`/`vite`, dev-only). Отдельным коммитом, с прогоном `npm run build && npm test`.
5. **L-3** — мёртвая колонка `queue_entries.priority` (вытеснена `priority_level`, 0046). Удалить.
6. **M-1 в БД** — CHECK на формат `scheduled_time` (на уровне приложения уже закрыт схемой `zTime`).
7. **L-2** — JSONB без валидации в БД (`rooms.schedule`); на входе приложения `zStudies` / `sRoomOverride` уже есть.
8. **Stage 2 (n8n / AI)** — инфраструктура готова: `event_outbox` (transactional outbox, HMAC, backoff, DLQ)
   + `audit_log`. Ротация листа ожидания, предсказание неявок.

## Ловушки этого проекта (каждая стоила прод-бага)

- `create or replace` без диффа с последней редакцией (0060 «потеряла» буфер и `not_held`).
- Колоночный `REVOKE` при табличном `GRANT UPDATE` — **no-op**. Сначала `revoke update on table`, потом `grant update (cols)`.
- SRF (`returns setof`) нельзя в `WHERE`: пиши `in (select fn())`, а не `= any(fn())`.
- `SECURITY DEFINER` **не применяет RLS** — вся авторизация должна быть в теле функции.
- Политики RLS — `to authenticated` и с `(select fn())`: иначе anon ловит 42501, а STABLE-функция дёргается на каждую строку.
- **Триггер `UPDATE OF col` реагирует на упоминание колонки в `SET`, а не на смену значения** (0075).
- **Выборка занятости по `scheduled_date` при времени от фактического старта** = «зелёный, но незаписываемый слот» (0074).
- **Read-then-write без `FOR UPDATE`** — это не CAS, а «проверка на глаз» (0075).
- Ранний выход в триггере формулируй через то, что защищаешь («занятость не выросла»), а не через удобный
  признак («слот не менялся») — иначе молча отключишь инвариант в соседнем случае (0068).
- Любой новый запрет статусного перехода **синхронно убирай из UI**, иначе остаётся мёртвая кнопка.
- Клиентские дефолты `duration_min || 30` и `normBuffer()` при **отрисовке занятости** запрещены: на
  «хвостовой» строке (0074) `duration_min` законно равен 0.
- Ошибка загрузки ≠ «пусто»: в лоадерах проверяй `error`, поднимай флаг, не затирай старые данные
  (канон — `lib/slotBusy.ts`).
- Тост об ошибке под оверлеем модалки = «кнопка не работает». Ошибку показывать в самой модалке (`.dlg-err`).
