## ЧТО ДЕЛАТЬ ДАЛЬШЕ (по приоритету)

### 1. `--blue` под белым текстом = 3.65:1 — нужно РЕШЕНИЕ ВЛАДЕЛЬЦА

Это все `.btn-primary`, активные пилюли, активные чипы дней — **27 узлов только на `/setup`**.
WCAG 1.4.3 AA требует 4.5:1 для мелкого текста. Технически правка на один токен, но это смена
брендового акцента, поэтому **спроси владельца, а не решай сам**. Замеренные варианты:

| вариант | белый на нём | комментарий |
|---|---|---|
| `#0a84ff` (сейчас) | 3.65 | не проходит |
| `#0b74e0` | 4.58 | минимально проходящий, ближе всего к текущему |
| `#0d6ecf` | 5.06 | с запасом |
| `#1268c2` | 5.55 | заметно темнее |

Там же: `--blue` как цвет ТЕКСТА = 3.82:1. Осветлённый `--blue-text: #4da3ff` (5.31) уже
добавлен в палитру в с18, но в проекте **~80 хардкодов того же значения** — их стоит свести к
токену одним механическим проходом (визуально это no-op, значение то же).

Покажи «до/после» на живом dev, прежде чем менять.

### 2. Ротация `SUPABASE_SERVICE_ROLE_KEY` (P0, откладывается с сессии 13)

Ключ ротирует владелец в Supabase. Твоя часть: чек-лист всех мест использования
(`lib/supabase/admin.ts` + все роуты, которые его берут), порядок замены без простоя и проверка
после. Заодно проверь `/api/auth/login-available`: при отказе БД он отвечает `available: null`,
а не «свободен» — убедись, что клиент трактует это fail-closed.

### 3. Остаток контраста

- Инпуты `.equip-block.equip-off .equip-info > input` остались на `opacity: .55`. Там `color`
  НЕ эквивалент — своя заливка и placeholder; нужна живая проверка.
- Мелкие провалы палитры: `.sb-badge` 3.41, `.sb-cab-count` 3.94, пустое состояние `.ei` 1.86.
- Метод замера: аудитор в браузере, который множит всю цепочку `opacity` и отдельно берёт фон
  ВНУТРИ группы и подложку ПОД ней. Формула «цвет на фоне» здесь врёт.

### 4. Компонентных тестов нет вообще (jsdom не настроен)

## Правила, которые нельзя нарушать

Полный список — в `AGENTS.md`. Самое важное, что стоит держать в голове с первой минуты:

- **Миграции применяет владелец вручную** через Supabase SQL Editor. Номер — следующий за
  максимальным **ПРИМЕНЁННЫМ** (по прод-БД!). Прод на `0126` → следующая `0127`.
  Идемпотентность обязательна. **Коммитит владелец.**
- **Порядок выкатки: СПЕРВА миграция в БД, ПОТОМ клиент.**
- **Любое изменение RLS / политик / RPC / триггеров / серверных роутов → ревью субагентом.**
  Окупается каждый раз: с18 дала два High в двух разных пакетах, и оба неочевидные — сломанный
  ЧУЖОЙ смоук и «детект без реакции» (флаг вычислялся, но нигде не читался).
- **Меняешь правило — ищи смоуки, которые утверждали СТАРОЕ.**
- **Удаление данных прода — только по явному списку ID из свежего снимка**, со сверкой по md5,
  dry-run через `raise exception` и проверкой, что before-образы легли в `audit_log`.
- **Пароли и ключи вводит владелец.** Настройки безопасности меняет владелец.
- **`tsc` и `eslint` НЕ парсят CSS** — сломанный CSS ловит только `npm run build`.
- **Замеряй, а не смотри.** Дважды статическая проверка пропускала то, что нашёл браузер.
