### 🔴 П'ять конфліктів ТЗ із реальністю — ВИНЕСИ ВЛАСНИКУ ДО КОДУ

Це не причіпки, це розвилки, після яких переробляти дорого. Спитай явно, до того
як писати міграцію.

1. **`fn_audit` зберігає ПОВНИЙ рядок** — `to_jsonb(old)` / `to_jsonb(new)`, тобто
   ПІБ, телефон, email, дату народження, протипоказання. Це прямо суперечить §6
   і критерію §12.7. АЛЕ: правило проєкту «зміна даних прода — зі звіркою
   before-образу в `audit_log`» спирається саме на ці знімки (так перевіряли
   скрипт закриття «test sound 1»). Вихолостити `audit_log` = зламати власну
   процедуру безпечних правок прода.
   Розвилка: (а) лишити `audit_log` технічним журналом як є і додати ОКРЕМИЙ шар
   `important_events` без PII (§3 це дозволяє: «додай сумісний шар»); (б) різати
   `before/after` до списку змінених полів і придумати іншу процедуру звірки прода.
   **Рекомендація: (а).** Питання власнику: чи погоджується, і що робити з 1069
   історичними рядками (лишити доживати 180 днів чи чистити зараз).
2. **`fn_audit` ковтає власні помилки** (`exception when others then null` —
   свідомо, «цілісність робочого запису важливіша»). §2.2 вимагає атомарності,
   §12.11 — щоб помилка запису не лишалась мовчазною. Це протилежні режими.
   Розвилка: важлива подія пишеться **fail-CLOSED** (не записалась — вся операція
   відкотилась, пацієнта не записали) чи **fail-OPEN** із окремим сигналом?
   Медичний контекст радше за fail-OPEN + гучний structured log, але це рішення
   власника, не наше.
3. **У енумі `user_role` немає `system`** (є admin, radiologist, registrar,
   referrer, ceo). §3 вимагає `actorRole: … | "system"`. Або нове значення енума
   (міграція + перевірка всіх `case`-ів по ролях), або окрема текстова колонка
   журналу. Рекомендація: текстова колонка журналу — енум ролей описує ЛЮДЕЙ і
   керує RLS, і додавати туди «систему» небезпечно.
4. **`patient_cases` НЕ аудіюється взагалі** — тригера `fn_audit` на ній немає.
   А §4.8–4.10 і §5 вимагають `case.created` / `case_step_added` / `case_cancelled`.
   Тобто ці події доведеться емітити явно з `create_case_rpc` і сусідів, а не
   «увімкнути тригер».
5. **«Одна дія — одна подія» (§2.1, §12.5) несумісне з рядковими тригерами.**
   Один перенос запису кейса чіпає `queue_entries` і `patient_cases`, аварійна
   зупинка — пачку рядків; тригер дасть N записів. Отже емітер має бути
   **прикладним** (у RPC / Server Action), а тригери лишаються технічним журналом.
   Це підтверджує розвилку №1.

## Правила, які не можна порушувати

Повний список — в `AGENTS.md`. Найважливіше з першої хвилини:

- **Міграції застосовує власник вручну**; номер — наступний за максимальним
  ЗАСТОСОВАНИМ по прод-БД (зараз `0127` → наступна `0128`). Смоук НЕ в тілі
  міграції — в `supabase/smoke/`. Ідемпотентність обовʼязкова. **Комітить власник.**
- **Порядок викатки: СПЕРШУ міграція в БД, ПОТІМ клієнт.**
- **Будь-яка зміна RLS / RPC / тригерів / серверних роутів → ревʼю субагентом,
  і другий раунд — по САМИХ фіксах.** Статистика с15–с24: окупається щоразу.
  У с23 ревʼю знайшло 3 High навіть у суто презентаційному пакеті; у с24 другий
  раунд показав, що фікси першого раунду не покриті жодним тестом.
- **⚠️ РЕВʼЮ НЕ ЗАМІНЮЄ ЖИВОЇ ПЕРЕВІРКИ** (урок с22): `/search` пройшов
  tsc/lint/tests/build і два раунди ревʼю — і відкрився голим HTML без CSS.
  **Новий екран → перевір імпорти `styles/prototype/*.css` І ВІДКРИЙ у браузері.**
- **Інваріант БД без дати + UI зі зрізом по даті = вічне блокування** (урок с24).
  Дані «поза зрізом» тримай ОКРЕМИМ станом (не підмішуй в `entries`) і з
  fail-CLOSED прапорцями `*Loaded`/`*Err`: стартове `[]` не відрізнити від «пусто».
- **Два запити в одному `reload` — це гонка.** Лічильник поколінь перед кожним
  `setState`; прапорець «завантажено» гасне разом із ключем зрізу.
- **Синій акцент — три ролі, роль обирає ВЛАСТИВІСТЬ** (с23): `background` під
  білим текстом → `--blue` + контур `--blue-line`; `color` → `--blue-text`;
  межа / кільце фокусу / крапка / смуга → `--blue-line`.
  **Чіпав кольори — прожени `npm run audit:contrast`** (він же в `npm test`).
- **PII (ПІБ/телефон/рядок пошуку) не потрапляє в URL, storage, console,
  телеметрію.** У deep-links — лише uuid і дата. **Для цієї сесії це головне.**
- **Зміна даних прода — лише за явним списком ID** зі свіжого знімка, зі звіркою
  before-образу, dry-run і перевіркою сліду в `audit_log`. Статус запису черги
  міняє тільки `queue_set_status_rpc`.
- **Перевіряй сторожів навмисною поломкою.** Тест, зелений на зламаній
  реалізації, — хибна гарантія (с23: лінт не читав TSX; с24: `TZ=UTC` робила тест
  на дату марним, тепер `TZ: "Europe/Kyiv"` у `vitest.config.ts`).
- **`tsc`/`eslint` НЕ парсять CSS** — чіпав `.css` → `npm run build` обовʼязковий.
- **Замеряй, а не дивись.** І **звіряй байти через `od -c`/`repr()`** при
  автозаміні — `\x01` ловився вже тричі (с20/с21/с22).
- **Нова модалка → додай її в гард гарячих клавіш `anyModalOpen`.**

  `git clone --depth 1 -b dev https://github.com/tiosynergy/RadFlow.git /tmp/radflow`

  Це ж — спосіб перевірити, що власник запушив саме перевірене дерево.
- **У хмарному контейнері є Chromium + Playwright** (`/opt/pw-browsers/chromium`,

- **Збірка у власника може падати на протухлому `.next`**
  (`TypeError: a[d] is not a function` + «prerendering /queue», хоча `/queue`
  динамічний) — причина в тому, що `next dev` працював під час розпакування.
  Лікується `Remove-Item -Recurse -Force .next` + `npm ci`.

  комітить, тож зонд мусить закінчуватись `raise exception`. Імперсонація:
  `set_config('request.jwt.claims', json_build_object('sub',uid,'role','authenticated')::text, true)`
  + `set local role authenticated`.
- **Міграцій у БД не відстежує жодна таблиця** — `supabase_migrations.schema_migrations`
  НЕ існує. Номер звіряй по `supabase/migrations/` у репо і по факту наявності обʼєктів.
