### Що зробила сесія 25

**Система логування важливих подій** (ТЗ `CLAUDE_MINIMAL_IMPORTANT_EVENTS_LOGGING_SPEC.md`).
`audit_log` лишився технічним журналом зі знімками рядків; важливі події — ОКРЕМИЙ
шар `important_events` (0128) без PII. Емісія ПРИКЛАДНА (з Server Actions і роутів
після успіху), режим **fail-OPEN** із гучним structured log. Роль людини виводить
сама RPC із `profiles` — підробити не можна. Реалізовано всі 12 `referral.*` і 16
із 20 загальних подій.

**Сторінка «Журнал дій»** (§11, лише admin): `/journal` + `POST /api/journal`,
фільтри період / співробітник / тип / ID, keyset-пагінація, людські формулювання,
імена співробітників резолвляться за id під RLS.

**Пошук за ID** — короткий ID із журналу або повний uuid знаходить запис
у `/search` і в швидкому пошуку дошок.

Деталі, розвилки і всі уроки — блок с25 у `docs/HANDOVER.md`.

## ЗАДАЧА СЕСІЇ

Тему обирає власник. Нижче — пріоритети в порядку, який пропонує попередня сесія.

### 1. Ротація `SUPABASE_SERVICE_ROLE_KEY` (P0, тягнеться з с13)

Найстаріший борг безпеки. Треба: чек-лист місць використання ключа (усі
`createAdminClient()` — роути `app/api/*`, `lib/rateLimit.ts`, емітер журналу
`lib/importantEvents.server.ts`), порядок заміни без простою, перевірка
`/api/auth/login-available` (fail-closed при `null`). **Ключ ротує власник** —
агент готує план і перевіряє після.

### 2. Жива перевірка прода після викатки PR #18

- `/journal` під реальним адміном: чи резолвляться імена співробітників
  (у харнесі вони були застаблені), «Показати ще» на другій сторінці,
  фільтр за ID запису;
- `/search` за ID з журналу під різними ролями;
- `/search` під radiologist / referrer / ceo і «Показати ще» (сів s19 лишений
  саме заради другої сторінки). **Паролі вводить власник.**

### 3. Компонентних тестів немає (jsdom не налаштований)

Найдорожча прогалина. с24 показала ціну: усі фікси жили в компонентах, і 528
тестів лишались зеленими на зламаній реалізації. У с25 екран журналу довелось
перевіряти саморобним харнесом (esbuild + headless Chromium). Болить у
SearchScreen, JournalScreen, обох дошках, `ImportPriceModal`,
`useQueueSounds`/`SoundToggle`.

### 4. Хвости журналу (якщо власник захоче добити ТЗ)

- **CEO-режим журналу**: політика `imp_events_read_ceo` в 0128 вже є, роут поки
  лише admin — §9 ТЗ вимагає продуктового рішення;
- `patient_data.exported` не емітиться: CSV-експорт суто клієнтський
  (`CeoDashboard`, `CallListBoard`) — щоб журналювати, потрібна серверна ручка;
- `schedule.exception_confirmed` пишеться лише всередині RPC 0109; правки
  графіка дня (`saveScheduleOverride`) не журналюються взагалі;
- decline заявки направника і зміна області гранта (`policy`/`room_ids`) не
  журналюються — у ТЗ немає типу (кандидат: `referral.access_changed`);
- наскрізного `requestId` немає — поле в журналі зарезервовано;
- outbox (§8) не переведено на посилання `important_event` (§12.12 — свідомо);
- `pickDetails` проекціює вкладеність лише для `from`/`to`; ключ `reason` має
  надто загальне імʼя — майбутній емітер може покласти туди вільний текст.

### 5. Залишок WCAG

Інпути `.equip-off` на `opacity: .55`; порожній стан `.ei` 1.86; `--red` як текст
3.33 на `--card-2`; `.doc-av` використовує неоголошені `--purple`/`--indigo`
(градієнт не малюється взагалі); `.slot.sel.taken` і `.slot.hinted` тонуть
в `opacity`. Модалки на 320px не перевірені.

### 6. Пошук, наступні ітерації

WaitlistBoard досі на старому серверному ilike; фільтр «направник» є в контракті,
UI-випадайки немає; relevance-сортування зарезервовано; ID кейса (`patient_case`)
у `/search` не шукається — лише записи черги й листа очікування; при зростанні
історії — trigram + generated digits.

### 7. Бэклог с24

Хвіст у ВИМКНЕНОМУ кабінеті не показується на жодній дошці (`roomsResidual`
вважає живими лише записи від сьогодні) — для радіолога там тупик лишається.

### 8. Сів s19

Відкат, коли стане не потрібен:
`supabase/maintenance/2026-07-30_cleanup_seed_s19.sql` з `v_dry := false`.

### 9. Відкладено власником

AI-етапи пошуку (тільки після окремого доручення і PII-gate); канал сповіщення
для outbox — до хостингу і реального SMTP; публічність репозиторію; мертва гілка
`kind:"image"` в n8n; доля колонок `services.contrast_allowed`/`contrast_price`;
автономний режим (8 питань §12); зміна логіна співробітника адміном; апгрейд
залежностей (**`npm audit fix --force` НЕ МОЖНА** — пропонує next@9).

**Carryover власника:** місячний spending limit в OpenAI — реальна стеля це
**monthly recharge limit** у Billing → Auto-recharge settings, не «Budget limit».

## Правила, які не можна порушувати

Повний список — в `AGENTS.md`. Найважливіше з першої хвилини:

- **Міграції застосовує власник вручну**; номер — наступний за максимальним
  ЗАСТОСОВАНИМ по прод-БД (зараз `0128` → наступна `0129`). Смоук НЕ в тілі
  міграції — в `supabase/smoke/`. Ідемпотентність обовʼязкова. **Комітить власник.**
- **Порядок викатки: СПЕРШУ міграція в БД, ПОТІМ клієнт.**
- **⚠️ Dry-run гоняй РЕАЛЬНИМИ БАЙТАМИ файла** (урок с25): 0128 пройшла два
  «успішні» dry-run і впала у власника на `42601`, бо перевірявся перепечатаний
  SQL без шапки, а в шапці `*/` закрив коментар достроково.
- **Будь-яка зміна RLS / RPC / тригерів / серверних роутів → ревʼю субагентом,
  і другий раунд — по САМИХ фіксах.** Статистика с15–с25: окупається щоразу.
  У с25 другий раунд знайшов, що фікс меж доби закривав лише половину випадків,
  а мій же тест закріплював хибне значення.
- **⚠️ РЕВʼЮ НЕ ЗАМІНЮЄ ЖИВОЇ ПЕРЕВІРКИ** (урок с22, підтверджено с25): `/search`
  колись відкрився голим HTML попри два раунди ревʼю; у с25 жива перевірка
  екрана знайшла «Система зупинив» і дубль направника, яких не бачили ні тести,
  ні ревʼю. **Новий екран → перевір імпорти `styles/prototype/*.css` І ВІДКРИЙ
  у браузері.**
- **Перевіряй сторожів навмисною поломкою.** У с25 ТРИ сторожі виявились
  зеленими на зламаній реалізації: `\b` не працює з кирилицею; ворожий payload
  відсікався лімітом довжини, а не алфавітом; dry-run перевіряв не файл.
- **Журнал подій:** актор — лише з перевіреної сесії, `clinic_id` події — з
  РЯДКА БД (не з клієнтського параметра), PII — чотири лінії захисту, новий шлях
  мутації → додай емісію туди ж. Деталі — блок «Журналы событий» в `AGENTS.md`.
- **PII (ПІБ/телефон/рядок пошуку) не потрапляє в URL, storage, console,
  телеметрію.** У deep-links — лише uuid і дата.
- **Зміна даних прода — лише за явним списком ID** зі свіжого знімка, зі звіркою
  before-образу, dry-run і перевіркою сліду в `audit_log`. Статус запису черги
  міняє тільки `queue_set_status_rpc`.
- **Синій акцент — три ролі, роль обирає ВЛАСТИВІСТЬ** (с23): `background` під
  білим текстом → `--blue` + контур `--blue-line`; `color` → `--blue-text`;
  межа / кільце фокусу / крапка / смуга → `--blue-line`.
  **Чіпав кольори — прожени `npm run audit:contrast`** (він же в `npm test`).
- **Інваріант БД без дати + UI зі зрізом по даті = вічне блокування** (урок с24).
  Дані «поза зрізом» тримай ОКРЕМИМ станом і з fail-CLOSED прапорцями
  `*Loaded`/`*Err`: стартове `[]` не відрізнити від «пусто».
- **Два запити в одному `reload` — це гонка.** Лічильник поколінь перед кожним
  `setState`; прапорець «завантажено» гасне разом із ключем зрізу.
- **`tsc`/`eslint` НЕ парсять CSS** — чіпав `.css` → `npm run build` обовʼязковий.
- **Нова модалка → додай її в гард гарячих клавіш `anyModalOpen`.**

## Середовище: що працює і що ні

- **⚠️ Шелла на пристрої НЕМАЄ.** `device_bash` віддає «Workspace unavailable».
  Живі `device_stage_files` / `device_commit_files` (шляхи Windows-абсолютні).
  Git робить власник — готуй команди.
- **Доставка: пиши файли ПРЯМО в папку** (`device_request_folder_access("D:\RadFlowDev")`
  один раз за сесію). Безпечний порядок: `device_stage_files` тих самих шляхів →
  `diff` із `git show HEAD:<файл>` (переконатись, що власник їх не правив) →
  `device_commit_files` з `expectedMtimeMs` зі стейджа. Тарбол уже не потрібен;
  ⚠️ якщо все ж робиш — тарболи НЕ в `.gitignore`, видаляй до `git add -A`.
- **Тулчейн — на клоні з GitHub:**
  `git clone --depth 1 -b main https://github.com/tiosynergy/RadFlow.git /tmp/radflow`
  → `npm ci` → `typecheck && lint && test && build && audit:contrast`.
- **У хмарному контейнері є Chromium + Playwright** (`/opt/pw-browsers/chromium`).
  У с25 так перевірявся новий екран БЕЗ входу в прод: справжній компонент
  забандлено esbuild-ом із реальним CSS прототипу, `next/navigation` і
  supabase-клієнт застаблено, `fetch` замокано → рендер + замір computed styles.
  ⚠️ Прибери харнес-файли з репо і відкоти `package.json` після.
- **`execute_sql` при ПОМИЛЦІ відкочує все** — це дешевий dry-run. ⚠️ При УСПІХУ
  комітить, тож зонд мусить закінчуватись `raise exception`. Імперсонація:
  `set_config('request.jwt.claims', json_build_object('sub',uid,'role','authenticated')::text, true)`
  + `set local role authenticated`.
- **Міграцій у БД не відстежує жодна таблиця** — номер звіряй по
  `supabase/migrations/` у репо і по факту наявності обʼєктів.
- **dev і prod — ОДИН проєкт Supabase**: фіксуй вихідний стан, явні id, прибирай
  за собою.
- **Мердж-цикл:** `compare/dev...main` (має бути 0 файлів!) →
  `compare/main...dev?expand=1` → PR → «Merge» тисне ВЛАСНИК →
  `git fetch` + `git merge --ff-only origin/main` + `git push origin dev`.
- **Живий UI** — Claude-in-Chrome проти `npm run dev` на пристрої. Вузькі екрани —
  iframe; вкладка зазвичай `hidden` (`AudioContext` suspended).
- **Планувальник** — лише `mcp__claude-code-remote__*`, не локальний cron.
- Решта пасток — в `AGENTS.md` і в `claude/radflow-handoff.md`.
