## 0. ПЕРШЕ, що треба знати — і чого я не можу заміряти

| питання | стан |
|---|---|
| Тариф Supabase і чи увімкнено **PITR** | ⚠️ **ПО API НЕ ВИДНО.** `get_project` віддає ref, регіон, версію — тарифу немає. Дивитись у Dashboard → Settings → Add-ons |
| Retention керованих бекапів | ⚠️ Там же. На Free історично — добовий бекап, retention 7 днів (тобто **RPO до 24 год**) |
| WAL-архівація живе | ✅ Заміряно: `archive_mode=on`, `wal_level=logical`, **45 311** сегментів заархівовано, останній **2026-09-14 01:16 UTC** |

⚠️ **WAL-архівація ≠ PITR.** Те, що `archive_mode=on` і лічильник росте,
доводить лише, що інфраструктура Supabase архівує WAL. Чи **куплено** для
цього проєкту відновлення на точку в часі — з бази не видно. Не плутати й не
припускати: це той самий клас, що leaked-password — факт живе в чужій консолі.

**Дія:** один погляд у Dashboard закриває обидва рядки. Доки не подивились,
плануйте по гіршому: **RPO 24 год**.

**локальної копії того JSON у репозиторії немає** (заміряно).

**Дешева дія, що знімає залежність:** покласти `katottg.min.json` у репозиторій
(~кілька МБ) і сидити з нього. Поки цього немає, `cities` — не «✅», а
«відновлюється, якщо чужий GitHub на місці». Для довідника адрес це
прийнятний риск, але він має бути названий, а не схований за галочкою.

## 2. ⚠️ Що НЕ повертається разом із базою

Це головна частина документа. Порядок — за ціною помилки.

### 2.1 `auth` — БЕЗ НЬОГО НІХТО НЕ ЗАЙДЕ

Заміряно: `auth.users` — **14**, `auth.identities` — **14**,
`public.profiles` — **9**, сиріт (профіль без auth-юзера) — **0**.

`profiles.id` = `auth.users.id`. Відновлення **лише схеми `public`** дає базу,
де всі 9 профілів указують у порожнечу: дані на місці, увійти не може НІХТО,
включно з адміном. Відновлювати треба **разом з `auth`**, або одразу після
цього перестворювати користувачів і зшивати id.

### 2.2 Vault — 3 секрети, і два з них БЕЗ ІМЕНІ

Заміряно (метадані; значення не читались і не читаються):

| id | name | description |
|---|---|---|
| `6fcc97a6…` | `cron_secret` | — |
| `6dafa5ec…` | **`<без імені>`** | `gcal:refresh, clinic b42134dc…` |
| `67e1bb62…` | **`<без імені>`** | `gcal:refresh, clinic c79588d6…` |

⚠️ Скрипт відновлення, який шукає секрети **за `name`**, знайде **один із
трьох**. Два refresh-токени Google ідентифікуються лише полем `description`.
Записано тут саме тому, що в момент відновлення це не згадають.

Без `cron_secret` два джоби з `pg_net` (нижче) стукають у прод **без
валідного Bearer** — роути fail-closed відбивають їх, і дзеркало та outbox
мовчки стоять.

### 2.5 Оточення Vercel

Бекап БД не несе жодної змінної оточення. Перелік нижче **знятий з коду**
(`process.env.*` по `.ts`), а не переписаний із памʼяті:

| змінна | без неї |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | не працює нічого |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | не працює клієнт і middleware |
| `SUPABASE_SERVICE_ROLE_KEY` | падають усі адмінські роути |
| `CRON_SECRET` | fail-closed відбиває **чотири** роути: `outbox/deliver`, `queue/sink-overdue`, `maintenance/retention`, `integrations/google-calendar/sync-all` |
| `GOOGLE_OAUTH_CLIENT_ID` / `_SECRET` / `_REDIRECT_URI` | не підключити дзеркало |
| `GOOGLE_CALENDAR_BACKUP_AVAILABLE` | прапорець доступності фічі |
| `N8N_WEBHOOK_URL` | не йдуть доставки outbox назовні |
| `IMPORT_WEBHOOK_SECRET` | не працює імпорт послуг |
| `AI_SEARCH_ENABLED`, `AI_ASSISTANT_ENABLED` | прапорці функцій |
| `VERCEL_GIT_COMMIT_SHA` | ставить Vercel; без неї штамп `/api/build` не звіриш |

⚠️ Ротація service-role ключа прив'язана власником до першого реального
центру (блок 6.2 плану) — при відновленні це зручний момент.

## 3. Процедура

> ⚠️ Кроки 1–2 — рішення, а не механіка. Не починати з кнопки «Restore».

1. **Зафіксувати момент і масштаб.** Що саме втрачено: рядки (тоді точкова
   правка, а не відновлення), таблиця, схема, весь проєкт. Відновлення всієї
   БД заради 20 рядків — гірше за проблему.
2. **Подивитись, що взагалі доступно** (Dashboard → Database → Backups):
   є PITR чи лише добовий знімок; на яку точку можна стати.
3. **Відновлювати в НОВИЙ проєкт, не поверх живого.** Це дає звірку перед
   переключенням і зберігає докази того, що сталось.
4. **Повернути `auth`** (п. 2.1) і звірити:
   `select count(*) from public.profiles p where not exists
   (select 1 from auth.users u where u.id = p.id)` → **0**.
5. **Повернути Vault** (п. 2.2), **cron** (п. 2.3), **розширення** (п. 2.4).
6. **Звірити схему з репозиторієм — це вже автоматизовано:**
   `npm run db:gate:check` → має бути `192/192` (або скільки на той момент).
   ⚠️ Скарга аудиту 12.07 «машинної історії того, яка схема на проді, не
   існує» **ЗАКРИТА**: `migration_ledger` + `scripts/migration-gate.mjs`
   дають рівно її. У липні було 0063 і вручну; зараз 192 і симетричний гейт.
7. **Звірити інваріанти:** `select public.invariants_check(false)` →
   `ok:true, checked:23, failed:[]`.
   ⚠️ Якщо червоний `ledger_md5` — спочатку `npm run db:gate`, потім знову
   (див. 0192, «ПІСЛЯ НАКАТУ §1»).
8. **Переключити оточення** Vercel на новий проєкт і задеплоїти.
9. **Звірити штамп деплою** проти локально порахованого
   (`sha256(sha)[:12]` vs `/api/build`).
10. **Перепідключити Google Calendar** (п. 2.6) і перевірити
    `last_sync_at` — не статус, а **час**.

## 4. RTO / RPO — розрахунок, а не факт

| | значення | підстава |
|---|---|---|
| **RPO** | **до 24 год** (гірший випадок) | добовий знімок, якщо PITR не куплено. З PITR — хвилини |
| **RTO (розрахунок)** | **2–4 год** | копіювання 133 МБ — хвилини; решта — кроки 3–6 і переключення оточення вручну |

⚠️ **RTO не заміряний.** Проєкт уже довів, що його оцінки занижені вдвічі
(RF-05: план 1–1,5 год → факт 3,5 год). Ставитись до «2–4 год» треба як до
нижньої межі, поки не буде репетиції.

**Що означає RPO 24 год по-людськи:** втрачається до доби записів. Заміряно
14.09 — у вікні «вчора…+7 днів» **128** записів, на сьогодні **34**. Тобто
центр вранці не знає, хто до нього записаний, і відновлює це телефонами.

## 5. Репетиція — чого бракує, щоб цей документ став фактом

1. створити окремий Supabase-проєкт;
2. відновити в нього останній бекап;
3. пройти кроки 4–7 і **записати фактичний час кожного**;
4. окремо перевірити те, що найлегше проґавити: вхід користувача (auth),
   `count(*) from cron.job` = 10, `db:gate:check`, `invariants_check`;
5. дописати сюди заміряні RTO/RPO замість розрахункових.

⚠️ Це коштує грошей (другий проєкт) і години часу — тобто **рішення
власника**, а не крок, який агент робить сам. До репетиції пункт 3.2 плану
лишається відкритим, і вердикт аудиту це враховує.
