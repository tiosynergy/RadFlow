# Локальная разработка: производительность dev-сервера

**Замерено 2026-07-28 (сессия 15)** на этом проекте: Next 15.5.21, Node 22, 35 маршрутов,
50 клиентских компонентов. Каждый прогон — с чистым `.next`, прогрев одними и теми же
10 маршрутами (`/login /register /queue /staff /services /waitlist /call-list /referral
/radiologist /ceo`), RSS суммарно по дереву процессов `next dev`.

## Результаты

| режим | RSS после 10 маршрутов | компиляция 10 маршрутов | кеш `.next` |
|---|---|---|---|
| `next dev` (webpack, дефолт) | **925 МБ** | 19 с | 61 МБ |
| `next dev --turbo` | **1112 МБ** | 13 с | 32 МБ |
| webpack + `--max-old-space-size=768` | 881 МБ | 19 с | — |
| webpack + `--max-old-space-size=512` | 866 МБ | 20 с | — |
| webpack + `experimental.webpackMemoryOptimizations` | 912 МБ | 25 с | — |
| webpack + `onDemandEntries` (15 с / 2 стр.), после 70 с простоя | **628 МБ** (было 746) | — | — |

Разбивка по процессам: из ~900 МБ **771 МБ — один процесс `next-server`**, остальное —
обёртки `npm`/`next` по 80 МБ.

## Выводы

**Это не утечка, а устройство dev-режима.** Сервер держит в памяти модульный граф всех
маршрутов, которые открыли за сессию: ~740 модулей на страницу, 50 клиентских компонентов,
крупнейшие файлы — `QueueBoard.tsx` (2277 строк), `app/queue/actions.ts` (2454),
`ReferralPortal.tsx` (1623). Память растёт по мере обхода досок и сама не возвращается.

**Что НЕ помогает (проверено, не повторять):**

- `--max-old-space-size` — эффект в пределах 6% (925 → 866 МБ), потому что память лежит не
  в V8 old space. Вред при этом реальный: тот же `NODE_OPTIONS` подхватит `npm run build`
  и уронит сборку по OOM.
- `experimental.webpackMemoryOptimizations` — в 15.5.21 разницы нет (912 против 925 —
  внутри шума), зато компиляция медленнее на четверть.
- `--turbo` — **память не экономит, а добавляет ~20%.** Он про скорость: компиляция −32%,
  кеш на диске вдвое меньше. Переходить стоит ради времени, не ради RAM.

**Что помогает:**

- `onDemandEntries` — единственный измеренный выигрыш по памяти: неактивные страницы
  выгружаются, −16% после минуты простоя. Плата — возврат на доску стоит повторной
  компиляции (2–3 с). Осмысленно при 8 ГБ RAM, при 16 ГБ — нет.
  ```js
  // next.config.mjs — НЕ включено в репозитории по умолчанию, добавлять по необходимости
  onDemandEntries: { maxInactiveAge: 15 * 1000, pagesBufferLength: 2 },
  ```
- Рестарт `next dev` раз в несколько часов работы: после десятков правок память не
  возвращается сама.
- Не обходить все доски подряд в одной сессии, если память в дефиците.

## Windows-специфика

Основной источник тормозов dev на Windows — не память, а антивирус на файловых вотчерах.
Исключения Defender для папки проекта и кеша npm (PowerShell **от администратора**):

```powershell
Add-MpPreference -ExclusionPath 'D:\RadFlowDev'
Add-MpPreference -ExclusionPath "$env:LOCALAPPDATA\npm-cache"
# проверка
(Get-MpPreference).ExclusionPath
```

⚠️ Это ослабление защиты: `node_modules` — типовая мишень атак на цепочку поставок npm.
Исключать **только папку проекта и кеш**, не диск целиком. Исключение процесса
(`-ExclusionProcess 'node.exe'`) снимает проверку с файлов, которые открывает любой
node-процесс где угодно — добавлять только если папочных исключений не хватило.

Откат: `Remove-MpPreference -ExclusionPath 'D:\RadFlowDev'` и т.д.

Как проверить эффект (одинаковый старт с чистым кешем до и после):

```powershell
cd D:\RadFlowDev; Remove-Item -Recurse -Force .next; Measure-Command { npm run build }
```

Если разницы нет — антивирус был ни при чём, исключения стоит откатить.

## Как перезамерить

Скрипт замера не хранится в репозитории (разовый). Схема: чистый `.next` → `next dev` на
свободном порту → дождаться `Ready in` → `curl` по списку маршрутов → сумма RSS по дереву
процессов (`ps -eo rss,pgid,cmd`, фильтр по process group). Сравнивать только прогоны с
одинаковым набором маршрутов: RSS прямо пропорционален числу скомпилированных страниц.
