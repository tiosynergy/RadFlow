## A-1 / A-2. Оракул радиолога: механизм один на две RPC

Обе RPC — `SECURITY DEFINER`, то есть **RLS внутри них не действует**, и весь
гейт обязан стоять в теле явно. Радиолога в теле ни одной из них нет: замер
`prosrc` даёт `auth_radiologist_room_ok` → **false** в обеих.

Запрет радиолога на запись держит **триггер**, а не RPC:

```
waitlist_entries  BEFORE INS/UPD/DEL  a00_radiologist_no_write  → guard_radiologist_no_write
patient_cases     BEFORE INS/UPD/DEL  a00_radiologist_no_write  → guard_radiologist_no_write
queue_entries     BEFORE INS/UPD/DEL  a00_radiologist_scope     → guard_radiologist_scope
```

DEFINER обходит RLS, но **не обходит триггеры** — поэтому записать радиолог не
может. Дыра не в записи, а в том, **чем именно ему отказывают**.

### Замер: карта всех сообщений FORBIDDEN

Канонический «не подтверждаем существование» текст — `FORBIDDEN: запис не
знайдено`. Его используют `guard_radiologist_no_write`, `guard_radiologist_scope`
(3×), `queue_set_status_rpc` (3×), `queue_reschedule_rpc`, `queue_set_call_rpc`,
`case_from_entry_rpc` (5×).

А `set_waitlist_status_rpc` отказывает **другим** текстом:
`FORBIDDEN: немає доступу або запис не знайдено`.

⚠️ **И это опровергает написанное в самом гарде.** Комментарий в
`guard_radiologist_no_write` гласит: «Те саме повідомлення, що в 0136 і **в RPC
для чужої клініки**: існування рядка не підтверджуємо». Строки **не совпадают** —
проза утверждает свойство, которого у кода нет. Ровно тот класс, за который
журнал ругает сам себя.

### A-1 — что различает радиолог в `set_waitlist_status_rpc`

| вход | ответ |
|---|---|
| строка есть в ЕГО центре | `FORBIDDEN: запис не знайдено` *(от триггера)* |
| строки нет / чужой центр | `FORBIDDEN: немає доступу або запис не знайдено` *(от RPC)* |

Радиолог проходит собственный гейт RPC (ветка «персонал своего центра»), и
только UPDATE упирается в триггер. Два разных текста → **оракул существования**.

### A-2 — `schedule_from_waitlist_rpc` различает ТРИ состояния

Здесь хуже: BEFORE-триггер срабатывает только если UPDATE **нашёл** строку.

| вход | ответ |
|---|---|
| строка в его центре, статус `waiting` | `FORBIDDEN: запис не знайдено` *(триггер)* |
| строка в его центре, статус НЕ `waiting` | `WAITLIST_STALE: кандидата вже записує інший оператор` |
| строки нет / чужой центр | `WAITLIST_NOT_FOUND: кандидата не знайдено` |

То есть утекает не только существование, но и **статус** кандидата.

### Сила оракула — названа честно

Чтобы им воспользоваться, нужен **валидный UUID** кандидата: uuid v4 не
угадывается. Поэтому это не средство перечисления, а подтверждение уже
имеющегося id (утёкшего в логе, ссылке, прежнем назначении кабинета). Severity —
**Low**, но дефект настоящий, и он лежит в слое, который обязан молчать.

## A-3. `cancel_case_rpc` — НЕ дефект, и вот почему

Ветка направителя в `cancel_case_rpc` уже ограничена тремя условиями:

```sql
where id = p_case_id and (created_by = v_actor or referrer_id = v_actor) for update;
...
if not public.auth_can_refer(v_clinic) then  -- активный грант к центру
...
if exists (select 1 from queue_entries where case_id = ... and status in
           ('in_progress','done','no_show','not_held')) then CASE_STARTED
```

**Замер: где вообще живёт `auth_referrer_can_book_room`.**

| место | роль |
|---|---|
| политика `queue_write_referrer` | размещение |
| политика `waitlist_write_referrer` | размещение |
| `create_case_rpc` | размещение |
| `add_case_step_rpc` | размещение |
| `case_from_entry_rpc` | размещение |
| `queue_reschedule_rpc` | размещение |
| `invariants_check` | пин на список |

Гейт отвечает на вопрос «**в какой кабинет вам можно ПОЛОЖИТЬ пациента**».
Отмена не кладёт никого — она ставит `cancelled`. Требовать здесь право на
кабинет означало бы: направитель, чей шаг персонал перенёс в кабинет вне его
списка, **теряет возможность отменить собственного пациента**. Это ухудшение, а
не защита.

**Вывод: находку закрываем как неверную**, с оговоркой — если появится операция,
которая при отмене что-то *переразмещает*, вопрос откроется заново.

## A-4. Межтенантный замок в `integration_apply_status` — подтверждён зондом

Функция — `SECURITY DEFINER`, ACL `postgres, service_role` (для `authenticated`
недоступна). Вызывается из `app/api/integrations/v1/appointments/[id]/events/route.ts`:
`p_clinic` сервер берёт **из ключа** (доверенное), а `p_entry` приходит **из URL**
(контролируется вызывающим).

Порядок в теле (нумерация строк `prosrc`):

```
80:   select q.case_id into v_case from queue_entries q where q.id = p_entry;   -- БЕЗ клиники
82:   perform 1 from patient_cases where id = v_case for update;                -- БЕЗ клиники
85-89: select ... from queue_entries where q.id = p_entry for update;           -- БЕЗ клиники
94:   if not found or v_row_cl is distinct from p_clinic then ... not_found     -- проверка ПОСЛЕ
```

Все соседние операторы клиникой ограничены (`on conflict (clinic_id,
source_event_id)`, `where clinic_id = p_clinic and source_event_id = v_sid`, и
т. д.) — **эти три оператора выпадают из общего правила.**

### Зонд на проде (транзакция откачена исключением)

Ключ клиники **A**, `p_entry` — запись клиники **B**:

```
PROBE_0199 txid=916930 result=not_found
  ЧУЖА queue.xmax 803178 -> 916930
  ЧУЖИЙ case.xmax  782737 -> 916930
```

`FOR UPDATE` штампует `xmax` строки своим txid — значит **обе чужие строки были
залочены нашей транзакцией**, и лишь потом функция вернула `not_found`.

**Что это даёт и чего не даёт.** Данные не утекают: `not_found` возвращается до
любого чтения полей. Но держатель интеграционного ключа центра A может:

1. брать `FOR UPDATE`-замки на строки центра B на всё время своей транзакции —
   **межтенантная блокировка**, то есть отказ в обслуживании чужому центру;
2. отличать «id существует и сейчас занят» от «id не существует» по тому,
   **заблокируется ли вызов** — временной оракул поверх «одного ответа», который
   комментарий на строке 91 как раз и обещает.

Severity — **Medium**: нужен валидный интеграционный ключ (то есть партнёр, а не
аноним), но межтенантность — свойство, которое продукт обещает безусловно.

### Почему так вышло (и это важнее самого бага)

Комментарий на строке 91 объясняет, зачем `select ... for update` идёт **без**
фильтра по клинике: «чужа клініка і неіснуючий запис — ОДНА відповідь (без
оракула існування)». Намерение верное — анти-оракул. Цена намерения не была
названа: чтобы *сравнить* клинику, строку сначала **берут и лочат**.
Анти-оракул и отсутствие межтенантного замка совместимы — нужно лишь прочитать
клинику **без** `for update`, сравнить, и лочить уже своё.
