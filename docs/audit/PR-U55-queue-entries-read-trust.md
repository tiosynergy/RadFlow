# U-55 — «не прочитали» ≠ «немає доступу»

**Гілка:** `feat/entry-read-trust` · **Сесія 49, шостий пакет** (після U-33, U-13,
0166/0167, U-17+U-18+U-14)

---

## 0. Як знайшлося

Не читанням коду. У попередньому пакеті сканер `readErrorTrust` навчили таблиці
`incidents` і поставили в `FILES` файл `app/queue/actions.ts`. Борг U-55 просив
доробити те саме для `queue_entries` — і одна ця таблиця дала **вісім** місць:

| | |
|---|---|
| читань `queue_entries` у файлі | **8** |
| із них у формі, якої сканер не знав | **3** (F0 `readRow(await …)`, F4 `let q = …`) |
| із них зі справжнім дефектом | **5** |
| із них годує **авторизацію** | **1** (`setQueuePriority`) |

П'ять місць писали `const { data: cur } = await supabase.from("queue_entries")…`
і вели `null` в одну гілку — «Немає доступу або запис не знайдено». Тобто
транзієнт мережі показувався користувачеві як **відмова в доступі**: діагноз, за
яким він піде питати права замість «повторіть».

---

## 1. Найдорожче місце — `setQueuePriority`

```ts
const [{ data: profile }, { data: entry }] = await Promise.all([…]);   // error не звʼязували
const isAdmin = profile?.role === "admin";
```

Збій читання профілю → `profile = null` → `isAdmin = false` → **адміністратор
діставав «Змінювати пріоритет може адміністратор або лікар-направник»**.

Дірки в безпеці тут не було: поведінка fail-CLOSED, і людині відмовляли, а не
дозволяли зайве. Коштувало інше — **людині казали, що вона не той, ким є**, і
зрозуміти, що це збій мережі, вона не могла нізвідки.

---

## 2. Що змінилось — і що НЕ змінилось

**Не змінилось:** жодне з п'яти місць не стало ані суворішим, ані м'якшим. Усі
як відмовляли, так і відмовляють. Змінився **діагноз**:

| причина | було | стало |
|---|---|---|
| рядка не видно / немає | «Немає доступу або запис не знайдено» | те саме |
| читання не вдалося | «Немає доступу або запис не знайдено» | «Не вдалося прочитати запис — спробуйте ще раз» |

Код відповіді на незнання — **`generic`, а не `forbidden`**: це не відмова в
доступі, а `ReferralPortal` підмінює текст саме для `forbidden` (урок U-18,
ревʼю р1).

**Два місця свідомо не зупиняють дію.** `updatePatientDetails` і `caseFromEntry`
читають знімок ДО мутації лише щоб вибрати сім'ю події журналу. Відмовити
користувачеві у виправленні телефона пацієнта через збій читання рядка **для
журналу** — гірше за деградовану подію. Але тепер вони не мовчать: пишуть
канонічне `important_event.skipped` / `pre_snapshot_unreadable`.

## 3. Правило: `lib/readRow.ts`

```ts
export type RowRead<T> =
  | { known: true; row: T }
  | { known: false; reason: "error" | "missing" };
```

Три відповіді замість двох. Помилка **переважає** над даними (PostgREST може
віддати і те, і те); відповіді немає взагалі — теж «не знаємо»; порожній
**об'єкт** `{}` — це рядок, а не незнання (вибірка одного поля з `null`-значенням
дала б саме `{ referrer_id: null }`).

Параметр типізований по **відповіді**, а не по даних: виведення через поле `data`
над union-типом `maybeSingle()` давало `T = never`.

## 4. Що знайшло ревʼю — включно з моєю власною регресією

| # | Знахідка | Наслідок |
|---|---|---|
| MAJOR | **Гейт ролі стояв ПЕРЕД обчисленням власника** | направник-власник запису, якому роль не потрібна взагалі, діставав відмову через збій читання **чужого йому** профілю — **регрес, який я вніс сам** |
| MAJOR | Лічильник гілок лишався 4/4 на **перевернутих** гілках | сторож мовчав про повністю переставлені діагнози |
| MAJOR | `statementEnd` мав `depth <= 0` | на виразі без `;` вікно поїхало **на 1057 символів** (замір), перескочило кінець функції і сіло на чужий `catch (error)` — червоне ставало зеленим |
| MAJOR | Текст логу брехав про наслідок | у `updatePatientDetails` емісія стоїть під `if (pre?.clinic_id)` — події **немає зовсім**, вона не «деградує» |
| MAJOR | Власний словник логів (`read.trust` / `entry_attribution_*`) | пропуски журналу шукають одним запитом по `important_event.skipped` — власне ім'я робило б тихо саме там, де ми домагаємось гучності |
| MAJOR | Лог шумів і на звичайній відмові доступу | звужено до `reason === "error"` |

Порядок гілок в авторизації — **не стиль, а поведінка**, і мутація N19
відтворює саме цю регресію.

## 5. Фальсифікація — 24/24 з ЗЕЛЕНОЮ базовою лінією

`scripts/falsify-u55.mjs`. Перед мутаціями стенд один раз ганяє немутований
набір і вимагає зеленого; кожна мутація має **очікуване ім'я** червоного тесту.

Що стенд знайшов у самих сторожах:

* **N08** — якір **не унікальний** (блок `if (!curRead.known) {…}` стоїть у файлі
  двічі слово в слово). Виправлено довшим хвостом, а не «приблизним» збігом.
* **N15** — розмивання `RULES = "\w+"` лишалось **зеленим**: зразок «чужа
  функція» брав **неімпортовану** `notARule`, тож перевірку проходила
  ІМПОРТ-умова, а не перелік правил. Дві незалежні умови дістали два незалежні
  зразки.
* **N16** — якір **не знайдено**: ревʼю дописало до `deferredChecked` другу
  законну гілку, і стара форма зникла. Саме для цього перевірка й стоїть.
* **N24** — межі вікна (`statementEnd`) не пінив **жоден** тест: зсув вікна
  робить сканер лише **поблажливішим**, а поблажливість завжди зелена. Додано
  поведінковий self-test, який перевіряє fail-CLOSED **викликом**.

Плюс одна **еквівалентна** мутація (N04, `!res.data` замість явної перевірки на
`null/undefined`), залишена в наборі свідомо зеленою: різниця неспостережна на
рядках таблиці, і жоден чесний тест її не розрізнить.

Окремо, поза стендом, полагоджено **декоративного сторожа**: цикл у тесті «і при
цьому дію НЕ зупиняє» шукав голе `if (!XRead.known) {` і після звуження гілок
не знаходив **нічого** — крутився нуль разів. Тепер кількість гілок пінимо
окремо: нуль збігів — це червоне.

## 6. Жива перевірка на проді — в ОБИДВА боки

Уся правка стоїть на одній фактичній посилці: **невидимий рядок і збій читання
приходять з бази ПО-РІЗНОМУ**. Якби невидимий рядок теж приходив помилкою (або
збій — нулем рядків), новий діагноз брехав би рівно там, де мав лікувати.
Заміряно на живій базі 2026-08-30, обидва боки:

| напрям | замір | що прийшло |
|---|---|---|
| **чужий рядок** (RLS не пускає) | читання `queue_entries` по id рядка іншої клініки під `role authenticated` з JWT адміна першої | **0 рядків, помилки НЕМАЄ** (свої 2 рядки при цьому видно) |
| **збій читання** | те саме читання під `statement_timeout = '20ms'` з `pg_sleep(1)` | **помилка `57014`**, а не порожня вибірка |

Тобто `missing` і `error` справді розрізняються джерелом, а не здогадкою:
перший бік лишає «Немає доступу або запис не знайдено», другий — дає нове
«Не вдалося прочитати запис». Синтетичних даних для заміру не створювалось:
обидва боки виміряні на наявних рядках у транзакції з `rollback`.
