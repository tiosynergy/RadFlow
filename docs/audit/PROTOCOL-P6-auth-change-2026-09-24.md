# П-6 — протокол замера: конфигурация смены пароля и почты

**Статус на 24.09.2026 (с77): протокол готов, живой прогон НЕ выполнялся.**
Прогон меняет состояние `auth` прода (пароль, почта, сессии тестового аккаунта),
поэтому идёт **только по явному слову владельца, по названному им id и с образом
«до»**. Пароли агент не спрашивает и не вводит — владелец делает это сам.

Откуда пункт: находка 15.09 (план §3), блокирующий пункт **П-6** с 22.09
(`ToDo_Production.md` §1), путь **T9** в `THREAT_MODEL_2026-09-14.md` §10 (записан
как **незамеренный**). Этот документ — чем именно перевести T9 из «незамерено» в
результат и на что смотреть при решении о четырёх тумблерах Auth.

⚠️ Это протокол **проверки собственной конфигурации** на тестовом аккаунте, а не
инструкция атаки. Все действия идут либо в дашборде Supabase, либо штатными
экранами RadFlow, либо запросом к БД. Никакого воспроизведения «за злоумышленника»
и никаких готовых полезных нагрузок здесь нет и быть не должно: вопрос «требует ли
платформа повторной аутентификации» решается настройкой и наблюдением состояния,
а не эксплойтом.

---

## 1. Вопрос, на который отвечает замер

Один: **какие из четырёх настроек Auth реально влияют на поведение продукта, и
что сломается, если их включить.** Настройки (прочитаны владельцем 15.09, живьём
не проверены): `Secure email change` — выкл, `Secure password change` — выкл,
`Require current password when updating` — выкл, минимальная длина пароля — 6.

Решение после замера — за владельцем: он не «просто щёлкнуть тумблер», потому что
`Secure email change` и `Require current password when updating` меняют штатные
сценарии (приглашение персонала, восстановление доступа направителя).

Контекст из кода (замер с77, это входные данные, а не вывод): приложение **ни
разу** не вызывает клиентский `auth.updateUser`. Пароль меняют только серверные
маршруты под admin API — `/api/account/set-password` (по одноразовому
`invite_token`) и `/api/staff/password` (админом). Почту приложение не меняет
нигде. Вход по логину резолвит адрес из `auth.users` (`resolve_login_email`), а
экраны показывают копию `profiles.email`. Отсюда две вещи, которые надо
подтвердить замером, а не принять: (1) включение тумблеров, вероятно, **не ломает
ни один живой сценарий**, потому что самообслуживаемого пути смены в продукте нет;
(2) если платформенный путь смены всё же открыт, интерфейс после смены почты будет
показывать старый адрес (рассинхрон `profiles.email` ↔ `auth.users.email`).

## 2. Шаг 0 — прочитать настройки (владелец, дашборд, без записи)

Записать в таблицу §6 как видно на экране:

1. **Authentication → Providers → Email:** `Confirm email`, `Secure email
   change`, `Secure password change`, `Require current password when updating`,
   `Minimum password length`, `Password requirements`.
2. **Authentication → Emails → SMTP:** включён ли **свой SMTP**. ⚠️ Если нет —
   встроенная почта Supabase шлёт письма только адресам участников команды
   проекта. Тогда проверка почтового шага может «не пройти» **случайно** (письмо
   до внешнего адреса не дойдёт), а не потому что путь закрыт. Это нужно знать до
   прогона, иначе результат прочитается неверно.
3. **Authentication → Emails:** включены ли уведомления «пароль изменён» / «почта
   изменена» и на какой адрес.
4. **Authentication → Sessions** (если доступно на тарифе): тайм-бокс сессии,
   тайм-аут неактивности, «одна сессия на пользователя».
5. **Authentication → Rate Limits:** лимит писем в час.

## 3. Шаг 1 — тестовый аккаунт и образ «до»

**Аккаунт называет владелец:** не свой, не аккаунт реального центра. Замер 24.09
(агрегатами, без адресов): у админов (2) и регистратора (1) адреса настоящие, у
CEO (2) и радиолога (1) служебные `*.radflow.local`, у направителей 2 служебных и
1 настоящий; незавершённых смен почты — 0.

* Предпочтительно — аккаунт с настоящим адресом, который читает владелец: тогда
  видно, приходят ли уведомления, и откат почты делается тем же путём назад.
* Радиолога не брать: служебный адрес случаен (`rad.<hex>@…`), «по логину» его не
  вернуть.

Образ «до» — **редактированный** (правило проекта: id, даты, флаги — да; адреса и
хеши — нет). Агент снимает запросом с явным id, кладёт в §6:

```sql
-- П-6: состояние аккаунта без адресов и хешей. Подставить названный id.
select u.id,
       split_part(u.email, '@', 2)                      as email_domain,
       u.email_confirmed_at, u.updated_at, u.last_sign_in_at,
       coalesce(u.email_change, '') <> ''               as pending_email_change,
       u.email_change_sent_at, u.email_change_confirm_status,
       u.banned_until,
       (select count(*) from auth.sessions s where s.user_id = u.id)                               as sessions,
       (select count(*) from auth.refresh_tokens r where r.user_id = u.id::text and not r.revoked) as live_refresh_tokens,
       (select split_part(p.email, '@', 2) from public.profiles p where p.id = u.id)               as profile_domain
  from auth.users u
 where u.id = '<ID>';
```

⚠️ `auth.audit_log_entries` на проде **пуст** (замер 24.09: 0 строк) — журнал Auth
живёт в логах платформы. Второй источник доказательств — логи Auth через
`query_logs`: метод, путь, статус, время (адреса не выводить).

## 4. Шаг 2 — что проверяем и чем подтверждаем

Каждый пункт — наблюдение над состоянием, снятое **до** и **после** штатного
действия. Действие выполняет владелец: смену пароля тестового аккаунта — из
раздела account settings дашборда Supabase (там же, где живёт эта настройка) или
штатным маршрутом продукта; смену почты — там же. Агент между «до» и «после»
только читает `auth.users`/`auth.sessions` запросом §3 и логи Auth.

| # | что смотрим | вывод «путь открыт» | вывод «путь закрыт» |
|---|---|---|---|
| П-1 | требуется ли при смене пароля текущий пароль / повторная аутентификация | смена проходит без него | платформа отвечает отказом «нужен текущий пароль / повторная аутентификация» |
| П-2 | куда уходит подтверждение при смене почты | только на новый адрес | в `auth.users` появляется `email_change_token_current` и/или письмо на **старый** адрес (при `Secure email change`) |
| П-3 | что показывает интерфейс после смены почты | старый адрес (рассинхрон `profiles.email` ↔ `auth.users.email`) | адрес синхронизирован |
| П-4 | переживают ли живые сессии смену пароля и админский сброс | `live_refresh_tokens` не обнуляется | сессии инвалидируются |
| П-5 | принимает ли платформа пароль короче 8 (минимум приложения) при минимуме 6 у GoTrue | 6-символьный проходит | отклонён |

И обратная проверка, ради решения о включении тумблеров:

| П-6 | после включения `Secure email change` + `Require current password when updating` прогнать штатные сценарии: приглашение сотрудника (`/api/staff` → `/set-password`), вход после смены пароля, админский сброс (`/api/staff/password`), самообслуживание направителя (`/api/referral/profile`) | что-то из этого перестаёт работать → тумблер имеет цену, назвать её | всё работает → включение безопасно |

## 5. Шаг 3 — откат (в тот же прогон, не «потом»)

* **Пароль:** владелец задаёт тестовому аккаунту известный пароль обратно тем же
  путём. Инвалидацию прошлых сессий это не отменяет — это норма.
* **Почта:** если менялась — вернуть на исходный адрес тем же путём; для аккаунта
  со служебным адресом возврат возможен только admin API, поэтому предпочтителен
  аккаунт с настоящим адресом (§3).
* **Проверка отката — запросом §3:** `email_domain` и `profile_domain` совпали с
  образом «до», `pending_email_change = false`. Успех подтверждается запросом, а
  не тем, что «команда не выдала ошибку».
* Тумблеры, включённые на шаге П-6, вернуть в исходное состояние из §6, если
  владелец не решил оставить их включёнными.
