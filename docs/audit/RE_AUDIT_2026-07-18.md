## Актуальные находки

### High — операции над одним кейсом не сериализованы

`add_case_step_rpc` читает кейс и вычисляет следующий `case_step` без блокировки строки `patient_cases`.

```sql
select * into v_case from public.patient_cases where id = p_case_id;
select coalesce(max(case_step), 0) + 1 into v_step_no
from public.queue_entries where case_id = p_case_id;
```

Два параллельных вызова могут получить один и тот же номер шага. Триггеры `0095` и `0099` проверяют существующие строки, но не видят незафиксированный шаг конкурента. Поэтому параллельные операции способны создать два шага с одинаковым номером, одним кабинетом или пересекающимся временем.

Возможна и гонка `cancel_case_rpc` ↔ `add_case_step_rpc`: отмена фиксирует `patient_cases.status = 'cancelled'`, а параллельное добавление, ранее прочитавшее `open`, создаёт новый активный шаг. Итог — активный шаг в отменённом кейсе.

**Доказательства:**

- `supabase/migrations/0097_add_case_step_rpc.sql:42,69`;
- `supabase/migrations/0092_cancel_case_rpc.sql:48–93`;
- `supabase/migrations/0095_case_distinct_room.sql`;
- `supabase/migrations/0099_fix_case_time_overlap_cast.sql`.

**Рекомендация:** все мутации одного кейса должны брать блокировку кейса в одинаковом порядке.

```sql
select * into v_case
from public.patient_cases
where id = p_case_id and clinic_id = v_clinic
for update;
```

Эта блокировка нужна в `add_case_step_rpc`, `cancel_case_rpc` и в ветке существующего кейса `case_from_entry_rpc`.

Нужен также DB-предохранитель:

```sql
create unique index if not exists queue_case_step_unique
on public.queue_entries (case_id, case_step)
where case_id is not null;
```

Перед созданием уникального индекса следует найти и исправить возможные исторические дубли.

### High — `case_from_entry_rpc` способен создать кейс-сироту

Исходная запись очереди читается без `FOR UPDATE`:

```sql
select * into v_entry from public.queue_entries where id = p_entry_id;
```

При двух параллельных вызовах оба могут увидеть `case_id = null`, создать разные кейсы и по очереди переписать `case_id` исходной записи. Первый созданный кейс останется с одним дополнительным шагом, но без исходной записи.

**Доказательства:**

- `supabase/migrations/0098_case_from_entry_rpc.sql:42,72–130`;
- `app/queue/actions.ts:2135–2163`.

**Рекомендация:** заблокировать исходную запись и после получения блокировки повторно принять решение о ветке сценария.

```sql
select * into v_entry
from public.queue_entries
where id = p_entry_id
for update;
```

### High — прямой `UPDATE case_id/case_step` обходит модель кейсов

Миграция `0091` выдаёт `authenticated` право обновлять эти колонки:

```sql
grant update (case_id, case_step) on public.queue_entries to authenticated;
```

Триггер гарантирует только совпадение клиники. Он не проверяет открытость кейса, совпадение пациента, уникальность шага или выполнение операции через разрешённый RPC. Пользователь, имеющий RLS-доступ к записи, может вручную привязать её к произвольному кейсу своей клиники через PostgREST.

**Доказательства:**

- `supabase/migrations/0091_patient_cases.sql:55–66,81–104`;
- `supabase/migrations/0057_referrer_write_assigned.sql`.

**Рекомендация:** удалить прямое право обновления. Специализированные `SECURITY DEFINER` RPC продолжат работать от владельца функции.

```sql
revoke update (case_id, case_step)
on public.queue_entries
from authenticated, anon;
```

### Medium — статус кейса становится неактуальным после штатной смены статуса шага

`patient_cases.status` пересчитывается только в `cancel_case_rpc`. Если все шаги завершены через `queue_set_status_rpc`, кейс остаётся `open` в БД. UI скрывает проблему, поскольку рассчитывает отображаемый статус из шагов в `lib/case.ts`.

Последствия: завершённый кейс остаётся доступным для добавления шага; будущая аналитика и n8n прочтут неверный жизненный цикл.

**Доказательства:**

- `supabase/migrations/0092_cancel_case_rpc.sql:76–93`;
- `supabase/migrations/0097_add_case_step_rpc.sql:49`;
- `components/CaseModal.tsx:136–141`;
- `lib/case.ts:33–43`.

**Рекомендация:** добавить единый DB-пересчёт статуса с запуском после изменения `status` или `case_id` у `queue_entries`.

### Medium — при позднем добавлении шага теряется вес пациента

`patient_cases` не хранит `patient_weight`; `add_case_step_rpc` создаёт добавленный шаг с `patient_weight = null`. Исходные шаги получают вес из формы, но поздние — уже нет.

**Доказательства:**

- `supabase/migrations/0091_patient_cases.sql:31–46`;
- `supabase/migrations/0097_add_case_step_rpc.sql`;
- `app/queue/actions.ts:2062–2071`.

**Рекомендация:** добавить `patient_weight` в снимок `patient_cases` и использовать его во всех case RPC.

### Medium — ограничение 300 строк скрывает поздние CITO-кандидаты

Вкладка `waiting` сначала выбирает не более 300 строк по дате создания, а потом сортирует их по приоритету только в браузере. Новый `cito` за пределами первых 300 строк не будет показан, хотя должен оказаться первым.

**Доказательства:**

- `components/WaitlistBoard.tsx:33–35`;
- `components/WaitlistBoard.tsx:185–195`;
- `components/WaitlistBoard.tsx:346–351`.

**Рекомендация:** реализовать серверную выборку доски с SQL-приоритетом и курсорной пагинацией.

```sql
order by case priority_level
  when 'cito' then 0
  when 'urgent' then 1
  else 2
end,
created_at asc;
```

### Medium — отсутствуют двухсессионные тесты конкурентности

Smoke-скрипты проверяют отдельные вызовы и права, но не воспроизводят параллельные транзакции.

Нужны сценарии:

1. два `add_case_step_rpc` в один кейс;
2. два `case_from_entry_rpc` для одной записи;
3. `cancel_case_rpc` одновременно с добавлением шага;
4. прямой `UPDATE case_id/case_step` должен завершаться `42501`;
5. завершение всех шагов должно менять статус кейса;
6. `cito` после 300-й waiting-записи должен быть видим первым.

### Low — ошибки RPC счётчиков не отображаются

`loadCounts()` игнорирует поле `error` и оставляет на экране старые значения. Нужен `countsErr` и ненавязчивое состояние «счётчики не обновлены».

**Доказательство:** `components/WaitlistBoard.tsx:203–215`.

### Low — неинформативное сообщение последнего коммита

Коммит `13ea3c9` имеет сообщение `++++`, что ухудшает трассируемость изменений.
