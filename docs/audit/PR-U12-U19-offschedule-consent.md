# U-12 / U-19 — згода на роботу поза графіком їде з тим, хто має право її дати

**Гілка:** `fix/u12-u19-offschedule-consent` → `dev` → `main`
**Сесія 47.** Міграцій немає. Продові дані не змінювались.

## Правило, довкола якого все крутиться (0077, не змінювалось)

`app/queue/actions.ts`, `scheduleBlock`:

```ts
if (!info) return { blocked: null, offSchedule: false };          // у межах графіка
if (!info.confirmable) return { blocked: offSchedError(info) };   // не можна НІКОМУ
if (!opts.isStaff) return { blocked: OFF_SCHED_ERR };             // направник — НІКОЛИ
if (!opts.offSchedule) return { blocked: offSchedNeedsConfirm(info) };
return { blocked: null, offSchedule: true };
```

`isStaff` = `profiles.clinic_id` викликача дорівнює `clinic_id` запису (у
направника і CEO там NULL). Порядок гілок — частина правила: спершу відсікається
неможливе для всіх, потім роль, і лише потім згода.

**Рішення власника (с47): серверне правило не чіпаємо. Бреше клієнт — його й
правимо.**

## Дефект

Редактор досліджень (`StudyEditModal`) не знав про це правило нічого і помилявся
в ОБИДВА боки.

| # | Що було | Наслідок |
|---|---|---|
| 1 | проп `offSchedule` був необовʼязковим із дефолтом `false`, і `ReferralPortal` його просто не передавав | для направника запис, що ЛЕГАЛЬНО стоїть поза графіком (17:55 у кабінеті до 18:00), ставав **незбережуваним назавжди**: стеля рахувалась по кінцю графіка → «⚠ Не вміщується» → сіре «Зберегти». Рівно той провал, заради якого писалась 0077 |
| 2 | згода в `onConfirm` була необовʼязковою деталлю `meta`, а пʼятий аргумент Server Action — `offSchedule?` | `ReferralPortal.doEditStudies` місяцями кликав дію ЧОТИРМА аргументами. Компілятор мовчав: пропущений необовʼязковий аргумент — легальний виклик |

Окремо, у формі створення направлення (`NewReferral`, той самий файл) — **U-19**:
при збої читання дня в `catch` лишались ПРОЧИТАНІ РАНІШЕ `override` і
`roomSchedule` іншої дати, а три підказки про графік стояли сиблінгами гілки
`slotsErr` — тобто портал міг сказати «🚫 не працює · Новий рік» про 2 січня.

## Правка

**Механізм, а не уважність.** Три пропи стали ОБОВʼЯЗКОВИМИ і БЕЗ дефолта, тож
повноту місць виклику перелічує `tsc`:

* `StudyEditModal.offSchedule: boolean` — запис сам стоїть поза графіком;
* `StudyEditModal.allowOffSchedule: boolean` — **дзеркало серверного `isStaff`**;
* `CaseModal.referralMode: boolean` — бо відколи екран кейса роздає
  `allowOffSchedule`, цей проп означає ще й РОЛЬ.

Той самий прийом і на сервері: `editQueueEntryStudies(..., offSchedule: boolean)`
— позиційний аргумент без дефолта, `z.boolean()` без `.optional()`.

Ім'я `allowOffSchedule` СПІЛЬНЕ з `RescheduleModal` свідомо: це одне правило на
двох сусідніх екранах правки запису. Відмінність — обовʼязковість: там мовчання
означає «прав немає» (рятує направника, але мовчки забирає овертайм у нової
дошки персоналу), тут відповідь мусить бути написана.

**Чесна відмова замість сірої кнопки.** Направник більше не гадає, ЧОМУ
«Зберегти» неактивне:

```
⏰ Поза графіком кабінету. Разом 60 хв — дослідження триває довше,
   ніж працює кабінет (до 18:00). Роботу поза графіком підтверджує
   лише центр, тож зберегти такий склад звідси не вийде.
   Змінити склад цього запису може лише центр — зверніться до адміністратора.
```

**Що знайшов сам `tsc`:** тип `BoardReferral` у `ReferrerBoard` (сама дошка
`off_schedule` не показує, але саме її рядок їде в модалку) і те, що `CaseModal`
рендерять ДВОЄ — `QueueBoard` і `ReferralPortal`. Константа `allowOffSchedule={true}`
всередині кейса тихо дала б направнику чужі права — тобто правка U-12
відтворила б власний дефект у сусідньому екрані. У формулюванні находки цього
не було.

## Що знайшли два раунди ревʼю

Прийнято і виправлено — 5:

1. **Текст відмови брехав для трьох видів із пʼяти.** `closed`, `before_start`,
   `too_late` мають `confirmable: false`, і сервер відхиляє їх гілкою ДО
   перевірки ролі — тобто центр теж безсилий. «Зверніться до центру» тут коштує
   дзвінка й повертає пацієнта ні з чим. Тепер банер розрізняє два види відмови,
   і для непідтверджуваних радить перенести запис.
2. **Три різні числа на одному екрані.** Рядок «Доступно у слоті» рахується по
   РОЗШИРЕНІЙ стелі (графік + 2 год grace, перерва не обмежує). Поруч із банером
   відмови це давало «доступно 125 хв» / «разом 60 хв» / «вміщується 5 хв».
   При рольовій забороні чесна межа одна — та, що в графіку.
3. **Два різні мінімуми.** `valid` приймає рядок від 5 хв, а порада «скоротіть
   до N хв» вимагала `MIN_STUDY` (15) — і казала «вкластися неможливо» там, де
   форма сама б зберегла 10-хвилинний склад. Введено спільну `MIN_ROW_DUR = 5`
   на обидва місця.
4. **Порада стрибала на очах.** `inSchedCap` включає стелю за наступним записом,
   а поки зайнятість не прочитана, вона дорівнює поточній тривалості. Додано
   `busyReady`.
5. **U-19: лічильник «вміщується ще N»** — таке саме твердження про день, як і
   три підказки, — лишався поза гейтом і при збої читання рахувався по хардкоду
   08:00–18:00 з порожньою зайнятістю. Тобто показував найбільше число саме
   тоді, коли ми не знаємо нічого.

Перевірено і **відхилено** — з причинами:

* «`off_schedule` у SELECT покладе список направника колонковими грантами» —
  у `queue_entries` табличний `GRANT SELECT` для `authenticated`, а `CaseModal`
  у режимі направника вже читає цю колонку в `STEP_SELECT` (0118). Перевірено
  запитом до прода.
* «`meta.offSchedule` впаде на `undefined`» — `onConfirm` типізований, єдиний
  виклик у `save()` завжди передає `meta`; сусідній `(meta && meta.dur)` —
  легасі-захист під стару сигнатуру.
* «липкий `offOk` між записами» — модалки монтуються умовно
  (`{editStudiesFor && <StudyEditModal…>}`), стан не переживає закриття.
* «`referralMode` fail-open через `!`» — проп обовʼязковий, `undefined`
  передати не можна; новий екран ловить сканер місць виклику.
* «zod без `.optional()` покладе стару вкладку» — ID Server Action залежить від
  тіла функції; стара вкладка не дійде до нового коду в принципі, а `parseInput`
  повертає людське повідомлення, а не виняток.
* «при `schedErr` треба заборонити збереження» — це зробило б екран
  СТВЕРДЖУВАЛЬНИМ на невідомості (урок U-1/U-2). Стелю там і так тримає
  `committedDur`: скоротити можна, збільшити — ні.
* «переплутані аргументи `roomScheduleFor` / `effectiveRoomBreaks`» — у функцій
  РІЗНІ сигнатури за задумом; виклики коректні.
* «CEO дістане чужі права на дошці персоналу» — у CEO `clinic_id = NULL`,
  `/queue` віддає його редіректом, на `/call-list` дошка порожня (нема на чому
  відкрити модалку). Записано в беклог як розбіжність сторінок, не як дірку.

## Знайдене й СВІДОМО не виправлене тут (у беклог)

* **U-20 (H).** Персонал не може підтвердити НОВИЙ вихід за графік у редакторі
  досліджень. При `offSchedule === false` `availableDur` тотожно дорівнює
  `inSchedCap` (обидві пари стель збігаються), тож `crossesNow ⟺ overflow` і
  `needsOffConfirm` НЕДОСЯЖНИЙ — галочка існує лише для записів, що вже стоять
  поза графіком. Сервер подовження за межу з підтвердженням дозволяє. Це той
  самий клас провалу, що U-12, лише для персоналу. Правка: відкривати grace-смугу
  при `offSchedule || allowOffSchedule` — і це окремий пакет, бо змінює стелю
  тривалості в КОЖНІЙ правці персоналу.
* **U-21 (M).** Непідтверджувані види (`closed` / `before_start` / `too_late`)
  невидимі персоналу: `offForbiddenForRole` завʼязаний лише на роль, кнопка
  активна, сервер відхиляє. Людина отримує помилку після натискання зеленої
  кнопки. Правка: `offHardBlocked = !!offNow && !offNow.confirmable` у `valid`
  і в банер для ВСІХ ролей.
* **U-22 (M).** Перерва, що вже ТРИВАЄ на момент старту запису, не бачиться
  стелями (`nextBreakStart` фільтрує `m > startMin`), а `offScheduleKind` ловить
  будь-який перетин. Для персоналу — глухий кут; для направника банер спрацьовує
  правильно.
* **P3.** `/call-list` не віддає CEO редіректом, на відміну від `/queue`.
* **P3.** `allowOffSchedule` на дошках персоналу — літерал, а не обчислене
  дзеркало `isStaff`. Сьогодні коректно (сторінки віддають `clinicId` саме з
  профілю), стане неправдою з появою мультиклінічної дошки персоналу.
