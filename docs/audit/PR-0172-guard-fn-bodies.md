# PR 0172 — тіла функцій, що вирішують доступ, під інваріантом

**Міграція:** `supabase/migrations/0172_guard_fn_bodies_invariant.sql`
**Коміт коду:** `d3c53cf`
**Сесія:** с56, пакет 21.

Передрук `public.invariants_check`: **18 перевірок → 19**.

---

## 1. Що закрито

0171 сам назвав цю межу: №17 `guard_triggers` пінить `pg_get_triggerdef`, а
там є **імʼя** функції і немає її **тіла**. Отже:

```sql
create or replace function public.guard_profile_privileges()
returns trigger language plpgsql security definer
set search_path to 'public','pg_temp'
as $$ begin return new; end $$;
```

лишає №17 дослівно зеленою і при цьому **вимикає сторожа привілеїв**: тригер
на місці, увімкнений, визначення побайтно те саме — а перевірки всередині
більше немає.

### Це не гіпотеза — це зонд із відкотом

Тимчасові таблиця й тригер у `pg_temp`, уся транзакція відкочена `raise`:

| замір | до вихолощення | після |
|---|---|---|
| `regexp_replace(pg_get_triggerdef(t.oid), '\s+', ' ', 'g')` | однаково | **однаково** (`def_same = t`) |
| дайджест тіла | `d8d32d62498c` | `ab85485bcc84` (`body_same = f`) |

Після зонда: `probe_rel = 0`, `probe_fn = 0`, `probe_tg = 0`,
`invariants_check(false)` → `ok:true, checked:18` — прод не зачеплено.

## 2. Що пінить №19 `guard_fn_bodies`

Двадцять два **підписи** (імʼя РАЗОМ із типами аргументів — див. §4):

| група | що саме |
|---|---|
| гарди №17 (11) | `guard_profile_privileges`, `guard_radiologist_scope`, `guard_radiologist_no_write`, `guard_no_client_delete`, `guard_no_client_delete_incident`, `guard_room_in_clinic`, `guard_waitlist_room`, `guard_referrer_doctor`, `guard_status_change_referrer`, `check_case_clinic_match`, `cleanup_orphan_clinic` |
| хелпери РІШЕННЯ (6) | `auth_is_admin()`, `auth_clinic_id()`, `auth_role()`, `auth_is_referrer()`, `auth_radiologist_room_ok(p_room uuid)`, `request_is_client_role()` |
| аудит | `fn_audit()` — слід на шести таблицях |
| роль нового профілю | `handle_new_user()` + окрема гілка на `auth.users.on_auth_user_created` |
| обсяг читання направника | `validate_referral_rooms()`, `prune_referral_rooms_on_room_delete()` |
| вихід назовні | `integration_outbox_enqueue()` |

**Як:** повний `md5` тіла з нормалізованими пробілами (плюс
`pg_get_function_sqlbody` — у SQL-функцій у формі `BEGIN ATOMIC` тіло лежить
не в `prosrc`) і окремо рядок атрибутів із названими полями
`secdef|vol|owner|lang|cfg`.

**Діагнози:** `missing:`, `body:<підпис>-><новий дайджест>`, `attrs:`,
`auth_trigger:`, `guard_fn_bodies_raised:<sqlstate>`.

## 3. ⚠️ ПЕРША РЕДАКЦІЯ БУЛА СЛАБША — чотири дірки, кожну підтверджено запитом

Два раунди ревʼю з різними лінзами (атакуюча / експлуатаційна), висновки
валідовані власними запитами, не прийняті на слово.

### (1) Гарди не вирішують самі — вони делегують

| гард | кому делегує рішення |
|---|---|
| `guard_profile_privileges` | `auth_is_admin()`, `auth_clinic_id()` |
| `guard_radiologist_scope` | `auth_role()`, `auth_radiologist_room_ok()` |
| `guard_radiologist_no_write` | `auth_role()` |
| `guard_status_change_referrer` | `auth_is_referrer()` |
| `handle_new_user` | `unique_login()`, `unique_login_from_email()` |

**Замір:** цих імен у тілі `invariants_check` було **0 згадок**. Пін лише на
тіла тригерних функцій лишав ту саму дірку поверхом нижче:
`create or replace function public.auth_is_admin() … as $$ select true $$` —
і всі перевірки зелені, а будь-який `authenticated` стає адміном.

### (2) `proowner` не пінився

Для `SECURITY DEFINER` власник — це і є права виконання. `fn_audit` ковтає
власні помилки (`exception when others then null`), тож зміна власника на
роль без `INSERT` в `audit_log` **мовчки** гасить аудит на шести таблицях:
`profiles`, `queue_entries`, `waitlist_entries`, `incidents`,
`referral_access`, `ceo_access`. Тепер `owner` і `lang` у дайджесті атрибутів.

### (3) `substr(md5(…), 1, 12)` — 48 біт

Другий прообраз добирається перебором за години, і простір перебору є:
коментарі входять у дайджест, тож nonce у коментарі всередині вихолощеного
тіла — робочий вектор. Тепер `md5` повний.

### (4) `handle_new_user` не покривався НІЧИМ — знахідка при валідації ревʼю

Ревʼю сказало «у public 54 тригерні функції», я міряв 53 — розбіжність
виявилась не помилкою, а **знахідкою**: 54-та (`handle_new_user`) висить не
на таблиці `public`, а на `auth.users` через `on_auth_user_created`. №17
фільтрує `nspname = 'public'` і не бачить ані функцію, ані тригер; замір у
тілі сторожа — **0 згадок** обох імен. Функція `SECURITY DEFINER` і вирішує,
який профіль (і яку роль) отримає новий користувач.

## 4. Чому ключ — підпис, а не імʼя

`auth_radiologist_room_ok(p_room uuid)` і `unique_login(p_base text)` мають
аргументи, тож голий `proname` перестав бути унікальним ключем, щойно до
списку додались хелпери. Ключ = `proname || '(' || identity_arguments || ')'`.
Фальсифікація підтвердила, що ключ **розрізняє типи**: очікування
`auth_radiologist_room_ok(p_room text)` дає `missing:`, а не тихий збіг.

## 6. Накат і перевірка Results

Накат — **DO-блоком через MCP**, а не файлом через SQL Editor. Блок
самоперевіряється: спершу звіряє, що в проді зараз тіло 0171
(`md5 = c8473081…`), потім збирає нове тіло і **відмовляється писати**, якщо
результат не збігається з md5 тіла файлу.

| замір після накату | значення |
|---|---|
| `invariants_check(false)` | `checked: 19`, `failed: [ledger_md5: 0172]` — норма ДО `db:gate` |
| `md5(prosrc)` | `8b3d332d25d9fa838113e2f29b84cdd3` = md5 тіла файлу |
| `md5(replace(prosrc, chr(13), ''))` | те саме |
| `cr_count` | **0** |
| леджер | 172 рядки, 0172 з `applied_at`, md5 проштамповано `db:gate` |

⚠️ **Побічний, але важливий замір:** 0171 через SQL Editor приніс 811 CR, а
цей шлях — жодного. Побайтна рівність «прод == артефакт міграції» досяжна,
але лише поза SQL Editor. `replace(chr(13), '')` у смоуку лишається
страховкою на наступний ручний накат.

## 8. Названі межі 0172 (кандидати на 0173, не пропуски)

1. **Аудит-тригери `trg_audit_*` не названі НІДЕ.** Замір: підрядка
   `trg_audit` у тілі сторожа — 0 разів. Отже `drop trigger
   trg_audit_profiles on public.profiles` сьогодні проходить **усі 19**
   перевірок зеленим: №19 бачить, що функція `fn_audit` існує з правильним
   тілом, але не те, що вона до чогось прицеплена.
2. **38 тригерних функцій розкладу і консистентності поза списком**
   (`check_no_overlap`, `check_room_schedule`, `guard_off_schedule`,
   `guard_status_transition`, сімка `tg_change_markers_*`). Вони бережуть
   правильність розкладу, а не доступ. Розширення подвоїть частоту передруків
   (8 із 30 проти 4 із 30) — це рішення власника.
3. **Решта 18 перевірок не має обробника винятків.** Замір: у всьому сторожі
   рівно ОДИН `exception when` (у №18). Виняток у будь-якій іншій перевірці
   відкочує транзакцію, і рядок у `maintenance_runs` не зʼявляється **зовсім**
   — тиша, яку видно як здоровʼя. №19 полагоджена; решта — окремий пакет, бо
   це зміна поведінки вже відвантажених перевірок.
4. **Еталон самопідтверджується.** Рецепт перезняття пінів благословляє те,
   що зараз у проді. У файлі це названо: перезнімати лише прочитавши дифф
   тіла очима.
