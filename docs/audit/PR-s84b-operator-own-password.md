# PR с84-B — «Змінити пароль» оператора: свій пароль на свій; собі «Скинути» заборонено

Дата: 09.10.2026. Без міграцій (база не змінювалась). Гілка від `dev 382a386`; дерево коду —
у коміті «с84 (після 0206): «Змінити пароль» оператора…».

## 1. Інцидент

Після bootstrap першого оператора власник натиснув «Скинути пароль» на **своєму** рядку
консолі `/platform`. Роут `/api/platform/operators/[id]/password` міняє пароль через
`auth.admin.updateUserById`, а GoTrue на admin-шляху завершує **всі** сесії людини
(`UpdatePassword(tx, nil)` → `Logout`). Логи Auth, 15:31:32 UTC:

| час (UTC) | запит | відповідь |
|---|---|---|
| 15:31:32 | `PUT /admin/users/<uuid>` | 200 |
| 15:31:32 | `GET /user` | 403 `session_not_found` |
| 15:33:07, 15:33:22 | `POST /token` | 400 `invalid_credentials` |
| 15:33:44 | `POST /token` | 200 |

Консоль після скидання перечитала перелік операторів, дістала 401, і картка помилки
(`if (err) return …`) замінила сторінку разом із блоком нового пароля — пароль показався
на мить і зник. Єдиний оператор лишився без входу (повернувся аварійним SQL-скиданням).
Власник попросив: «потрібна можливість міняти пароль на свій».

## 2. Що зроблено

**Новий роут `POST /api/platform/me/password`** — оператор змінює ВЛАСНИЙ пароль на свій:

* лише JSON (415 для решти — той самий захід від login-CSRF, що у вході);
* гейт `requirePlatformOperator` з лімітом **5 за 15 хв на оператора, fail-closed**
  (у `RateLimitOpt` гейта зʼявився `onFailure`; тут ліміт — захист від перебору пароля);
* тіло: `current_password`, `new_password` (8 символів … **72 байти UTF-8** — межа bcrypt,
  GoTrue довший відхиляє `validation_failed`; кирилицею це ≈36 літер), той самий пароль — 400;
* email і id — з ПЕРЕВІРЕНОЇ сесії (другий `getUser`; id мусить збігтися з гейтом, інакше 401;
  без email — 409);
* поточний пароль перевіряє одноразовий anon-клієнт без cookie (`lib/supabase/passwordCheck.ts`):
  вхід → `signOut({ scope: "local" })` → звірка id; «невірний» (400) і «не знаємо» (503) — різні
  відповіді; вхід у ЧУЖИЙ акаунт — теж «невірний» (без оракула);
* зміна — через ВЛАСНУ сесію: `auth.updateUser({ password, current_password })` → `PUT /user`,
  GoTrue лишає поточну сесію і завершує інші (`LogoutAllExceptMe`);
* помилки — за класами auth-js: `AuthSessionMissingError` → 401, `AuthWeakPasswordError`
  (`reasons`, `pwned`) → 400, `AuthRetryableFetchError` (мережа, 500–504, 520–530) → 503
  «результат невідомий — спробуйте увійти з НОВИМ паролем, а якщо ні — зі старим»; коди
  `same_password`, `current_password_invalid`/`_required`, `reauthentication_needed`,
  `validation_failed`, 429 `over_request_rate_limit`, `refresh_token_*`/`bad_jwt` — свої тексти;
  відповідь несе `field` (`current`/`new`), куди консоль повертає фокус;
* слід у журналі платформи — `operator.password_changed` (без деталей, без паролів).

**Скидання собі заборонене:** `/api/platform/operators/[id]/password` повертає 400 до читання
цілі, порівнюючи id без регістру (`zUuid` приймає верхній регістр).

**Консоль:** на своєму рядку — «Змінити пароль» (діалог: поточний, новий, ще раз; кнопки без
`disabled` у пастці фокуса — `aria-disabled`; помилка — у постійному `role="alert"`, повтор тієї
самої помилки оголошується знову; «Паролі не збігаються» — у постійній `aria-live`; приховане
поле `username` для менеджера паролів — ПІСЛЯ полів пароля, щоб `BaseDialog` фокусував
«Поточний пароль»). «Скинути» — лише чужим; підтвердження тепер каже, що відкриті сесії цього
оператора завершаться. Картка помилки переліку — лише коли немає ні переліку, ні виданого
пароля; інакше помилка показується в картці переліку, а блок пароля лишається. Будь-який 401 —
«Сесія завершилась — увійдіть знову».

## 3. Межі захисту (ревʼю, лінзи B і C)

Перевірка поточного пароля — **захист роуту, а не межа безпеки акаунта**: cookie сесії
Supabase читаються JS-ом, anon-ключ публічний, тож власник токена змінить пароль напряму в
GoTrue (`PUT /auth/v1/user`). Справжня межа — перемикачі GoTrue з **ToDo П-6** (рішення
власника): «Require current password when updating» (роут уже передає `current_password`; поки
перемикач вимкнений, GoTrue поле ігнорує) і «Secure email change». ⚠️ **За екраном 15.09 обидва
вимкнені** (П-6): пряма зміна пароля без поточного відкрита; поштовий шлях «зміна email →
/recover» (T9 моделі загроз) не заміряно — він залежить ще від «Confirm email» (вимкнено) і SMTP
(власного немає). Навіть увімкнені вони межу не замикають: recovery-сесії й акаунти без пароля GoTrue не перевіряє, а за
пласкої моделі довіри (Н-26) викрадена операторська сесія замикає власника через інший
операторський акаунт і «Скинути». При підозрі на крадіжку — «Вийти» (глобальний вихід) або
«Скинути» іншим оператором.

> **Виправлення 09.10 (с84-C).** Перша редакція цього розділу заводила окремий пункт **Н-28** і
> казала, що «Secure email change» «має лишатись увімкненим». Обидва твердження хибні: це ті самі
> перемикачі, що в П-6, і за заміром 15.09 вони вимкнені. Н-28 злито в П-6.

## 4. Ревʼю

Два незалежні раунди, лінза B (коректність, UX, тести; звірено зі справжніми auth-js 2.110.8,
@supabase/ssr 0.12.3 і upstream GoTrue) і лінза C (атакувальник). Раунд 1: Medium — межа 72
байти падала в 500 «спробуйте ще раз» (пастка з довгим кириличним паролем); перебільшене
твердження «викрадена сесія не змінить пароль»; Low — `session_not_found` приходить як
`AuthSessionMissingError` без коду (гілка не спрацьовувала, тест перевіряв неіснуючу форму),
`disabled` у пастці фокуса, ліміт fail-open, вразливі до вакуумності асерти. Раунд 2: код на
дроті — `current_password_invalid` (не …mismatch — так зветься лише Go-константа, звірено з
upstream `apierrors/errorcode.go`), 429 і невдалий refresh ішли в «оберіть інший пароль»,
межа захисту в AGENTS.md усе ще завищена. Усе виправлено; High не було.
