## Навіщо цей документ

Липневий і серпневий проходи читали політики **ПО ФОРМІ**: чи є RLS, чи є
політика на кожну команду, чи згадана `clinic_id`. Цього досить, щоб побачити
відсутню політику, і **не досить**, щоб побачити політику, яка є, виглядає
правильно і при цьому пускає не того. План завершення аудиту назвав це прямо:
«13 таблиць із 21 читались лише ПО ФОРМІ».

Тут — прохід **ПО СМИСЛУ**: питання не «чи є політика», а «кого саме вона
пускає, і чи той це, кого задумували».

⚠️ **Кожне твердження — ЗАМІР у проді.** Три гіпотези замір зняв; вони лишились
зі знаком «знято», бо метод, що їх зняв, дорожчий за самі гіпотези.

⚠️ **ГОЛОВНИЙ УРОК ПРОХОДУ — у рамці, а не в політиках.** Перша редакція цього
документа читала **лише SELECT-бік і лише прямі читання через PostgREST**, а
називалася «усі 63 політики по смислу». Обидві незалежні ревізії вдарили в одне
й те саме місце: рядок можна дістати не лише політикою. Найважча знахідка
(**С-11**) лежить не в жодній із 63 політик, а в SECURITY DEFINER функції, яка
їх обходить — і вона **жива, не латентна**.

## С-11 — DEFINER-функція обходить кабінетний гейт радіолога (ЖИВЕ)

### Що

```
waitlist_candidates_for_slot(p_room uuid, p_date date, p_time_min integer)
  SECURITY DEFINER, власник postgres, returns SETOF waitlist_entries
  execute: authenticated = true, anon = false
```

Власник — `postgres`, таблиця без `FORCE ROW LEVEL SECURITY`, отже **RLS до
тіла не застосовується взагалі**. `returns SETOF waitlist_entries` означає
**ПОВНИЙ рядок**: `patient_name`, `patient_phone`, `patient_dob`, `indication`,
`contraindications`.

Уся авторизація функції — два рядки:

```sql
if v_clinic is null then raise '28000'; end if;          -- не авторизований
if public.auth_is_referrer() then raise '42501'; end if;  -- не направник
```

**Радіолог проходить обидва.** Далі фільтр рядків:

```sql
where w.clinic_id = v_clinic and w.status = 'waiting'
  and (p_room is null or w.room_id is null or w.room_id = p_room)
```

Межа **центру** тримається. Межа **кабінету** — ні: `auth_radiologist_room_ok`
у функції немає взагалі. А саме вона й є тим, що обмежує радіолога при прямому
читанні:

```
waitlist_select: ... and (auth_role() is distinct from 'radiologist'
                          or auth_radiologist_room_ok(room_id))
```

### Замір у проді — В ОБИДВА БОКИ

У проді 1 радіолог, йому призначено **4 з 7** кабінетів центру.

| | рядків |
|---|---|
| `waiting` у його центрі | 1 |
| з них читає **через RLS** (`waitlist_select`) | **0** |
| з них віддає **RPC** при `p_room = null` | **1** |

Обидва боки розходяться на тому самому рядку. Це **не латентна діра**: рівно
один рядок вейтліста з ПІБ і телефоном пацієнта сьогодні доступний радіологу
через RPC і недоступний через RLS.

⚠️ **Чому «1 рядок» — не привід відкласти.** Той єдиний рядок має
`room_id IS NULL`, тобто RPC віддає його через гілку `w.room_id is null`, а RLS
ховає його через fail-closed NULL у `auth_radiologist_room_ok`. Дві половини
системи розходяться в трактуванні NULL у протилежні боки. Кількість «1» — це
стан тестових даних на сьогодні, а не властивість схеми: наповнений вейтліст
дає рівно стільки рядків, скільки в центрі чекає пацієнтів.

### У продукті цей шаблон уже зроблено ПРАВИЛЬНО

Це не «невідома практика», а розбіжність із власним стандартом репозиторію.
`room_busy_slots` — сусідня DEFINER-функція — рахує явну пару `acl.can_read` /
`acl.ok`, **занулює** `patient_name`/`status`/`studies` при `ok = false` і
повторно застосовує `auth_radiologist_room_ok`. Тобто канон у домі є;
`waitlist_candidates_for_slot` під нього просто не привели.

### Рекомендація

Мінімальна правка, що не чіпає жодної політики: додати в `where` функції

```sql
and public.auth_radiologist_room_ok(w.room_id)
```

Це відновлює рівно ту межу, яку `waitlist_select` уже тримає, і для персоналу
не-радіолога не міняє нічого (функція повертає `true` за першим диз'юнктом).

**Червоний тест перед накатом (обов'язковий, названий):** під сесією радіолога
виклик `waitlist_candidates_for_slot(null, <дата>, <хв>)` має віддати **0**
рядків, а прямий `select` із `waitlist_entries` — теж 0 (зелений базис: ті самі
0 і до правки — саме тому базис мусить бути на **не-радіологі**, де функція до
і після правки віддає ОДНАКОВУ кількість; інакше тест зелений через те, що
зламав усіх, а не через те, що полагодив одного).

⚠️ **Перевірити решту DEFINER-поверхні тим самим питанням.** С-11 знайдено не
обходом усіх 116 DEFINER-функцій, а точковою перевіркою однієї. Питання
«чи повторює ця функція гейти тих політик, які обходить» **не поставлене** до
решти 30 клієнтських DEFINER-функцій. Це відкритий хвіст, а не закритий блок.

## С-12 — читання по колонці, яку клієнт може писати

`queue_select` має три диз'юнкти. Перший — межа центру плюс кабінетний гейт.
Другий і третій — **чиста рівність uuid, без жодної перевірки належності**:

```sql
or (created_by = auth.uid())
or (referrer_id = auth.uid())
```

Ні `clinic_id`, ні `auth_radiologist_room_ok`, ні `referral_access`.

Тепер права на запис у ці ж колонки (заміряно, бо **табличного** UPDATE на
`queue_entries` у клієнта немає — контроль тут колонковий):

| колонка | UPDATE для `authenticated` |
|---|---|
| `referrer_id` | **true** |
| `patient_name` | true |
| `created_by` | false |
| `status` | false |
| `clinic_id` | false |

**29 із 40 колонок** мають колонковий UPDATE; `INSERT` — **40 із 40**.

Тобто колонкове звуження тут — справжній, працюючий контроль (id, clinic_id,
status, position клієнт не пише). Але `referrer_id` з нього **випав**.

### Ланцюг

1. Реєстратор/адмін центру А проходить `queue_write_staff` — у ній ні USING, ні
   WITH CHECK не згадують `referrer_id`.
2. Колонкове право на `referrer_id` у нього є.
3. Тригер `guard_referrer_doctor` спрацьовує **лише** якщо рядок створив
   направник: `exists (select 1 from profiles where id = OLD.created_by and
   role = 'referrer')`. Для рядка, створеного персоналом (у проді таких **45**),
   тригер мовчить.
4. FK — `referrer_id references profiles(id)`, **без предиката центру**: будь-який
   профіль бази.
5. Далі третій диз'юнкт `queue_select` віддає цьому користувачу ПОВНИЙ рядок —
   назавжди, без перевірки центру й кабінету.

### Замір: сьогодні чисто

| хто в `referrer_id` | рядків |
|---|---|
| роль `referrer`, є `referral_access` цього центру, `active` | 53 |
| роль `referrer`, є `referral_access` цього центру, `pending_referrer` | 2 |
| **будь-що інше** | **0** |

**Вага середня, не висока:** зловмисник тут — свій же реєстратор, який ці рядки
й так читає, а `fn_audit` запише зміну `referrer_id` у журнал. Небезпечна не
атака, а **архітектура**: право читати рядок визначається колонкою, яку пише
клієнт, і не звіряється ні з чим. `waitlist_entries` цю ж поверхню **закрила** —
там `referrer_id` і `created_by` колонкового UPDATE не мають (18 із 28). Тобто
черга — виняток із власного канону сусідньої таблиці.

**Рекомендація:** зняти колонковий UPDATE на `queue_entries.referrer_id` (як у
вейтлісті) і вести зміну направника через RPC. Червоний тест: прямий
PostgREST-PATCH `referrer_id` від адміна → **42501**, а не «1 row updated».

## С-13 — `profiles`: таблиця особистостей тримається на одному тригері

Заміряно:

| | `anon` | `authenticated` |
|---|---|---|
| табличний SELECT | false | false |
| **колонковий SELECT** | **14 із 16** | **14 із 16** |
| табличний INSERT | **true** | **true** |
| табличний UPDATE | **true** | **true** |
| **колонковий UPDATE** | **16 із 16** | **16 із 16** |
| табличний DELETE | **true** | **true** |

Політика `profiles_update_self`: USING = `id = auth.uid()`, WITH CHECK =
`id = auth.uid()`. **Жодної згадки колонок.** Отже на рівні RLS + грантів
запит `update profiles set role = 'admin' where id = auth.uid()` **дозволений**.

Не проходить він через **третій шар, який у першій редакції цього документа не
згаданий жодного разу** — тригер `trg_guard_profile_privileges`
(`guard_profile_privileges`, BEFORE UPDATE, `tgenabled='O'`). Тіло прочитане:
кидає `insufficient_privilege` на зміну `clinic_id`; на зміну `role` — якщо це
не адмін свого центру, що міняє **чужу** роль; і на `login`, `email`,
`invite_token`, `password_set`, `approved`. Тримає.

**Це рівно той шаблон, який цей же документ засуджує в С-6** — «захист тримає
один шар» — і засуджує на таблицях, менш важливих за цю.

Три супутні факти, кожен заміряний:

1. **INSERT і DELETE на `profiles`** видані обом клієнтським ролям, а політик
   INSERT і DELETE на таблиці **немає жодної**. Тобто С-6 у чистому вигляді, і
   `profiles` у таблиці С-6 першої редакції **не було**.
2. **0178 відкликала лише ЧИТАННЯ.** `invite_token` і `invite_issued_at` не
   читаються (14 із 16), але **пишуться** (16 із 16) обома ролями. Тримає їх
   той самий тригер, а не грант. Розділ ~~С-8~~ робив висновок «0178 працює як
   задумано» з боку читання і не відкривав бік запису.
3. **`anon` має колонковий SELECT на тих самих 14 колонках** — `full_name`,
   `email`, `phone`, `login`. Його не пускають **лише предикати політик**
   (`auth_clinic_id()`/`auth.uid()` = NULL). Один шар, на таблиці особистостей.

**Рекомендація:** зняти з `anon` усе (він не має тут жодного робочого шляху);
зняти колонковий UPDATE на `role`, `clinic_id`, `invite_token`,
`invite_issued_at`, `password_set`, `approved`, `login`, `email` — усе, що
тригер і так забороняє. Тригер лишається як другий шар, а не як єдиний.
Поведінка застосунку не зміниться: ці поля пише `service_role` під
admin-клієнтом, для якого `auth.uid() is null` і тригер і зараз пропускає.

### Чому це варте уваги, хоч живої діри немає

`referral_access` і `ceo_access` — **самі таблиці контролю доступу**: перша
вирішує, хто з направників бачить центр, друга — хто бачить клініку як CEO.
Обидві віддані клієнтським ролям на запис і тримаються рівно на тому, що ніхто
ніколи не додав туди permissive-політику. Наступна політика на `referral_access`,
написана для читання, але без `for select`, відкриє `anon` запис у таблицю
власних прав. `rate_limits` — лічильник, що зупиняє перебір; право його
редагувати видано тим самим ролям, які він обмежує. `profiles` — таблиця
особистостей.

### Протилежний, сильний шаблон — він у домі вже є

Дев'ять таблиць не мають у клієнтських ролей **жодного** права доступу до даних:
`integration_keys`, `google_calendar_connections`, `google_oauth_states`,
`inbound_events`, `external_refs`, `migration_ledger`, `maintenance_runs`,
`integration_webhooks`, `change_marker_settings`. `event_outbox` — майже: у нього
`anon` і `authenticated` мають `x` і `t` (REFERENCES і TRIGGER), даних це не
відкриває, але «жодного права» — неправда, і в першій редакції тут стояло саме
«жодного». Ще п'ять — `audit_log`, `important_events`, `queue_delay_events`,
`schedule_exceptions`, `user_change_markers` — лише SELECT.

⚠️ **Сторож №22 (`grant_digest`) це НЕ ловить — і не має.** Він пінить **набір**
грантів і червоніє на будь-яку зміну, тобто стереже статус-кво, а не судить
його: сьогоднішній надлишок уже всередині еталона.

**Рекомендація:** одна міграція `revoke` на 14 таблицях + передрук №22. Жоден із
цих шляхів сьогодні не працює (їх глушить RLS), тож поведінка не зміниться.
Червоний тест: запис `anon` у `referral_access` має падати з **42501**, а не з
«0 rows» — заміна коду помилки і є доказом нового шару.

## П-1 — неписане правило «історія назавжди»

Чотири хелпери реферерської видимості гейтять активність:
`auth_can_refer`, `auth_referrer_clinics`, `auth_referrer_visible_rooms`,
`auth_referrer_can_book_room` — усі мають `status = 'active'`.

І **вісім політик** звіряють `auth.uid()` напряму, без гейта:

| таблиця | політика | cmd | предикат |
|---|---|---|---|
| `queue_entries` | `queue_select` | SELECT | `created_by = uid` **OR** `referrer_id = uid` |
| `waitlist_entries` | `waitlist_select` | SELECT | `created_by = uid` **OR** `referrer_id = uid` |
| `patient_cases` | `cases_select_referrer` | SELECT | `referrer_id = uid` |
| `referral_access` | `ra_referrer_select` | SELECT | `referrer_id = uid` |
| `clinics` | `clinics_referrer_read` | SELECT | підзапит без `status` |
| **`referrer_private`** | **`rp_owner_select`** | SELECT | `referrer_id = uid` |
| **`referrer_private`** | **`rp_owner_insert`** | **INSERT** | `referrer_id = uid` |
| **`referrer_private`** | **`rp_owner_update`** | **UPDATE** | `referrer_id = uid` |

Перша редакція називала п'ять і стверджувала, що **всі** політики ЗАПИСУ гейт
мають. Обидва твердження хибні: `referrer_private` — таблиця з трьома власними
політиками, з яких **дві на запис і жодна не гейтована**. Тобто неактивний
направник не лише читає, а й **пише** свій рядок `referrer_private`
(`referrer_id`, `email`, `updated_at`). Для цієї таблиці це виглядає доречно —
людина редагує свій контакт, — але правило треба записати саме так, інакше
запис рішення буде неповний з першого дня.

Окремо, тим самим шаблоном для іншої особи: `ceo_access_self_select`
(`ceo_id = auth.uid()`, без гейта) — відкликаний CEO далі читає **свої** рядки
`ceo_access`. Перша редакція стверджувала «відкликаний не бачить нічого»; це
правда для даних центру і неправда для його власного запису доступу.

### ⚠️ РОЗТИН: чому це НЕ дефект (і чому спершу написано «дефект»)

Першим висновком було: «`clinics_referrer_read` — єдиний предикат без гейта,
отже розбіжність, отже дефект». Висновок **хибний**, і зняли його два заміри
в коді, а не міркування.

**Замір 1 — шапка `0038_referral_center_card.sql`:** «у порталі направника
картку центру (**запрошення**/активний) можна розгорнути й показати… Чому RPC,
а не пряме читання: чинні RLS НЕ дають направнику прочитати профіль адміна
чужого центру і кабінети центру, **поки доступ ще не active**». Тобто продукт
**свідомо показує картку тому, хто ще НЕ активний**.

**Замір 2 — `app/referral/page.tsx:80–92`:** портал будує `clinicIds` із **УСІХ**
рядків `referral_access` користувача, без фільтра за статусом, і читає `clinics`
по цьому списку. Вкладка «Мої центри» має розділи «запити», «активні» та
**«історія»** (`revoked`/`declined`) — усі показують назву центру.

**Наслідок:** «виправлення» політики додаванням `status='active'` показало б
`"Центр"` замість назви для кожного запрошення й відкликаного доступу —
`Center.name ?? "Центр"`. Тихий регрес UI, якого не ловить жоден тест.

**Рекомендація:** не міняти політики. **Записати правило** — формою, яку
власник уже обрав для RF-03 («Задумано — закрити записом рішення»): усі вісім
політик поіменно, причина (історія в порталі), і окремо — що для
`referrer_private` правило поширюється й на запис.

## С-5 — апертура `clinics` ширша за задум

| хто дає | кому | колонки |
|---|---|---|
| RPC `referral_center_card` (0038, DEFINER) | направнику будь-якого статусу | `id`, `name`, `city` |
| `app/referral/page.tsx` | йому ж | + `timezone` |
| **політика `clinics_referrer_read`** | **йому ж** | **усі 13** |

Заміряно колонковий ACL: усі 13 колонок `clinics` читабельні для
`authenticated` (і для `anon` — його тримає лише RLS). Отже звуження в
застосунку — домовленість клієнта, а не контроль. Рукописний запит PostgREST
від будь-якого направника, зокрема **відкликаного**, віддає `address`, `phones`,
`emails`, `configured_at`, `queue_delay_policy`, `overlap_threshold_min`,
`max_cascade_patients`, `allow_after_hours_shift`.

Пацієнтських даних немає. Але чотири останні — **внутрішні операційні пороги
чужого бізнесу**; ні портал, ні RPC їх не просять.

**Чому RLS це не лікує:** політика не обмежує колонки. Звузити можна колонковим
`revoke` (як 0178) або поданням/RPC. Колонковий шлях тут не підходить: грант
роль-широкий, а `app/queue/actions.ts` і `SetupWizard` читають ці ж колонки під
тією самою роллю для персоналу. Отже — лишити порталу вже наявну RPC і прибрати
пряме читання таблиці.

⚠️ Симетрична примітка, якої не було: `clinics_update` дозволяє адміну центру
**писати** ці ж пороги. Це задумано, але означає, що С-5 — не лише про читання.

## С-7 — три мертві політики

Політика мертва, якщо жоден запит не може її активувати. Перевірка двобічна:
**табличний** ACL і **колонковий** — бо одного замало (див. пастки).

| політика | чому мертва |
|---|---|
| `sched_desk_write` (ALL) | `authenticated` на `schedule_overrides` не має ні INSERT, ні UPDATE, ні DELETE — ні таблично, ні колонково. SELECT-гілка `A and B` строго накрита `sched_staff_read` (`A`) через permissive-OR |
| `cases_update_staff` | `patient_cases`: UPDATE `false` таблично **і 0 колонок** |
| `cases_update_referrer` | те саме |

Запис в обидві таблиці йде через DEFINER-функції, власник `postgres`, таблиці
без `FORCE ROW LEVEL SECURITY` (заміряно: `relforcerowsecurity = false` на всіх
33 таблицях), тож RLS до них не застосовується.

Шкоди сьогодні немає. Шкода завтра: політика читається як «цей шлях працює», і
наступний, хто додасть грант «щоб запрацювало», відкриє прямий запис в обхід
RPC з усіма її перевірками.

## С-9 — CEO і PII пацієнта (питання власнику, не дефект)

Гіпотеза: `audit_log` — обхід, бо CEO читає його цілком, а `before`/`after` — це
`to_jsonb(рядок черги)`.

**Замір ключів `audit_log`** (лише імена ключів; значення не друкувались):
`patient_name` — 2672 непорожніх, `patient_phone` — 2656, далі `patient_dob`,
`patient_age`, `patient_sex`, `patient_weight`, `indication`,
`contraindications`, `radiologist_note`, `call_note`, `doctor`. Усього 2817
рядків журналу.

**Обходу немає:** CEO має **прямі** політики на тих самих даних — `queue_ceo_read`
і `waitlist_ceo_read`, обидві чиста межа клініки (`clinic_id in
auth_ceo_clinics()`, гейт `active` усередині хелпера), без обмеження колонок —
заміряно: `authenticated` читає **40 із 40** колонок `queue_entries` і **28 із
28** `waitlist_entries`, колонкових `revoke` немає.

Отже це не розбіжність політик, а **продуктове рішення** під критерій **Р2**.

**Питання власнику:** чи має CEO бачити персональні дані пацієнтів, чи лише
операційні показники центру? Якщо друге — це не правка політики, а окрема
поверхня (подання без PII-колонок + зняття прямих грантів), і `audit_log` треба
звужувати разом із нею, інакше він лишиться обходом уже справжнім.

⚠️ Механізм для такого звуження в продукті **вже є і працює**: `queue_entries` і
`waitlist_entries` мають колонково обмежений UPDATE (29 із 40 і 18 із 28). Той
самий прийом застосовний до SELECT для ролі CEO, якщо для неї завести окрему
роль БД.

## С-14 — realtime: поза рамкою цього проходу (ВІДКРИТЕ)

Публікація `supabase_realtime` містить **11 таблиць** схеми public:
`doctors`, `incidents`, **`patient_cases`**, **`queue_entries`**,
`referral_access`, `rooms`, `schedule_overrides`, `service_room_overrides`,
`services`, `user_change_markers`, **`waitlist_entries`**.

Жирним — три таблиці з PII, про які весь розділ С-9.

**10 із 11 мають `relreplident = 'f'` (REPLICA IDENTITY FULL)** — виняток лише
`user_change_markers`. FULL означає, що кожен UPDATE і DELETE пише у WAL
**повний старий рядок**, з пацієнтськими колонками включно.

Чому це названо тут, хоч і не заміряно: весь цей документ міркує про читання
рядків через PostgREST і **жодного разу** — про потік реплікації, який возить
ті самі рядки підписникам за **іншими** правилами фільтрації. Зокрема,
DELETE-події у Postgres Changes документовано **не фільтруються RLS**. Клієнтський
DELETE на черзі й вейтлісті знято грантом (С-2), але видалення відбуваються —
`clinic_deletion_execute`, ретенція журналу, FK-каскади — і WAL-події при цьому
виникають.

**Це не твердження про витік.** Це твердження, що питання не поставлене, а
поверхня — рівно та сама, що в С-9. Живу перевірку (підписка з-під сесії
персоналу іншого центру / радіолога) треба зробити **разом із блоком 2.2**, де
жива сесія й так потрібна.

## С-15 — подання `v_clinic_people`

Єдине подання в схемі public. `reloptions = {security_invoker=true}` — отже RLS
базових таблиць застосовується **від імені викликача**, обходу немає. Добре.

Але `anon` і `authenticated` мають на нього SELECT, **INSERT, UPDATE, DELETE**,

`postgres` і всі політики `profiles` перетворяться на декорацію — мовчки. Цю
опцію не пасе жоден із 23 інваріантів (№23 стереже колонки і constraint-и, не
`reloptions`). Кандидат у пін.

## Методичні пастки цього проходу

**1. `has_table_privilege(..., 'SELECT') = false` на читабельній таблиці нічого
не означає.** Справжній контроль — колонковий. Пастка спрацювала двічі і дала
**протилежні** відповіді: на `profiles` табличне «false» брехало, на
`schedule_overrides` — казало правду. Розрізнити можна **тільки** другим запитом
по `pg_attribute`.

**2. «Єдиний виняток зі схеми» — гіпотеза, не висновок.** Вісім політик без
гейта виглядали недоглядом, а виявились неписаним правилом продукту. Ціна
перевірки — два читання файлів; ціна «виправлення» без перевірки — тихий регрес
UI без жодного червоного тесту.

**3. Порожня колонка ≠ захищена колонка.** Доказ — код, що її вирізає, а не
лічильник, який сьогодні нуль.

**4. Заміряти треба в обидва боки.** «Скільки бачить неактивний» без «скільки
бачить активний» не відрізняє знахідку від зламаного запиту.

**5. НОВА, найдорожча: перелік, складений вручну, — це перелік підозр, а не
вимір.** Перша редакція перелічила таблиці С-6 «по пам'яті проходу» і пропустила
**п'ять із чотирнадцяти**, зокрема `profiles`. Механічний запит (право є ∧
застосовної політики немає) знайшов усі. Правило: **якщо твердження має форму
списку — список мусить народжуватись запитом.**

**6. НОВА: RLS — не єдиний шлях до рядка.** Прохід, що читає лише
`pg_policies`, за побудовою не побачить DEFINER-функцію, подання чи потік
реплікації. Найважча знахідка (С-11) — саме звідти. Питання «хто ще віддає цей
рядок» треба ставити окремо від «яка політика його віддає».

**7. НОВА: «прочитано N політик» — перевіряйте знаменник.** Перша редакція
чесно виміряла 63/21 і назвалась повним семантичним проходом, а по смислу
прочитала ~34: **18 із 23 політик ЗАПИСУ не були відкриті взагалі.** Лічильник
збігався, робота — ні.
