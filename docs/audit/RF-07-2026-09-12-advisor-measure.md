# RF-07 — вимір, а не правка (2026-09-12)

**Статус RF-07: залишається відкладеним.** Цей документ — тільки вимір і
рекомендація. RLS не чіпали, жодної міграції не подавали.

Рішення власника про відкладення RF-07 зафіксоване в
`docs/audit/DECISIONS-2026-09-09.md`; борг «не перевірена еквівалентність
наборів рядків під кожною роллю» — у `claude/tech-debt-2026-09-09.md`.

---

## 1. Звідки береться число 68

Advisor рахує одну знахідку на трійку **(таблиця × роль × дія)**, де під одну
трійку підпадає більш ніж одна PERMISSIVE-політика. Дві розгортки:

* роль `public` у `pg_policies.roles` розгортається у **п'ять** ролей:
  `anon`, `authenticated`, `authenticator`, `dashboard_user`,
  `supabase_privileged_role`;
* `cmd = ALL` розгортається у **чотири** дії: SELECT / INSERT / UPDATE / DELETE.

З цією моделлю власний перерахунок дав рівно **68** — збіг з advisor-ом точний.
Попередня оцінка «35» була помилкою: розгорталися лише `anon` + `authenticated`.

## 2. Скільки з 68 взагалі можуть виконатися

Політика виконується тільки тоді, коли роль має відповідний **GRANT** на
таблицю. Звірка з `information_schema.role_table_grants`:

| | знахідок |
|---|---|
| усього | **68** |
| роль **не має** гранта на цю дію → політика не виконується ніколи | **41** |
| роль має грант | **27** |
| &nbsp;&nbsp;з них `authenticated` | 18 |
| &nbsp;&nbsp;з них `anon` | 9 |

41 знахідка з 68 — чистий шум моделі advisor-а. Найбільша група
(`profiles` / SELECT / 4 політики) потрапляє саме сюди: **ні `anon`, ні
`authenticated` не мають SELECT на `profiles`** — читання йде через
SECURITY DEFINER, RLS обходиться.

## 3. Скільки з 27 щось коштують

`pg_stat_statements`, розподіл часу виконання за ролями за весь час життя:

| роль | час | частка |
|---|---|---|
| supabase_admin | 31 384 887 мс | 62.6 % |
| **authenticated** | **12 768 377 мс** | **25.5 %** |
| postgres | 4 453 143 мс | 8.9 % |
| authenticator | 1 059 517 мс | 2.1 % |
| service_role | 300 033 мс | 0.6 % |
| **anon** | **13 408 мс** | **0.0 %** |

`anon` за весь час — 13.4 секунди на 13 878 викликів. **9 знахідок під `anon`
не коштують нічого.**

Лишається **18 знахідок під `authenticated`** — це і є вся реальна поверхня
RF-07.

Далі: усередині `authenticated` табличні SELECT-и через PostgREST (єдине, чим
керує RLS) дають приблизно 1.05 млн мс — це ~8 % часу `authenticated` і ~2 %
часу інстансу. Накладні витрати саме від «кількох PERMISSIVE замість однієї» —
частка від цих 2 %.

## 4. Чому злиття тут не є локальною правкою

Прочитані `qual` двох найгарячіших живих груп (`queue_entries` / SELECT,
`services` / SELECT). Два структурні бар'єри:

**(а) Групи змішують `ALL` і `SELECT`.** У `queue_entries` / SELECT чотири
політики: `queue_ceo_read` (SELECT), `queue_select` (SELECT),
`queue_write_referrer` (**ALL**), `queue_write_staff` (**ALL**). Злити їх в
одну SELECT-політику не можна, не розібравши спершу обидві `ALL`-політики на
пер-дієві — а це змінює поверхню запису, не читання.

**(б) Групи змішують набори ролей.** `queue_ceo_read` і
`queue_write_referrer` оголошені на `{public}`, `queue_select` і
`queue_write_staff` — на `{authenticated}`. Об'єднання змінює і рольову
поверхню.

Тобто «злиття» в advisor-івському сенсі тут неможливе без зміни поверхні
доступу — рівно те, що умова задачі забороняє.

## 5. Що натомість є безпечним і дешевим (окреме від RF-07)

Advisor має **другу** рекомендацію — `auth_rls_initplan`: загорнути виклик
STABLE-функції без аргументів у `(select f())`, щоб він став InitPlan і
виконався один раз на запит, а не на рядок. Це **строго еквівалентно** за
набором рядків і не чіпає ні ролі, ні дії.

Кандидатів — **15 політик** (тільки виклики **без аргументів**; виклики на
кшталт `auth_radiologist_room_ok(room_id)` або `auth_is_ceo_of(clinic_id)`
залежать від рядка і загортанню не підлягають):

`audit_read_admin`, `ceo_access_clinic_select`, `clinics_select`,
`imp_events_read_admin`, `profiles_admin_update`, `profiles_ceo_linked_read`,
`profiles_referrer_linked_read`, `profiles_select`, `queue_select`,
`queue_write_staff`, `radrooms_admin_write`, `radrooms_select`,
`ra_clinic_select`, `sro_admin_write`, `sro_staff_read`.

Усі задіяні функції (`auth_clinic_id`, `auth_is_admin`, `auth_is_referrer`,
`auth_role`) — `STABLE`, `SECURITY DEFINER`, `cost 100`.

**Застереження, яке знімає половину очікуваного виграшу.** Заміряно:

```
explain analyze select count(*) from queue_entries where clinic_id = auth_clinic_id();
→ Index Only Scan, Index Cond: (clinic_id = auth_clinic_id()), 0.295 ms
```

Планувальник і без обгортки згорнув STABLE-виклик в умову індексу. Виграш
з'являється тільки там, де виклик стоїть у позиції, з якої планувальник його
підняти не може (гілка `OR`, сусідство з рядково-залежним предикатом).
**Отже виграш не автоматичний — його треба міряти політика за політикою, а не
приймати на віру з формулювання advisor-а.**

## 6. Рекомендація

1. **RF-07 (злиття PERMISSIVE) — лишити відкладеним.** Реальна поверхня — 18
   знахідок, вартість — частка від ~2 % часу інстансу, а виконання вимагає
   розбирання `ALL`-політик і зміни рольової поверхні. Співвідношення ризику
   до виграшу негативне.
2. Число «68» у звітах більше не вживати без розшифровки: 41 із них — трійки
   без гранта, ще 9 — під роллю, яка за весь час життя проєкту витратила
   13 секунд.
3. `auth_rls_initplan` (15 політик) — окремий кандидат, але **лише після**
   пер-політичного заміру; без червоного заміру правити RLS немає підстав.

## 7. Що знайшлося попутно і важить більше

Найдорожчий запит `authenticated` — `room_busy_slots`: 10.05 млн мс, ~20 %
часу всього інстансу. До RLS це відношення не має (SECURITY DEFINER). Деталі —
у `docs/audit/PERF-2026-09-12-pg-timezone-names.md`.
