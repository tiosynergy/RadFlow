# Живий прогін сценарію `waitlist` — гонка за кандидата листа очікування

**10.09.2026, с62, пакет 48.** Прогін на ПРОДІ під живим токеном персоналу
(адміністратор Medicom). Токен у переписку, лог і вивід не потрапляв — лише
метадані (`alg=ES256 kid=є · role=authenticated · лишилось ~54 хв`); файл із
токеном видалено одразу після прогону.

Це закриває пункт «`waitlist` — код, який ніхто не запускав».

## Що саме перевірялось

Гарант — **умовний UPDATE усередині `schedule_from_waitlist_rpc`**:

```sql
update public.waitlist_entries
   set status = 'scheduled', claim_token = null
 where id = p_waitlist_id and status = 'waiting' and clinic_id = v_clinic;
get diagnostics v_rows = row_count;
if v_rows = 0 then … raise exception 'WAITLIST_STALE …' using errcode = '55000';
```

⚠️ На відміну від 23P01 (тригер 0064) і 23505 (індекс 0018), це виключення
породжує не двигун, а РЯДОК у тілі функції. Отже гарант можна зняти, не
отримавши жодної помилки БД — лише двох переможців.

## Результат: PASS, exit 0

Кабінет «Ревуцького, 44a» (MRI, Medicom), слоти-кандидати на +7…+14 днів.

```
Придатних слотів: 4
Слот гонки: 2026-09-17 10:00

КОНТРОЛЬ (4 різних слотів, службова роль)          → PASS, вікна перетинаються
КОНТРОЛЬ ЛИСТА (4 × RPC, РІЗНІ кандидати і слоти)  → PASS, вікна перетинаються

ГОНКА ЗА КАНДИДАТА (4 × RPC на ОДНОМУ кандидаті):
  +0 мс  246 мс  ВІДМОВА 55000  WAITLIST_STALE
  +0 мс  231 мс  УДАЧА
  +0 мс  246 мс  ВІДМОВА 55000  WAITLIST_STALE
  +0 мс  245 мс  ВІДМОВА 55000  WAITLIST_STALE
  → PASS: 1 удача з 4, решта — 55000 від CAS-застовплення
  кандидат: status=scheduled · scheduled_entry_id=є · збігається з переможцем: так
```

Три твердження, доведені ОКРЕМО:

1. **Взаємне виключення застовплення.** Рівно один переможець; усі троє інших
   впали САМЕ `55000`, а не чужим SQLSTATE.
2. **Паралельність КОРИСТУВАЦЬКОГО клієнта.** Контроль листа — та сама
   операція тим самим клієнтом у різні слоти — пройшов увесь, і вікна запитів
   перетинаються. Без нього «1 удача + 3 × 55000» не можна було б приписати
   конкуренції: послідовні виклики дали б той самий результат і без будь-якого
   блокування рядка.
3. **Атомарність кроків 1–3.** Кандидат `scheduled`, `scheduled_entry_id`
   проставлений і вказує саме на запис ПЕРЕМОЖЦЯ.

## 🔴 Перший прогін був ЧЕРВОНИЙ, і це знайшло дефект у самому харнесі

```
ГОНКА: +0 мс 227 мс ВІДМОВА 23P01 OVERLAP: кабінет … вже зайнятий
       +0 мс 463 мс ВІДМОВА 23P01 OVERLAP: кабінет … вже зайнятий
  → FAIL: кандидата не записав НІХТО — фікстура або слот непридатні
```

**Причина — мій же код.** `runWaitlistControl` створює РЕАЛЬНІ записи черги в
тих самих слотах, які потім бере гонка, а прибирав їх лише блок `finally` —
тобто в момент гонки вони ще висіли, і тригер 0064 чесно відмовив обом
пострілам. Сценарій падав на власних фікстурах.

Дві речі, які тут варто зафіксувати:

* **Вердикт не збрехав.** Він сказав «не записав НІХТО — фікстура або слот
  непридатні» і назвав SQLSTATE обох невдах. Саме для цього драбинка й
  розрізняє «впали через гонку» і «впали НЕ через гонку»: якби вона приймала
  будь-яку відмову за програш у гонці, прогін надрукував би PASS на зламаній
  постановці.
* **Це знайшов ПЕРШИЙ ЖЕ живий прогін**, а не тести й не два раунди ревʼю.
  Обидві лінзи ревʼю дивились на залишки в проді й на «чи доводить сценарій
  хоч що-небудь»; черга виконання контролю й гонки не належала ні до однієї з
  них. Ще один випадок правила «зелені тести — не заміна живій перевірці».

Полагоджено: контроль листа прибирає за собою ОДРАЗУ (порядок той самий, що в
`runControl` і `runRace`: створив → вистрілив → прибрав), з дочитуванням
`scheduled_entry_id` перед видаленням.

## Пастка, яку зловив смоук-прогін БЕЗ токена

`node scripts/race-check.mjs waitlist` без `--room` обрав кабінет центру
**titenkosmokeCLINIC**, тоді як сесія персоналу — у **Medicom**. Фікстура лягла
б у центр КАБІНЕТА, а RPC звіряє центр ТОКЕНА → `42501` усім пострілам.
Вердикт сказав би «впали НЕ через гонку», тобто дефекту не сховав би, але
діагноз послав би шукати поламаний гард, якого ніхто не ламав.

Закрито гардом `assertTokenClinicMatches` — питає ТУ САМУ `auth_clinic_id()`,
якою користується сама RPC, і стоїть ПЕРЕД першим записом.
