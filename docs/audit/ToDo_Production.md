### Подробности П-6 (чтобы замер не начинали с нуля)

1. **Где смотреть:** Supabase Dashboard → `/auth/providers?provider=Email` и
   раздел Auth → Policies. Четыре настройки: `Secure email change`,
   `Secure password change`, `Require current password when updating`,
   `Minimum password length`.
2. ⚠️ **Замер, а не рассуждение — как с П-5.** Там тумблер оказался уже
   включённым, и неопределённость сняли пять минут в дашборде. Здесь наоборот:
   состояние прочитано, но **цепочка не проверена живьём**. Сначала воспроизвести
   на тестовом аккаунте (не на аккаунте владельца и не на реальном центре),
   потом решать.
3. **Что именно воспроизводить:** из активной сессии сменить пароль, не зная
   старого; затем сменить почту и убедиться, на какие адреса ушло
   подтверждение. Если подтверждение приходит только на новый адрес — прежний
   владелец аккаунта не узнаёт о захвате вообще.
4. **Решение после замера — за владельцем.** Включение `Secure email change` и
   `Require current password when updating` меняет поведение живых сценариев
   (приглашения персонала, восстановление пароля направителя), поэтому это не
   «просто щёлкнуть тумблер»: нужен прогон приглашения и входа после смены.
5. **Побочно:** минимальная длина 6 — отдельный вопрос; `Prevent use of leaked
   passwords` уже включён (П-5, 15.09), и он частично компенсирует короткие
   пароли, но не компенсирует смену без знания старого.
6. ⚠️ **Модель угроз это не покрывала.** ✅ Путь дописан 24.09 (с77) как **T9** в
   `THREAT_MODEL_2026-09-14.md` §10 — с пометкой «не замерено»; после замера
   строку перевести в замеренную.
7. 🆕 **Что дало чтение кода (с77) — это гипотезы для замера, а не выводы:**
   приложение **ни разу** не вызывает `auth.updateUser` — все смены пароля идут
   admin API на сервере (`/api/account/set-password` по одноразовому токену,
   `/api/staff/password` админом). Значит, тумблеры закрывают путь, которым не
   пользуется ни один живой сценарий, и включение их, скорее всего, ничего не
   сломает (проверить прогоном приглашения и входа — шаг 7 протокола). Путь
   атакующего — прямой `PUT /auth/v1/user` с токеном живой сессии; он же
   **обходит минимальную длину 8** из `zPassword` (у GoTrue — 6). Вход по логину
   резолвит адрес из `auth.users` (`resolve_login_email`), а экран персонала
   показывает копию `profiles.email` — **после смены почты интерфейс продолжает
   показывать старую**. И админский сброс пароля (`/api/staff/password`) почту
   не трогает: если почту уже сменили, атакующий возвращает контроль через
   `/auth/v1/recover`. Всё это — шаги 3–6 протокола.
