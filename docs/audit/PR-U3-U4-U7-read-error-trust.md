# Пакет U-3 + U-4 + U-7 — проковтнута помилка читання

Сесія 46. Один клас дефекту, три місця. Той самий корінь, що в U-5/U-6:
**екран стверджує на даних, яких немає.** Різниця лише в тому, звідки береться
«немає»: там дані не встигли прийти, тут — читання впало, а помилку не подивились.

PostgREST не кидає виняток. Він повертає `{ data, error }`. Не подивитись на
`error` означає перетворити збій читання на порожні дані — а порожні дані кожен
із цих екранів показував як ФАКТ.

## Що було зламано

### U-3 · `RescheduleModal` — «особливого дня немає»

`ovRes.error` не перевірявся, хоча сусіднє читання (`rooms`) свою помилку вже
перевіряло і навіть мало коментар про хардкод 08–18. При збої `override` ставав
`null`, і `roomScheduleFor` повертався до звичайного графіка: **закритий святковий
день малювався робочим, скорочений — повним.**

### U-4 · `StudyEditModal` — межі тривалості з чужого графіка

Не перевірялась ЖОДНА з двох помилок. `override = null` і `roomSchedule = null`
разом дають хардкод «Пн–Сб 08:00–18:00», тож при збої:

* `capBySched` рахувався до 18:00 — **дослідження можна було розтягнути за реальне
  закриття кабінету без жодної згоди** (`offOk` не спрацьовував, бо `inSchedCap`
  теж рахувався по вигаданій межі);
* `roomBreaks` виходив порожнім — тобто «перерв немає» замість «ми їх не знаємо»,
  і дослідження перетинало перерву;
* сітка дня малювалась по чужому графіку.

Коментар у `catch` — «транзієнт — межі лишаться дефолтними; сітку прикриє busyErr»
— був **фактично хибним**: `busyErr` це інше джерело (RPC `room_busy_slots`), і при
збої читання графіка воно лишається здоровим.

### U-7 · `CeoDashboard` — «0 % завантаж.» червоним

```ts
const { data: rdata } = await supabase.from("rooms")…   // error навіть не зв'язувався
setRooms(rdata || []);
```

Помилка не діставалась із відповіді взагалі. При збої: `rooms = []` → `visRooms = []`
→ `capacityMin = 0` → `util = 0` → коло «0 % завантаж.» ЧЕРВОНИМ, підпис «Низька»
і «Кабінетів немає». **Керівник читав збій читання як факт «апарати простоюють»** —
а це та цифра, за якою вирішують, чи купувати апарат.

Прямо нижче в тому ж файлі помилки RPC вже НЕ ковтались, із коментарем про рівно
цей ризик. Правило було, застосували його не всюди — той самий урок, що в U-8.

## Що зробили

| Місце | Було | Стало |
|---|---|---|
| `RescheduleModal` | `ovRes.error` ігнорувався | `throw` у той самий `catch`, що й для `rooms` |
| `StudyEditModal` | обидві помилки ігнорувались | обидві перевіряються; з'явились `schedLoading`/`schedErr` |
| `StudyEditModal` | межі з фолбэка 08–18 | `capBySched`/`capByBreak`/`inSchedCap` під `schedApplies` + `schedReady` |
| `StudyEditModal` | власний текст банера | спільний `lib/availabilityTrust` (як на решті екранів запису) |
| `CeoDashboard` | `error` не зв'язувався | зв'язаний; усі три шляхи провалу ведуть у `failed()` |
| `CeoDashboard` | «0 %» як факт | `ProgressCircle unknown` → «—»; вердикт і нульовий стан під `utilKnown` |
| `CeoDashboard` | лише тост на 6 с | постійний банер + прапорець `dataErr` |

Консервативна стеля при невідомості — **поточна тривалість запису**: редагувати й
скорочувати можна, ЗБІЛЬШИТИ — ні. Це не нове правило, а те саме, що вже діяло для
зайнятості (`busyReady`, H-6); тепер воно застосоване й до графіка.

## Що знайшло ревʼю пакета (і що з цього — власні регресії)

Два незалежні раунди. Другий (незалежний рецензент) дав сім знахідок; шість
підтвердились особистою перевіркою коду, і чотири з них — **регресії, внесені саме
цією правкою**:

1. **`RescheduleModal`: `throw` лишав оверрайд ПОПЕРЕДНЬОЇ дати.** До правки збій
   давав `data = null` і `setOverride(null)`; після — `setOverride` просто не
   викликався. Дата тут міняється при відкритій модалці, тож на 2 січня показувався
   банер «🚫 не працює · Новий рік» — і `valid` гасив «Перенести» для відкритого дня.
   *Виправлено:* `catch` обнуляє прочитане, а обидва банери («не працює», «особливий
   графік») стоять під `!schedErr` — вони були поза гейтом сітки.
2. **`CeoDashboard`: збережені старі кабінети — це кабінети ІНШОГО центру.** Рішення
   «не затирати `rooms` при збої» при зміні scope показувало апарати центру А під
   назвою центру Б. *Виправлено:* `loadedKeyRef` — старі цифри лишаються лише якщо
   вони про той самий scope+період, інакше стираються.
3. **`CeoDashboard`: гонка перекритих проходів.** `reload()` перестворюється на зміну
   періоду/scope і запускається негайно; пізній успіх старого проходу знімав `dataErr`
   і малював чужий період без банера — рівно те, від чого прапорець і поставлено.
   *Виправлено:* захист поколінням (`genRef`), той самий приймач, що в `lib/slotBusy`
   (H-3A).
4. **`StudyEditModal`: `schedReady` брехав, коли читання не було взагалі.** Прапорець
   дивився лише на виняток. Але «не читали» — теж «не знаємо»: без кабінету або без
   дати читання пропускається, а `maybeSingle()` віддає `{data:null, error:null}`,
   коли кабінет невидимий за RLS або видалений. У всіх трьох випадках екран
   упевнено показував «до кінця графіка (18:00)» для графіка, якого не бачив.
   *Виправлено:* `schedApplies` входить у `schedReady`; порожній рядок кабінету
   трактується як невідомий графік; без кабінету/дати графік не обмежує взагалі
   (стеля — `DUR_MAX`), і межа так і підписується.
5. **Підпис межі був плоским.** `windowLabel = !availTrusted ? …` ставив слова «дані
   не підтверджені» поруч із РЕАЛЬНИМ часом 18:00 у банері «поза графіком» (у нього
   інша межа — `inSchedCap`). *Виправлено:* `labelFor(cap)` — підпис рахується по
   самій межі, окремо для кожного споживача.
6. **Стеля невідомості могла стати `Infinity`.** При `duration_min = 0/null` усі три
   стелі ставали нескінченними і в UI друкувалось «Доступно у слоті: Infinity хв»
   (раніше це маскував завжди скінченний `capBySched`). *Виправлено:* фолбэк `DUR_MAX`.
7. **Сам сторож мав три дірки** — див. нижче.

## Сторож: сканер, а не список

Урок U-8: правило, застосоване руками, забудуть. Тому головний артефакт пакета —
не перелік перевірок, а **сканер** (`tests/readErrorTrust.test.ts`). Він сам
знаходить кожне читання `rooms`/`schedule_overrides` у шести екранах, класифікує
форму виклику (`named` / `destructured` / `promise-all`) і вимагає, щоб помилку
подивились. Нове читання — або нова форма, якої сканер не знає, — робить тест
червоним. Наступного порушника знаходить тест, а не наступний аудит.

Ревʼю знайшло в самому сканері три дірки, усі закриті:

* бачив лише подвійні лапки — `.from('rooms')` був би невидимим (не «невідома
  форма», а взагалі ніщо);
* `toContain(binder + ".error")` без межі слова — сторож із `binder="ov"`
  задовольнявся чужим `prov.error`;
* законна ідіома `const { data, error } = await …` вважалась невідомою формою,
  тобто сторож червонів на правильному коді.

**Свідомі межі сканера** (задокументовані в шапці тесту): він бачить лише
літеральне імʼя таблиці — `.from(TBL)` зі змінною не помітить; і він перевіряє,
що `error` ПРОЧИТАЛИ, а не що з ним щось зробили (`if (x.error) {}` пройде).

Сканер перевіряється **на самому собі**: окремий блок годує йому синтетичні
зразки (одинарні лапки, деструктуризація без `error`, кома всередині `select()`
у `Promise.all`) — інакше «зелено» означало б лише «сьогодні все добре».

## Що знайшла ЖИВА перевірка (а не тести й не ревʼю)

На проді, з підміненим `fetch` на конкретні запити (нічого не зберігалось,
статуси не мінялись, прод-дані звірені запитом — усі 8 записів на 28.08 у
вихідних статусах, `updated_at` не зрушив):

* **U-7** — коло чесно показало «—» замість «0 %», зʼявився постійний банер,
  «Завантаженість по апаратах» сказала «Дані не завантажились».
  **АЛЕ поруч лишились «Записи 0» і «Дохід 0 ₴»** — той самий дефект у сусідніх
  картках. Гейт був прив'язаний до однієї цифри, хоча всі вони похідні від тих
  самих даних. Виправлено: один прапорець `dataFresh` («дані на екрані описують
  ОБРАНИЙ зріз») на ВСІ похідні числа екрана — записи, дохід, тижневий графік,
  топ-5, смужки по апаратах. Коли дані свої, лише не оновились, цифри
  лишаються: про несвіжість каже банер, стирати робочі числа нема за що.
* **U-4** — `Доступно у слоті` впало зі 115 хв (порахованих по вигаданому
  графіку) до 90 хв — поточної тривалості запису, з підписом «дані кабінету не
  підтверджені»; спроба збільшити тривалість до 105 хв дала «⚠ Не вміщується» і
  сіру кнопку «Зберегти». Сітку дня замінив рядок «Не завантажилось: графік
  кабінету».
* **U-3** — сітка схована, у футері «Не завантажилось: графік кабінету»,
  «Перенести на цей слот» сіра; жодного твердження «не працює / особливий
  графік» не зʼявилось.

⚠️ Регресію «оверрайд ПОПЕРЕДНЬОЇ дати» живою перевіркою відтворити не можна без
створення рядка `schedule_overrides` на проді — вона лишається під статичними
сторожами (D17, D19), а не під живим сценарієм. Це записано свідомо.

## Фальсифікація

35 дефектів по черзі вносяться в код і тести, після кожного — прогін; кожен має
почервонити свій тест (`falsify.mjs`). Результат: **усі адресні**, а в першій
редакції (30 дефектів) **1 був мовчазним** — і саме він виявив декоративну
перевірку.

Мовчазним був дефект «прибрати межу слова з `consultsError`». Причина: приклад
у самому тесті — `binder="res"` проти `"ovRes.error"` — не спрацьовував і без межі
слова, бо в `ovRes` велика `R`. Перевірка виглядала правильною і не перевіряла
нічого. Приклади замінені на суфіксний (`prov.error` проти `ov`), префіксний
(`ovx.error`) і збіг через крапку (`a.ov.error`).

Це другий випадок у сесії, коли фальсифікація ловить сторожа, який пройшов би
ревʼю очима (перший — F1 у U-8, `toContain("showMove")` проти `showMoveLoading`).

## Чого пакет НАВМИСНО не робив

Ревʼю знайшло два реальні дефекти на сусідніх рядках. Вони **не цього класу** і
вимагають власного циклу — записані як нові знахідки аудиту:

* **U-12 · `ReferralPortal` не передає `offSchedule`.** `<StudyEditModal>` там
  рендериться без цього пропа, тож для направника запис, який ЛЕГАЛЬНО стоїть
  поза графіком (17:55 у кабінеті до 18:00), назавжди несохранюваний — рівно той
  провал, від якого писалась міграція 0077. Плюс `doEditStudies` кличе
  `editQueueEntryStudies(id, arr, dur, buffer)` — чотирма аргументами, губить
  пʼятий (`offSchedule`), тож галочка згоди мовчки викидається на клієнті, а
  сервер відхиляє збереження по `scheduleBlock`.
* **U-13 · порожній рядок `maybeSingle()` у `BookingModal` і `ReferralPortal`.**
  Той самий «не читали = не знаємо», що закрито тут у двох файлах. Не чіпали, бо
  шлях направника вимагає окремої перевірки RLS-видимості кабінетів (0139).
* **U-14 · сканер не покриває `incidents`** — теж джерело правди про доступність
  кабінету, але приходить пропами з дошки, тобто це інший канал (як у U-6).

* `npm run lint` — 0 помилок (одне відоме хибне попередження
  `react-hooks/exhaustive-deps` про `openBooking`, причина записана в коді);
* `npm run typecheck`, `npm run build`, `db:gate` — зелені;
* фальсифікація — 35 дефектів, звіт вище;
* **жива перевірка на проді** — три екрани, розділ вище;
* жодних змін у БД, міграцій і даних прода цей пакет не робить.

⚠️ Порядок тут не косметичний: жива перевірка знайшла те, чого не знайшли ні
тести, ні два раунди ревʼю по коду. «Тести зелені» — не заміна.
