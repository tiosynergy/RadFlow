# U-17 + U-18 + U-14 — читання, яких сторож не бачив

**Гілка:** `feat/read-trust-actions` · **Сесія 49, пʼятий пакет** (після U-33, U-13, 0166/0167)

---

## 0. Як знайшлися обидва дефекти

Не читанням коду. Аудит просив дрібницю — «додати `incidents` у `TABLE_RE`
сканера `readErrorTrust`» (U-14, помічений як заділ на майбутнє: ревʼю U-11
руками звірило всі девʼять продуктових читань цієї таблиці й дірок не знайшло).

Я додав таблицю — і заразом поставив у `FILES` файл `app/queue/actions.ts`,
якого там ніколи не було: сканер із дня свого написання дивився **лише в
`components/`**. Прогін одразу назвав два читання у ВІДОМО невідомій формі —
рівно U-17 і U-18 зі списку аудиту. Тобто сторож, задуманий «на майбутнє»,
першим же запуском знайшов минуле.

Заодно він назвав третє місце — `ReferralPortal`, — і воно виявилось **хибною
тривогою**: код там правильний, а сканер вимагав літерального `supabase` перед
`.from(`, тож `createClient().from(…)` для нього був невідомою формою. Це гірше
за хибну тривогу: найдешевший спосіб сховати читання від сторожа — назвати
клієнт інакше.

## 1. U-18 — «не читали» ≠ «модальність збігається»

```ts
async function studiesRoomMismatch(supabase, roomId, studies): Promise<boolean> {
  const { data } = await supabase.from("rooms").select("modality").eq("id", roomId).maybeSingle();
  return !studiesMatchModality(studies, data?.modality ?? null);   // error не звʼязували
}
```

`studiesMatchModality` **свідомо** поблажлива до `null`: кабінет `OTHER` не має
каталогу областей, обмежувати склад для нього нема чим. Отже збій читання
приходив тим самим значенням, що й «кабінет без каталогу».

**Замір, який робить діагноз однозначним** (прод, 2026-08-30):

| | |
|---|---|
| `rooms.modality` | **NOT NULL**, рядків із `null` — **0** |
| читання кабінету чужої клініки | **0 рядків, помилки НЕМАЄ** (`foreign_read rows=0 modality=<null>`) |
| те саме читання з видимістю | `own_read rows=1 modality=MRI` |
| тригер `check_studies_match_room` (0088) | **на місці** |

Тобто `null` тут не міг означати «кабінет без модальності» — тільки «ми не
прочитали». Поблажливість, потрібна `OTHER`, діставалась незнанню задарма.

### Чого цей дефект НЕ коштував — і чому це головна правка ревʼю

Перша редакція цього пакета стверджувала: користувач діставав «сиру помилку
тригера». **Ревʼю р2 показало, що це неправда**, і я звірив особисто: обидва
класифікатори — `classifyError` і `mapBookingError` — ловлять `MODALITY_MISMATCH`
і віддають **той самий** дружній текст. Видимий наслідок дефекту дорівнював нулю.

Втрачалось інше: **прикладна перевірка мовчки переставала існувати**. Її робота —
не текст (текст і так є), а другий рубіж; щойно читання ламалось, правильність
трималась на одному тригері, і дізнатись про це було нізвідки — зовні результат
виглядав однаково. Той самий клас, що знято TRUNCATE у 0166: глибина оборони,
яка тихо стає глибиною в один шар.

Це змінило й **лікування**. Перша редакція відмовляла при будь-якому незнанні
(fail-closed) — і це була б регресія: транзієнтний збій коштував би користувачеві
дії там, де раніше все проходило штатно, не додавши нічого до правильності.
Тепер:

| вердикт | що робимо | чому |
|---|---|---|
| `mismatch` | дружня відмова | як і було |
| `gone` (рядка немає) | відмова «оновіть форму» | запис і так не пройде, тільки з гіршим текстом |
| `empty` (значення порожнє) | відмова «спробуйте ще раз» | аномалія схеми; сьогодні недосяжна |
| `unreadable` (транзієнт) | **пропускаємо і пишемо лог** | тригер 0088 стереже; відмова коштувала б дії |

Різниця з сусідом по файлу принципова, а не примхлива: `closedRegionGate`
відмовляє при недоступному каталозі, бо **закриті послуги тригер не стереже**, а
модальність — стереже (заміряно).

Рішення винесено в чисту `modalityVerdict` (`lib/studies.ts`), у дії лишились
читання і мапа «вердикт → відповідь». Пʼять місць виклику:
`rescheduleQueueEntry`, `editQueueEntryStudies`, `createBooking`,
`scheduleFromWaitlist`, `createReferralBooking`.

## 2. U-17 — слід аварійної зупинки губився мовчки

```ts
const { data: incs } = await supabase.from("incidents")…   // error не звʼязували
await Promise.all((incs ?? []).map(inc => emitImportantEvent({ … })));
```

Збій читання → `incs = null` → `?? []` → **нуль подій журналу** про аварійну
зупинку, яка вже сталася і закомічена в RPC. Аудит назвав це найсерйознішим
пунктом свого списку: єдиний знайдений fail-open, наслідок якого **пишеться в
БД**, а не показується на екрані.

**Замір на проді** — обидва напрямки:

| | |
|---|---|
| щойно створений аварійний інцидент, читання роллю виклику | `desk_read rows=1` |
| конкурентне зняття аварії між RPC і читанням | `after_resolve rows=0`, **помилки немає** |

Друга гілка — та сама «порожньо без помилки», що й у U-18, і вона досяжна не
теоретично, а буденно: крон `resolve-expired-incidents` ходить раз на 5 хвилин.

**Лікування.** Відмовити не можна: зупинка вже відбулася, і «помилка» була б
брехнею про неї (той самий довід, що для `deliverPendingOutbox` поруч). Тому
лікуємо ВИДИМІСТЬ: `error` звʼязано, і три різні біди дістають три різні коди
через чисту `incidentGapCode` — `read_failed`, `no_rows`, `partial`.

Дві межі названо прямо в коді:

* **подію-замінник не вигадують.** У журналі фіксований перелік сутностей;
  «події про клініку» серед них немає, і підсунути `clinic_id` під
  `entityType: "incident"` означало б записати неправду в те саме місце, яке ми
  лагодимо. Слід аварії при цьому не зникає повністю: подія `event_outbox`
  пишеться транзакційно в самій RPC.
* **повтору читання немає** — він дублював би весь ланцюжок фільтрів і читався б
  у формі, якої сканер не розбирає. Корінь інший: журнал взагалі не мав би
  залежати від другого читання. Структурне лікування — навчити
  `emergency_stop_rpc` повертати `incident_ids` (борг **U-56**).

## 3. Що знайшли два раунди ревʼю

Обидва раунди — незалежні, висновки перевірено особисто по коду.

### Раунд 1 (коректність)

| | знахідка |
|---|---|
| MAJOR | **імʼя лог-події вибивалось із канону**: я писав `event: "incident.emergency_stop"`, а всі девʼять інших місць пишуть `event: "important_event.skipped"` — саме за ним і шукають пропуски журналу. Тобто вийшло **тихо там, де все й затівалось**. Тип події переїхав у `message` |
| MINOR | тип `{ known: true; modality: string \| null }` дозволяв повернути `null` у «відомій» гілці — тобто рівно вихідний дефект, і компілятор мовчав би. Звужено до `string` |
| MINOR | `ROOM_GONE_ERR` мав `code: "forbidden"`, а `ReferralPortal` підмінює текст для цього коду своїм «Немає доступу…» — порада «оновіть форму» зникала саме на шляху направника |
| MINOR | порожнє значення в ПРОЧИТАНОМУ рядку діагностувалось як «кабінет не знайдено». Додано третю причину `empty` |
| MINOR | два читання `rooms` у `actions.ts` мають однаковий биндер — тести звались однаково. Додано порядковий номер |

Раунд 1 також **перевірив шлях направника по політиках, а не міркуванням**:
`bookable ⊆ visible` (`rooms_referrer_read` 0139 ∧ `auth_referrer_can_book_room`
0029/0137), тож кабінета, куди направник вправі писати, але рядка не бачить, не
існує — регресії немає.

### Раунд 2 (сторожі)

| | знахідка |
|---|---|
| **BLOCKER** | fail-open, вставлений **після** розбору (`if (!mod.known && mod.reason === "error") return null;`), проходив УСІ пʼять пінів гейта. Лікування структурне: рішення винесено в чисту функцію і перевіряється ВИКЛИКОМ — така вставка стала неможливою за побудовою |
| **MAJOR** | обґрунтування пакета спиралось на **хибну посилку** («сира помилка тригера») — див. §1 |
| MAJOR | привʼязка читання до `roomId` не пінилась узагалі: `[^\n]*` ковтав увесь ланцюжок фільтрів |
| MAJOR | негативний пін `code: "forbidden"` обходився переносом рядка |
| MAJOR | коди `incidents_read_*` перевірялись на НАЯВНІСТЬ — перестановка гілок лишалась зеленою |
| MAJOR | тіло `logError` можна було сховати за `if (process.env.…)` усередині запіненого `if` |
| MAJOR | **деструктуризована форма (F2) не перевірялась зовсім** — приймалась за самим фактом слова `error` у шаблоні і виключалась із генерації перевірок. Моє ж розширення `RECEIVER` перевело `createClient().from(…)` з «невідомої» форми (червоно) у цю непідконтрольну (зелено) |
| MAJOR | лічильник «рівно пʼять місць виклику» був **антикорельований із власною метою**: шостий шлях БЕЗ гейта лишав число 5 (зелено), а шостий З гейтом давав 6 і повідомлення «кличуть не в усіх пʼяти» — тобто брехню. Тепер звіряється МНОЖИНА імен функцій |
| MAJOR | гард обсягу нагляду читав **власне оголошення** (`TABLE_RE.source`, `FILES.length >= 7`) — зелений і після перейменування таблиці, і після викидання пʼяти екранів |
| MINOR | текстові піни правила дублювали поведінкові тести, але червоніли б на `if (res.error != null)` — правці без дефекту |
| MINOR | придатність вікна блоку стверджував один сусідній тест; його видалення робило решту вакуумними |
| MINOR | биндер із `Promise.all` міг бути не ідентифікатором (`{ data: room`) → червоний тест із безглуздим імʼям; форма живе в `app/fhir/R4/Slot/route.ts` |
| MINOR | у фальсифікації не було **базової лінії**: зламаний заздалегідь сторож дав би 32 «правильні» червоні й бездоганний звіт |

## 5. Чого пакет свідомо НЕ робить

* **`queue_entries` не додано в сканер.** Заміряно: один рядок у регулярці
  робить червоними ще **вісім** місць — шість у `app/queue/actions.ts` (серед них
  `const { data: cur }`, чий збій читання показується як «Запис не знайдено»),
  одне в `CeoDashboard`, одне в `RescheduleModal`. Це окремий пакет (**U-55**):
  змішати «слід аварійної зупинки» з «читання бреше про ненайдений запис»
  означало б ревʼювати два різні ризики одним поглядом.
* **Охоплення сканера не універсальне.** Поза `FILES` лишається 30+ літеральних
  читань цих таблиць (сторінки, дошки, кілька route-handler-ів). Межа названа в
  шапці файлу і окремим тестом — щоб новий describe не створював враження, ніби
  охоплення під замком.
