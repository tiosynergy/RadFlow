## Сценарій `run` — два записи в ОДИН слот · PASS

Гарант: тригер `check_no_overlap` (0064).

```
КОНТРОЛЬ (2 різних слотів):  +0 мс 236 мс УДАЧА · +0 мс 302 мс УДАЧА
  → PASS: обидва пройшли, вікна запитів ПЕРЕТИНАЮТЬСЯ
ГОНКА (2 постріли в один слот): +0 мс 201 мс УДАЧА · +0 мс 243 мс ВІДМОВА 23P01
  → PASS: 1 удача з 2, решта — 23P01 OVERLAP від тригера 0064
розкид стартів: 0 мс · Прибрано 6 id · Лишилось: записів 0, позначок 0
```

⚠️ **Контроль тут не формальність.** Без нього «одна удача з двох» могла б
означати, що запити просто не встигли перетнутись, і гарант ні до чого.
Контроль доводить, що вікна перетинались.

## Сценарій `room` — два `in_progress` в ОДИН кабінет · PASS

Гарант: частковий унікальний індекс `queue_one_in_progress_per_room` (0018).

```
КОНТРОЛЬ: +0 мс 895 мс УДАЧА · +1 мс 881 мс УДАЧА → PASS, вікна перетинаються
ГОНКА:    +0 мс 223 мс ВІДМОВА 23505 · +1 мс 185 мс УДАЧА
  → PASS: 1 удача з 2, решта — 23505 від унікального індексу 0018
розкид стартів: 1 мс · Прибрано 6 id · Лишилось: записів 0, позначок 0
```

⚠️ Симетрія, яку варто назвати: САМЕ цей індекс до 0185 не стеріг ніхто —
частковий унікальний індекс у принципі не може бути constraint-ом, тож гілка
`k:` перевірки №23 його не бачить. Ветка `u:`, додана вчора за знахідкою
ревʼю, стереже інваріант, який сьогодні доведено живим пострілом.

## Сценарій `cas` — PASS (перший запуск за історію проєкту)

Гарант: `for update` + звірка `p_expected` усередині `queue_set_status_rpc`
(0075). Тут «відмова» — НЕ виняток: невдаха мусить отримати `updated=false` і
побачити статус переможця.

```
КОНТРОЛЬ: +0 мс 953 мс УДАЧА · +1 мс 962 мс УДАЧА → PASS, вікна перетинаються
ПАРАЛЕЛЬНИЙ CAS (2 × scheduled → waiting на ОДНОМУ записі):
  +0 мс 307 мс  ОНОВИВ
  +2 мс 306 мс  не оновив (бачить «waiting»)
  → PASS: 1 updated=true з 2, решта побачили «waiting» — лок і перечитування працюють
розкид стартів: 2 мс · Прибрано 5 id · Лишилось: записів 0, позначок 0
```

### ⚠️ ПЕРШИЙ ПРОГІН УПАВ, І ПРИЧИНА — В ІНСТРУМЕНТІ, А НЕ В ПРОДІ

`PGRST301 «No suitable key or wrong key type»`. Помилка ВИГЛЯДАЛА як проблема
ключа чи алгоритму й відправила діагностику шукати асиметричні ключі. Заміри,
зроблені дорогою (кожен корисний сам по собі):

| що перевіряли | результат |
|---|---|
| anon-ключ у `.env.local` | збігається з ЧИННИМ legacy anon, ref вірний, до 2036 |
| шлюз без Authorization | чиста `42501` (права), а не відмова по JWT |
| `alg` токена застосунку | **ES256** + `kid` — проєкт на асиметричних ключах |
| ключ сервіс-ролі | новий формат `sb_secret_…`, не JWT |
| обидві схеми `apikey` з ES256-токеном | **HTTP 200** |
| підміна `global.headers.Authorization` у supabase-js | працює |
| ГОЛИЙ `fetch` із ноди тим самим токеном | **HTTP 200** |

Тобто цілим було все — і токен, і оточення, і бібліотека. Винен був лаунчер:

> **`set /p` у cmd обрізає рядок на 1023 символах. Токен — 1038.**
> Заміряно прямо: `set/p прочитав 1023`, `у файлі 1038`.

Обрізана підпис — і PostgREST відмовив абсолютно правильно. Лаунчер переписано
на Node (обмеження немає), і він друкує довжину переданого токена, щоб обрізання
більше ніколи не було невидимим.

**Урок, що коштував години:** повідомлення про помилку називало НАСЛІДОК
(«ключ не підходить»), а не ПРИЧИНУ (рядок обрізали). Коли всі виміри вздовж
шляху зелені, підозрюваний — сам вимірювальний тракт, а не система.

⚠️ І другий урок, дрібніший: перша редакція перевіряльника токена друкувала
довжину, крапки, роль і термін — але НЕ `alg`. Тобто прилад міряв усе, крім
тієї єдиної властивості, через яку гіпотеза здавалась правдоподібною. Тепер
`alg`/`kid` друкує і перевіряльник, і сам харнес — ДО пострілу.

## ⚠️ ЗНАХІДКА: усі чотири RPC закриті від службової ролі

⚠️ **ПОПРАВКА ДО ПОПЕРЕДНЬОГО ФОРМУЛЮВАННЯ.** Спершу тут було сказано, що
«один токен розблоковує чотири сценарії». Це НЕПРАВДА, і ось точна межа:
харнес реалізує РІВНО ТРИ сценарії — `run`, `room`, `cas`. Токен розблоковує
лише `cas`. Решта — паралельні case-операції, конкурентний
`schedule_from_waitlist_rpc`, emergency stop з реальними affected rows —
коду в харнесі НЕ МАЮТЬ узагалі, і токен їм не допоможе: їх треба написати.
Це окремий пакет, а не «прогнати з токеном».

Сам замір нижче лишається чинним і корисним.

Замір 10.09 (зонд у транзакції з маркером відкоту, службова роль,
`auth_clinic_id() = NULL`, `auth_role() = NULL`):

| RPC | відповідь службовій ролі |
|---|---|
| `emergency_stop_rpc` | **28000** AUTH: не авторизовано |
| `schedule_from_waitlist_rpc` | **28000** AUTH: не авторизовано |
| `add_case_step_rpc` | **28000** AUTH: не авторизовано |
| `queue_set_status_rpc` | **42501** FORBIDDEN: запис не знайдено |

Це подвійно корисно:

1. **Позитивний результат безпеки:** усі чотири RPC справді закриті від
   службової ролі. Ключ бекенда не може ними керувати.
2. **Планувальний висновок:** решта сценаріїв конкурентності — паралельні
   case-операції, конкурентний `schedule_from_waitlist_rpc`, emergency stop з
   реальними affected rows — упираються в ТУ САМУ умову авторизації, що й
   `cas`. ⚠️ Але токен їх НЕ запускає: коду для них у харнесі немає (див.
   поправку вище).
