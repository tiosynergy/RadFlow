## 1. Звідки пакет

Завдання власника (с84, дослівно за змістом): окремий **контур платформи** — людина RadFlow,
яка керує **центрами як клієнтами, а не пацієнтами як записами**; оператор **не входить** у
`user_role` центру (admin, registrar, radiologist, referrer, ceo), це окремий обліковий запис
платформи **без `clinic_id`**; **service-role у браузер не віддавати**; функціонал і доступ
до даних — як у подібних SaaS (RadFlow не медичний продукт); **білінгу ще немає** — перша
версія = ручний контур, не платіжний провайдер, рахунки пізніше; **статуси центру від оплати
не залежать, але оператор може змінювати статус центру**.

## 2. Модель (рішення, прийняті в пакеті)

* **Оператор** = акаунт `auth.users` **без рядка `profiles`** (`user_metadata.managed='true'` —
  `handle_new_user` профілю не створює). Для RLS він ніхто: `auth_role()`/`auth_clinic_id()`
  NULL, політики дають нуль рядків, DEFINER-функції для `authenticated` відмовляють.
* **Право** = рядок у `platform_operators` (deny-all RLS, читає лише service_role). Усе, що
  оператор читає й пише, іде через сервер **після гейта** `requirePlatformOperator`
  (`lib/platformAuth.ts`): сесія → рядок за `user.id` ПЕРЕВІРЕНОЇ сесії (ніколи з тіла) →
  `active` → ліміт; єдиний вихід «ok» у кінці.
* **`app_metadata.platform='operator'`** — лише маршрутизація в middleware (edge, бази під
  рукою немає); ставить і знімає тільки сервер через `auth.admin`. Прав не дає.
* **Статус центру** — side-таблиця `platform_accounts` (немає рядка = `trial`):
  `trial / active / suspended / archived`. **DDL `clinics` не чіпали свідомо**
  (`tests/tzKyivPhase2.test.ts` пінить `k:clinics`; і адмін центру не може виставити собі
  статус через `clinics_update`). Статус застосовується при ВІДКРИТТІ сесії нашим сервером:
  `suspended`/`archived` — персонал центру не входить (див. §6 — це мʼякий гейт).
* **Облік без білінгу** — `plan`, `paid_until`, `notes` у тому ж рядку; на доступ не впливають.
* **Журнал оператора** `platform_log` (без ПДн; дія форми `a.b`), окремий від журналу центру.
* **Перший оператор** — `POST /api/platform/bootstrap` під `CRON_SECRET`, лише поки
  `platform_operators` порожня (потім 409); далі операторів створює оператор у консолі.

## 5. Ревʼю — три лінзи і другий раунд по фіксах

**Лінза A (SQL / ритуал / ACL).** **High:** накат падав би ЗАВЖДИ — нове тіло №24 читало
`platform_operators` до DDL (`raised:42P01` у сентинелі) → порядок DDL → старий №23 → передрук.
Також: явні гранти service_role + асерт; власний пробний центр у пробах (живий центр після
першої реальної зміни статусу дав би 23505 на PK обліку); ключі ПДн журналу розширено (паролі,
секрети, `note(s)`) і `k:platform_log` перезаміряно; передумова відкату; бюджет часу смоуку зовні.

**Лінза B (коректність / UX / тести).** **High:** петля `/platform ⇄ /queue`, коли прапорець є,
а рядка немає або він не прочитався → тристанове читання + машина станів (§3). Medium:
самовирівнювання прапорця при вході, `claim_synced`; контраст `.pf-secret .pf-hint` 4.17 → 4.73;
гейт перевірявся на одному роуті → `describe.each` по всіх; двійник не бачив атрибутів
`createUser/updateUserById` → `authArgs`. Low: `count==null` у bootstrap → 500; той самий
статус без рядка — no-op; біла проекція `details`; деградація агрегатів; доступність консолі
(заголовок без кнопки, aria-label з email префіксом, спінер, гліф aria-hidden); форма обліку не
скидає правлені поля при перечитуванні; дата `paid_until` без зсуву поясу; глибоке посилання.

**Лінза C (атакувальник).** HIGH немає; витоку service-role, доступу клієнтських ролей до
таблиць/функції, ескалації через прапорець — немає (перевірено читанням і запитами). **M-1:**
статус обходиться прямим входом у GoTrue (див. §6) — задокументовано, рішення власника (Н-25).
**M-2:** відкритий редірект `/login?redirect=/%09//evil.com` (WHATWG вирізає `\t` ДО розбору) →
`safeRedirectPath`. **M-3:** пласка модель довіри операторів — прийнято для v1 (Н-26). Low,
виправлені: збій читання рядка оператора знімав прапорець (→ `operatorKnown`); гонка «двоє
вимикають одне одного» (→ повторний перерахунок і повернення рядка); ліміт bootstrap до
порівняння секрету; login-CSRF (→ 415 для не-JSON); повний URL вебхука (→ хост); автовхід після
пароля оминав статус (→ `loginVerdict`); поведінкова проба ролей.

**Раунд 2 (по самих фіксах).** **H-1:** перша редакція `safeRedirectPath` перевіряла ВХІД, а
віддавала нормалізований шлях — `/..//evil.com` ставав `//evil.com` (регресія фіксу!) → перевірка
ВИХОДУ + інваріант на корпусі. **M-1:** проба ролей частково вакуумна — функція INVOKER з EXECUTE
падала б 42501 на ЧУЖІЙ таблиці, а відмову `SET ROLE` ковтав той самий обробник → перевірка
перемикання ролі, текст відмови мусить назвати обʼєкт, falsify E/F (механіку перевірено на живому
сервері: тексти «permission denied for table …» / «… for function …», роль повертається
відкатом субтранзакції). Low: перерахунок активних БЕЗ цілі (три запити), чесний текст
`claim_synced` за напрямком, порівняння форми обліку з trim, `key` картки, спінер на `/platform`,
деградація переліку центрів, маска лівої мітки хоста вебхука, червона базова лінія №24 у смоуку,
передумова відкату за метаданими, коментарі, поведінковий тест `createDeferredClient`.

## 6. Ціна і межі (названі заздалегідь)

* **Статус — мʼякий гейт.** Застосовується у двох місцях, де сесію відкриває НАШ сервер:
  `/api/auth/login` і автовхід `/api/account/set-password`. Anon-ключ публічний: вхід напряму
  в GoTrue (`/auth/v1/token`) і обмін коду в `/auth/callback` вердикт оминають, RLS статусу не
  знає; живі сесії, server actions, направники й керівники статусом не обмежені. Справжнє
  застосування — у БД (Н-25, рішення власника: це ще й продуктове питання — миттєво відрізати
  центр посеред зміни чи ні).
* **Пласка довіра операторів** (Н-26): будь-хто з операторів скидає пароль будь-якому
  активному (і може увійти під ним) та вимикає будь-кого, крім себе й останнього; контроль —
  журнал. Ролі/сповіщення — за рішенням власника.
* **Вікно bootstrap:** поки таблиця порожня, власник `CRON_SECRET` може викарбувати оператора —
  тому bootstrap одразу після деплою (409 на свіжому середовищі = хтось устиг раніше).
* Двійник PostgREST не вміє `update().select()` з поверненням рядків — гілка
  `clinic_blocked` у `/api/account/set-password` застережена статичним піном, а сам вердикт —
  поведінково через `/api/auth/login`.
* Акаунт «і оператор, і профіль центру» досяжний лише SQL — не робити (`loginVerdict` віддає
  пріоритет оператору, `requireRole` пустить за профілем).
* Під час накату FK на `clinics` і `auth.users` тримали SHARE ROW EXCLUSIVE ≈ секунди (записи в
  ці дві таблиці чекали; читання — ні). Реальних центрів на проді ще немає.
