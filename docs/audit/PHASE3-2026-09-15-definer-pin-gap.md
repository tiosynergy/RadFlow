## 4. 🔴 ГЛАВНАЯ НАХОДКА: `auth_is_desk` решает пять RLS-политик и не пинуется ничем

Двадцать одна функция — не однородный список. Двадцать из них **применяют**
решение (RPC очереди, кейсов, поиска, KPI). Одна — **принимает** его.

**`auth_is_desk()` вызывается в пяти политиках RLS, замер:**

| таблица | политика | команда | где |
|---|---|---|---|
| `doctors` | `doctors_desk_insert` | INSERT | `WITH CHECK` |
| `doctors` | `doctors_desk_update` | UPDATE | `USING` + `WITH CHECK` |
| `incidents` | `incidents_desk_insert` | INSERT | `WITH CHECK` |
| `incidents` | `incidents_desk_update` | UPDATE | `USING` + `WITH CHECK` |
| `schedule_overrides` | `sched_desk_write` | ALL | `USING` + `WITH CHECK` |

**Что это значит буквально.** Тело `auth_is_desk`, переписанное на
`return true`, открывает ЗАПИСЬ в три таблицы любому залогиненному
пользователю любого центра. `invariants_check` останется `ok:true`,
`checked:25`, `failed:[]` — потому что этой функции нет ни в списке №19
(пины тел, доступные `authenticated`), ни в №22 (пины тел, доступных `anon`).

⚠️ **И это не абстрактный «вектор».** Вся семья предикатов авторизации в
списке №19 **уже есть**: `auth_can_refer`, `auth_can_see_slot_details`,
`auth_clinic_id`, `auth_is_admin`, `auth_is_referrer`, `auth_radiologist_room_ok`,
`auth_referrer_clinics`, `auth_referrer_visible_rooms`, `auth_role`.
**`auth_is_desk` — единственный `auth_*`-предикат вне списка.** То есть это не
непокрытый класс, а **пропущенный член покрытого класса**, что хуже: защита
выглядит сплошной.

**Это буквальный повтор урока, уже записанного проектом** после `room_busy_slots`:
*«пинить функцию, которая РЕШАЕТ, а не только ту, что применяет решение»*.
Тогда `auth_can_see_slot_details` не пинился ничем 128 миграций. Здесь —
`auth_is_desk`.

## 5. ⚠️ Свежий долг: 0199 переписала тела двух непинованных функций

Миграция `0199_tenant_locks_and_radiologist_oracle.sql` (накат 15.09, уже на
проде) правит тела трёх функций:

| функция | доступна `authenticated` | в списке №19 |
|---|---|---|
| `set_waitlist_status_rpc` | **да** | **нет** |
| `schedule_from_waitlist_rpc` | **да** | **нет** |
| `integration_apply_status` | нет (`postgres`, `service_role`) | нет |

Сама 0199 сделана аккуратно — правит тело через `pg_get_functiondef` с
предварительной сверкой md5 и пост-ассертами, то есть **вслепую не пишет**.
Но результат этой правки **ничем не закреплён**: следующая правка тех же
функций уже не встретит ни одного сторожа.

⚠️ Это и есть долг, который в журнале назывался «0200». Его формулировка
уточняется замером: речь про **две** функции, а не три —
`integration_apply_status` недоступна `authenticated`, и её место в №22/№19
надо решать отдельно, а не заодно.

## 6. Что предлагается делать — по приоритету, с ценой

**Пакет 0200, узкий:** добавить в список №19 три подписи —
`auth_is_desk`, `set_waitlist_status_rpc`, `schedule_from_waitlist_rpc`.

Почему именно эти три, а не все 21: первая закрывает **решение о доступе**
(раздел 4), две другие — тела, переписанные **вчера** и потому наиболее
вероятные к следующей правке (раздел 5). Остальные 18 — применители решения;
их подмена видна по поведению продукта, а не молча.

⚠️ **Цена не нулевая, и её надо назвать заранее.** Список №19 пинует ПОЛНУЮ
строку: md5 тела + `attrs` (`;cfg=`, `secdef=`, `;owner=`, `;acl=`, `;vol=`,
`;lang=`). Значит любая будущая правка этих трёх функций — включая простой
`grant`/`revoke` — обязана идти вместе с обновлением пина. Это ровно тот
обмен, ради которого список и существует, но он превращает три функции из
«свободных» в «связанные».

**Оценка:** миграция + пины в тестах + фальсификация + два раунда ревью —
**2–3 ч**. Класс работы — прод-миграция, затрагивающая сторожа авторизации,
то есть полный протокол: ревью двумя разными линзами, проверка ЗАПРОСОМ после
наката, симметричный гейт (`накатил — смёржил`).

### Что НЕ предлагается и почему

* **пинить все 21** — список №19 станет тяжёлым, а 18 применителей дают
  громкий отказ при подмене. Это осознанная граница, а не забывчивость;
* **закрывать межи 5 и 8** — в схеме нет объекта нужной формы, красный базис
  взять неоткуда (раздел 1);
* **закрывать межи 1 и 2** (членство в ролях, `nspacl`, default privileges) —
  это не «дописать строку в список», а новая ветка сторожа по другому
  источнику. Отдельный пакет, и он **больше**, чем весь остаток 4.2.

### 🔴 Находка сборки: форма миграции выбрана неверно, и поймал это НЕ прод

Черновик написан якорной подменой — по образцу 0199, самой свежей миграции
такого класса. **Для списка №19 эта форма не работает**, и причина в тесте, а
не в базе. `tests/guardFnBodiesInvariant.test.ts`, функция `latestReprint()`:

```ts
const at = txt.search(/^create or replace function public\.invariants_check/m);
if (at < 0) continue;           // файл без ПОЛНОГО передрука просто пропускается
```

Тест берёт **последний файл миграции, содержащий полный передрук стража**, и
сверяет разобранный из него список с константой `PINNED`. Якорная миграция
такого текста не содержит — значит:

* 0200 был бы **пропущен** тестом, разбирался бы по-прежнему список из 0198;
* добавление трёх подписей в `PINNED` дало бы **40 строк против 43** — красное
  `npm test`, и диагноз указывал бы не туда.

**Вывод: 0200 обязан быть ПОЛНЫМ ПЕРЕДРУКОМ**, как 0192–0198, то есть
собираться скриптом `scripts/build-0200-reprint.mjs` по образцу
`build-0198-reprint.mjs` (в репозитории есть builder на каждую такую
миграцию — это и есть канон, а 0199 был исключением для обычных функций).

⚠️ **Это ровно то, ради чего существует правило «два раунда ревью разными
линзами, прежде чем трогать стража».** Первый же раунд — свой собственный,
по тестам, а не по SQL — снял форму пакета целиком. Накат якорной версии не
сломал бы прод, но дал бы красный `npm test` с диагнозом «список не сходится»,
и разбираться пришлось бы уже после правки боевого стража.

### Что осталось для 0200 — точный список

1. `scripts/build-0200-reprint.mjs` по образцу `build-0198-reprint.mjs`:
   тело стража + три строки после якоря `auth_is_admin()`;
2. сгенерировать `supabase/migrations/0200_…sql` (полный передрук) и
   `scripts/frag/0200_apply.sql` / `_dryrun.sql` / `_rollback.sql`
   — фрагмент нужен потому, что передрук и `comment on function` в каноничном
   файле идут **разными транзакциями**, а обрыв между ними оставляет новое
   тело со старым пином и мгновенно красит №25 (урок 0198);
3. добавить три подписи в `PINNED` в `tests/guardFnBodiesInvariant.test.ts`;
4. фальсификация: мутация «убрать строку `auth_is_desk` из списка» обязана
   дать красное — иначе пин декоративен;
5. два раунда ревью разными линзами, накат, проверка **запросом**
   (`invariants_check(false)` → `ok:true, checked:25`), симметричный гейт.

Логика, предсостояние и все асcерты уже написаны в черновике — переносятся
в билдер без пересчёта.
