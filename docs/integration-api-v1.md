# RadFlow Integration API v1 (читання + вебхуки + статуси виконання)

Контракт для інтеграторів RIS/PACS. Джерело рішень —
`docs/pacs-fhir-integration-plan.md` (§3 межі полів, §6 дизайн API).
**Режим A (за замовчуванням): жодних персональних даних пацієнта** — назовні
йдуть лише операційні поля (час, кабінет, послуга, статуси). Матчинг
пацієнта — на боці RIS за `entry_id` (opaque) / accession.

## Автентифікація

`Authorization: Bearer rfk_<48hex>` — ключ видає власник RadFlow
(`node scripts/integration-admin.mjs key:create …`), показується один раз,
у БД лише sha256. Ключ прив'язаний до однієї клініки і скоупів:
`slots:read`, `appointments:read`, `events:write`. Ліміт: 240
запитів/хв на ключ (`429` при перевищенні). Відкликання — миттєве.

## GET /api/integrations/v1/appointments

Скоуп `appointments:read`. Параметри (усі опційні):

| параметр | формат | опис |
|---|---|---|
| `updated_since` + `after_id` | ISO-8601 + uuid | keyset-курсор інкрементального синку: `(updated_at, id) > (…)`. Перший запит — лише `updated_since`; далі передавайте `paging.next` ЯК Є. Offset-піджингу немає навмисно (рухливий `updated_at` губив би рядки) |
| `date_from`, `date_to` | YYYY-MM-DD | за датою запису (`scheduled_date`) |
| `status` | CSV | значення `queue_status` (scheduled, waiting, in_progress, done, no_show, cancelled, not_held, needs_reschedule) |
| `room_id` | uuid | один кабінет |
| `limit` | 1..500 (дефолт 100) | порядок `updated_at ASC, id ASC` |

Відповідь:

```json
{
  "appointments": [{
    "entry_id": "uuid", "clinic_id": "uuid", "room_id": "uuid|null",
    "status": "scheduled", "call_status": "confirmed",
    "scheduled_at": "2026-08-12T07:30:00+00:00",
    "scheduled_date": "2026-08-12", "scheduled_time": "10:30",
    "duration_min": 30, "buffer_time_min": 5,
    "priority_level": "planned", "cito": false, "has_contrast": true,
    "off_schedule": false, "case_id": null, "case_step": null,
    "created_at": "…", "updated_at": "…",
    "studies": [{ "type": "МРТ", "region": "Колінний суглоб", "contrast": true }]
  }],
  "paging": { "limit": 100, "returned": 42, "has_more": false, "next": null }
}
```

Рекомендований синк: цикл, поки `has_more` — наступний запит з
`paging.next` (`updated_since` + `after_id`). Обробка ідемпотентна: подія/
рядок застосовується, лише якщо його `(updated_at, seq)` новіший за
збережений для `entry_id` (`seq` є лише у вебхуках; для REST достатньо
`updated_at` — сторінка завжди віддає повний поточний стан).

## GET /api/integrations/v1/slots

Скоуп `slots:read`. Параметри: `room_id` (обов'язковий uuid), `date_from`,
`date_to` (YYYY-MM-DD; діапазон ≤ 31 день; дефолт — сьогодні у TZ клініки
+13 днів).

Відповідь по днях: робоче вікно кабінету, перерви, зайнятість і **вільні
інтервали** (вікно − перерви − зайнятість). Часи — «стінні» `HH:MM` у
`timezone` клініки (IANA), конверсію в абсолютний час робить консюмер.
Причини недоступності не розкриваються.

`busy` — це **весь час, який не можна зайняти, крім перерв**: не лише записи
черги, а й простої кабінету (поломка, планове ТО, аварійна зупинка). Причина
назовні не йде — простій і запис виглядають однаково. Інтервали `busy`
злиті й не перетинаються; простій обрізається робочим вікном, тож `"24:00"`
у відповіді не зʼявляється. Кабінет, зупинений на весь день, віддає
`busy: [весь window]` і `free: []`.

> Зміна від 2026-08-27 (аудит I-1). До неї простої в цю відповідь **не
> потрапляли**: зупинений томограф публікувався як вільний, і бронь з боку RIS
> відхилялася вже на записі. Консюмер, який рахує завантаження кабінету за
> `busy`, тепер має враховувати, що 100% `busy` не означає 100% записів.

```json
{
  "room_id": "uuid", "modality": "MRI", "timezone": "Europe/Kyiv",
  "date_from": "2026-08-12", "date_to": "2026-08-12",
  "days": [{
    "date": "2026-08-12", "open": true,
    "window": { "start": "08:00", "end": "18:00" },
    "breaks": [{ "start": "13:00", "end": "14:00" }],
    "busy":   [{ "start": "10:30", "end": "11:05" }],
    "free":   [{ "start": "08:00", "end": "10:30" },
               { "start": "11:05", "end": "13:00" },
               { "start": "14:00", "end": "18:00" }]
  }]
}
```

`open:false` — кабінет цього дня не працює (`window/breaks/busy/free` порожні).

## GET /api/integrations/v1/rooms

Скоуп `slots:read`. Довідник кабінетів — звідки брати `room_id` для `/slots`
і для матчингу подій. Параметри: `include_inactive=1` (показати вимкнені),
`limit` 1..500 (дефолт 200).

```json
{
  "timezone": "Europe/Kyiv",
  "paging": { "limit": 200, "returned": 3, "has_more": false },
  "rooms": [{ "room_id": "uuid", "name": "МРТ-1", "modality": "MRI",
              "apparatus_model": "Siemens Magnetom", "active": true }]
}
```

`timezone` клініки повертається тут же: «стінні» часи зі `/slots` без неї
інтерпретувати не можна. Вимкнені кабінети за замовчуванням не віддаються —
у них не можна записувати.

## GET /api/integrations/v1/services

Скоуп `slots:read`. Довідник послуг зі **стабільним кодом** `code`
(`services.code`, 0144) — саме він призначений для HL7 `AIS` / FHIR
`serviceType` і переживає перейменування послуги.

| параметр | формат | опис |
|---|---|---|
| `room_id` | uuid \| `base` | що реально доступне в кабінеті: власні послуги кабінету + базові послуги тієї самої модальності. `base` — лише базові послуги клініки |
| `include_inactive` | `1` | показати неактивні |
| `limit` | 1..500 (дефолт 200) | |

```json
{
  "paging": { "limit": 200, "returned": 12, "has_more": false },
  "services": [{ "code": "SVC-3F91A0C2D4", "name": "МРТ колінного суглоба",
                 "modality": "MRI", "duration_min": 30,
                 "contrast_allowed": true, "room_id": null, "active": true,
                 "has_room_overrides": false }]
}
```

**Порожній список — не помилка.** `?room_id=X` віддає порожньо, якщо в
каталозі клініки немає послуг модальності цього кабінету. Каталог і черга в
RadFlow не зчеплені: реєстратор заводить запис із довільним переліком
досліджень, навіть коли послуги в довіднику не заведені. Тому не блокуйте
запис на підставі порожнього довідника — використовуйте `code` там, де він є.

`duration_min` може бути `null` (тривалість не задана) — передбачте це.
Ціни не віддаються навмисно. `room_id: null` = базова послуга клініки.

### Кабінетні перевизначення (важливо для планування)

Клініка може переозначити базову послугу **для окремого кабінету**: змінити
тривалість або прибрати послугу саме в цьому кабінеті. Звідси два режими
відповіді:

- **`?room_id=X` — зріз кабінету, ефективні значення.** `duration_min` уже
  враховує перевизначення. Послуга, прибрана в цьому кабінеті, **не
  повертається взагалі** — і під `include_inactive=1` теж: у кабінеті X її
  просто немає. Саме цей зріз показує реєстратор у себе на екрані, тож
  плануйте завантаження кабінету за ним.
- **`?room_id=base` і запит без `room_id` — каталог клініки, базові
  значення.** Одного правильного `duration_min` тут не існує: у різних
  кабінетах він різний. Такі позиції позначені `has_room_overrides: true` —
  побачивши прапорець, беріть точні значення зрізом кабінету.

`has_room_overrides` присутній завжди (`true`/`false`) і піднімається лише
тоді, коли перевизначення реально змінює віддані поля.

## POST /api/integrations/v1/appointments/{id}/events

Скоуп `events:write`. Канал «RIS повідомляє факт руху пацієнта». Приймаються
**лише факти**, не дані дослідження.

```json
{ "event": "arrived|started|finished",
  "source_event_id": "RIS-2026-08-12-000431",
  "at": "2026-08-12T10:31:00+03:00",
  "accession": "ACC-123" }
```

| поле | обов'язкове | правила |
|---|---|---|
| `event` | так | `arrived` → «Очікує», `started` → «Триває», `finished` → «Виконано» |
| `source_event_id` | так | ключ ідемпотентності, унікальний у межах клініки; друковані ASCII, до 200 символів. Пробіли по краях обрізаються, керуючі символи відхиляються |
| `at` | ні | ISO-8601 **з часовою зоною** (без зони — `400`). Фактичний час події; для `started` лягає в `in_progress_at`, обрізаний зверху по «зараз» |
| `accession` | ні | accession number RIS; прив'язується до запису (до 200 символів) |

Тіло закрите **переліком дозволених ключів**: будь-яке інше поле →
`400` з перерахуванням зайвих. Ліміт тіла — 8 КБ (`413`).

Відповідь: `{"result": …, "message": …, "entry_id": …, "requested_status": …,
"status": …, "previous_status": …}` (+ `accession_bound`, якщо передавали
`accession`).

| `result` | HTTP | що сталося |
|---|---|---|
| `applied` | 200 | статус змінено |
| `duplicate` | 200 | цей `source_event_id` уже приймали — повтор безпечний |
| `noop` | 200 | запис уже в цьому або пізнішому стані (застаріла подія) |
| `conflict` | 409 | запис у стані поза ланцюжком (скасовано, неявка, не відбулося) — подія його НЕ воскрешає |
| `busy` / `rejected_busy` | 409 | у кабінеті вже інший пацієнт `in_progress` |
| `reused` | 409 | той самий `source_event_id` під іншу подію/запис — колізія джерел, подія НЕ застосована |
| `rejected` | 422 | доменний гард (графік, перетин, заборонений перехід) — ретрай не допоможе |
| `not_found` | 404 | запису немає (або він чужої клініки) |

**Розрив ланцюжка добудовується.** Якщо RIS надіслав `finished`, а запис ще
`scheduled` — RadFlow сам проведе `waiting → in_progress → done`. Тобто
втрачена подія не блокує наступну.

**Ретраї.** Повторюйте на `409`, `429`, `5xx` (з backoff); на `400`, `404`,
`413`, `422` — не повторюйте, це контракт або стан, який ретрай не змінить.
Повторення з ТИМ САМИМ `source_event_id` безпечне: дедуп per clinic, і подія
не застосується двічі. `not_found` не «з'їдає» ключ: якщо запис зʼявиться
пізніше, той самий `source_event_id` можна надіслати ще раз.

Кожне застосування видно адміністратору в «Журналі дій» окремим типом —
з назвою ключа інтеграції як джерелом.

## Вебхуки (RadFlow → RIS)

Налаштовує власник (`webhook:set --clinic … --url https://…`); один ендпоінт
на клініку, тільки `https`. Кожна зміна запису породжує POST:

| подія | коли |
|---|---|
| `integration.appointment.created` | запис створено |
| `integration.appointment.rescheduled` | змінено час або кабінет |
| `integration.appointment.cancelled` | статус → cancelled / not_held |
| `integration.appointment.noshow` | статус → no_show |
| `integration.appointment.updated` | інші зміни експортованих полів |
| `integration.appointment.deleted` | запис видалено (payload: `entry_id`, `clinic_id`, `deleted:true`, `occurred_at`) |

Видалення КЛІНІКИ подій не породжує — канал вмирає разом з нею.
Події «тонкі» щодо послуг: `studies` несе type/region/contrast; стабільні
коди послуг (`services.code`, 0144) — через REST-довідник наступних фаз
(рішення зафіксовано, події не роздуваємо).

Тіло: `{…поля як в appointments, "event": "...", "idempotencyKey": "uuid",
"seq": N}` — завжди **повний поточний стан** запису (state-based, не diff).
`seq` — монотонний номер події: два UPDATE в одній транзакції БД мають
однаковий `updated_at`, тож порядок відновлюється парою `(updated_at, seq)`.

Вимоги до приймача (частина контракту):

1. **Дедуплікація за `Idempotency-Key`** (заголовок і поле) — доставка
   at-least-once, повтори законні.
2. **Порядок не гарантований** (ретраї з backoff: 30s→…→1h, до 10 спроб,
   далі dead-letter): застосовувати подію, лише якщо її `(updated_at, seq)`
   новіший за збережений для цього `entry_id`.
   Вимкнення вебхука (`webhook:disable`) НЕ буферизує назавжди: події
   ретраяться за тим самим backoff і при довгому вікні йдуть у dead-letter —
   після повторного ввімкнення зробіть повний ресинк через GET.
3. **Перевірка підпису** `X-RadFlow-Signature: sha256=<hex>` —
   HMAC-SHA256 від сирого тіла секретом вебхука (порівняння —
   константний час). Запити без валідного підпису відкидати.
4. Відповідь 2xx = прийнято (до 3 с); інакше — ретрай.

## Помилки

`400` невалідний параметр або тіло (текст у `{"error": "..."}`); `401` ключ
невалідний/відкликаний; `403` бракує скоупа; `404` чужий/неіснуючий кабінет
або запис; `409` стан заважає **зараз** (повтор пізніше має сенс); `413` тіло
понад 8 КБ; `422` доменний гард (ретрай не допоможе); `429` ліміт; `5xx`
тимчасово, повторіть із backoff.

Тексти помилок бази назовні не виходять: у відповіді — стабільний машинний
`reason` (`room_busy`, `stale`, `bad_request`, `domain_guard`,
`illegal_transition`, `server_error`) і прапорець `retryable`.

## Межі (важливо)

- Персональні дані пацієнтів НЕ передаються (режим A). Режим B
  (демографічний pass-through) — окрема письмова угода, поза цим документом.
- Клінічний контент (показання, протипоказання, нотатки лікаря, висновки,
  зображення) НЕ передається і НЕ приймається — такі запити відхиляються.
- Ззовні можна рухати **лише статус виконання** вже наявного запису
  (`events:write`). Створити запис, перенести його, змінити пацієнта,
  послугу чи кабінет через API не можна — планування лишається за
  реєстратором RadFlow.
- Канал подій приймає рівно чотири поля (`event`, `source_event_id`, `at`,
  `accession`). Це не «фільтр», а закритий перелік: усе інше — `400`, тож
  клінічний або персональний вміст не може потрапити в систему навіть
  помилково.
