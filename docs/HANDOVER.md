## 1. Обзор проекта

**RadFlow** — multi-tenant SaaS для интеллектуального управления очередью в центрах лучевой диагностики (МРТ/КТ). Вся очередь, расписание, приоритеты, инциденты и пересчёт живут внутри системы; RadFlow — единственный источник правды по очереди клиники. Каждая клиника (tenant) изолирована на уровне БД через PostgreSQL RLS по `clinic_id`. Несколько ролей работают над одной очередью одновременно, изменения расходятся в реальном времени.

### Стек

| Слой | Решение |
|------|---------|
| Приложение | Next.js 15 (App Router), React 19, TypeScript, Tailwind |
| Данные/Auth | Supabase: PostgreSQL + RLS + Auth |
| Realtime | Supabase Realtime (`postgres_changes`) через единый хук `lib/useRealtimeRefetch.ts` |
| Мутации | Server Actions (`"use server"`), CAS-оптимистичная блокировка статусов (`expectedFrom`) |
| Привилегии | `requireRole()` на сервер-роутах; service-role клиент `lib/supabase/admin.ts` (обходит RLS!) |
| Таймзона | Универсальная: `clinics.timezone` (IANA) + модель «настінний-час-як-UTC» |
| Хостинг | Vercel (авто-деплой из `main`, **Hobby** — cron только суточные); миграции применяются вручную в Supabase |

### Структура репозитория

## 2. Что изменилось в последних сессиях

Всё нижеперечисленное **закоммичено в `dev`**, но **не смерджено в `main` и не задеплоено**. **Миграций ничего из этого не требует** — схема осталась на `0060`.

### 2.1. Шаг слота 30 → 5 минут (главное)

Ключевой вывод аудита: **БД от шага сетки не зависит.** `check_no_overlap` сравнивает `tstzrange(scheduled_at, +duration)`, `room_busy_slots` отдаёт сырые интервалы занятости. Никакой «сетки» в схеме нет. Поэтому переход целиком фронтендовый, миграции не понадобились, а запрет двойной брони сохранился без изменений.

Что сделано:

- **`lib/slots.ts`** (новый): `SLOT_STEP = 5`, `SLOT_BLOCK = 30`, `buildSlots()`, `groupSlots()`, `countFit()`.
- **`components/SlotPicker.tsx`** (новый): единый компонент выбора слота вместо трёх инлайновых 30-минутных сеток. В строке 4 получасовых слота, каждый разбит на 6 пятиминуток (`00/05/10/15/20/25`); строк столько, чтобы покрыть график кабинета.
  - красный — занятая 5-минутка (занятость = длительность + буфер);
  - оранжевый — `tight` (исследование не влезает до следующей записи / конца графика);
  - приглушённый — прошедшее время;
  - **зелёный** — пятиминутки начала и конца планируемого исследования.
- Подключён в `BookingModal`, `RescheduleModal`, `ReferralPortal`. Каждая модалка передаёт свой `stateOf()` — семантика состояний не менялась.
- **Клинические длительности исследований НЕ трогали** (менялся только шаг выбора времени).

### 2.2. Счётчик ёмкости дня

Было «N вільних» — считало 5-минутные стартовые позиции. Но они **перекрываются**: 11:05, 11:10, 11:15 — три «свободных» позиции, а занять можно одну. После перехода на 5 минут число раздулось (~109) и стало откровенно врать.

Стало **«вміщується ще N»** (`countFit()`): жадная укладка слева направо с учётом `длительность + буфер` — сколько ещё исследований текущей длительности реально влезет. Это то число, которое нужно регистратуре.

### 2.3. Перерывы кабинета на конкретную дату

Раньше перерывы задавались только в Setup Wizard (базовые, `rooms.schedule.breaks[]`), а в редакторе графика на дату («Режим роботи») их не было — и в сетку они не попадали.

- `RoomOverride.breaks[]` в `lib/schedule.ts`; хранение в `schedule_overrides.rooms[roomId].breaks[]` (JSONB → миграция не нужна).
- Редактор перерывов в `ScheduleEditModal` (режим «Інші години»): добавить/удалить, валидация `начало < конец`.
- Новый хелпер **`effectiveRoomBreaks(date, roomId, roomSchedule, override)`**: если на дату есть override кабинета — перерывы берутся из него (пусто = без перерывов), иначе базовые. Подключён в Booking / Reschedule / Referral / StudyEditModal.
- **Цвет перерыва в сетке (закрыт UX-долг, 2026-07-11).** Раньше перерыв красился тем же красным, что и занятая запись. Теперь три разных состояния: `break` (сам слот внутри перерыва) → **серая штриховка** `.slot.brk` + строка «перерва» в легенде (показывается, только если перерывы в этот день есть); `tight` (слот рабочий, но исследование заедет в перерыв) → **оранжевый**, как и прочие «не вміщується», с тултипом «…перетне перерву 13:00–14:00»; `busy`/`blocked` → красный. Хелперы `inBreak()` / `breakClash()` в `lib/schedule.ts` (`overlapsBreak()` оставлен, но в сетке больше не используется).

### 2.4. Контраст в редакторе исследований (была потеря данных)

`StudyEditModal` не имел поля `contrast`: `seed()` не читал его из БД, а `save()` писал только `{type, region, dur}`. Любое редактирование состава **молча снимало контраст и теряло `price`** (сервер выводит `has_contrast` именно из `studies`).

Исправлено: чекбокс «Контраст» у каждого исследования (МРТ и КТ), ±15 мин (`CONTRAST_DUR`), контраст читается из записи и пишется обратно вместе с `price`.

## 5. Открытые задачи и приоритеты

### 5.1. 🔐 Ротация `SUPABASE_SERVICE_ROLE_KEY` (безопасность, P0)

Ключ засветился в скриншоте. **Агент не выполняет это сам** — проводит Игоря по шагам.

Важно: старый JWT-`service_role` **нельзя ротировать по отдельности** — Supabase перешёл на новые API-ключи. Правильный путь: Settings → API Keys → создать новый **secret** (`sb_secret_…`) → обновить env в Vercel → redeploy → проверить service-role флоу → **только потом** отключить старый ключ (он живой, пока явно не отключён). Проверить, не лежит ли ключ в n8n-конфиге и локальных `.env`.

### 5.2. Обработка коллизий очереди — ✅ ПОСТРОЕНА (2026-07-11), нужен live-тест

**Проблема:** идущее `in_progress` исследование затягивается и наезжает на следующую запись. Пациент А записан на 10:00, заведён в 10:20 — а пациент Б уже под дверью со слотом на 11:00.

**Продуктовые вопросы закрыты (ответы Игоря):**
1. Наезд меньше буфера → **тихий индикатор** (серый бейдж «+N хв»), панель не поднимаем.
2. Двигаем **только следующую запись (Б)**, не хвост дня.
3. За конец графика **не выталкиваем** — кто не влезает до закрытия, идёт в обзвон.

**Следствие:** транзакционный сдвиг хвоста **не понадобился**. Слот для Б ищется такой, где он никого не заденет (`firstFittingSlot`) → каскад не возникает по построению, и хватает обычного переноса одной записи (`rescheduleQueueEntry`, вся серверная валидация уже есть). **Миграций нет, RLS не трогали.**

**Что построено:**
- `lib/queueStatus.ts` → `collisionFor()` — единый источник правды: зона (`drift`/`clash`), время освобождения кабинета, наезд, кто в кабинете. Считает от `in_progress_at` и **не даёт кабинету «освободиться в прошлом»** (если «Завершити» не нажали — пациент всё ещё внутри). Записи в «Запізненні» пропускаются (у них своя панель) — иначе протухшая утренняя запись перехватывала бы панель у реального следующего пациента.
- `lib/slots.ts` → `firstFittingSlot()` — первый слот, куда запись влезает целиком (длительность + буфер, мимо занятости, перерывов, простоев, конца графика). `null` = только обзвон.
- `components/CollisionPanel.tsx` — панель решения: «Перенести на HH:MM» / параллельный кабинет (только если раньше) / «В обзвін» (`to_recall`) / «Змінити вручну». Занятость берёт из RPC `room_busy_slots` (он уже учитывает фактический старт), а не с доски.
- `components/QueueBoard.tsx` — бейджи в строке + панель в раскрытой + `doCollisionMove` / `doCollisionRecall`.

**Не сделано (осознанно):** панель есть только на админской доске. У радиолога — прежние guard'ы вызова (он не переносит записи). Если решим дать — переиспользовать `collisionFor`.

**Осталось:** live-тест на сиде (см. §7) и `npm run typecheck` / `build` у Игоря.

## 6. Технические решения и гочи

### 6.1. Модель времени — САМОЕ ОПАСНОЕ МЕСТО

В системе **три разных представления времени**. Перепутать их — значит получить данные, которые выглядят правильно, но ведут себя криво.

| Что | Как хранится |
|-----|--------------|
| `scheduled_time` | **`text` формата `"HH:MM"`** (не `time`!). `make_time()` даст `"08:00:00"`, и UI напечатает секунды |
| `scheduled_at` | **Не задавать вручную** — авторитетно считает триггер `set_scheduled_at` из `scheduled_date + scheduled_time` как «настінний UTC» (миграция 0035) |
| `in_progress_at` | **Реальный инстант** (`now()`). Миграция 0060 сама переводит его в «настінний» через TZ клиники |
| Время **инцидентов** | **Наоборот — «настінний UTC»** (клиент сравнивает `started_at` с `Date.UTC(...)` слота) |

Клиентская сторона: `wallNow(tz)` возвращает текущий «настінний» момент клиники, закодированный как UTC-мс. **Никогда не хардкодить `Europe/Kiev`** — брать `clinics.timezone`; на мультиклиничных экранах передавать TZ поэлементно.

### 6.2. Шаг слота 5 мин

- БД не знает про шаг сетки. Не пытайся «научить» её пятиминуткам — не нужно.
- Занятость слота = `duration_min + buffer_time_min`. Буфер — **после** исследования.
- `check_not_during_incident` буфер **не** учитывает (по чистой длительности) — это осознанное расхождение с `check_no_overlap`.
- Считаешь «сколько влезет» — используй `countFit()`, а не количество свободных стартовых позиций (они перекрываются).

### 6.3. Мультитенантность и права

- **RLS по `clinic_id` — security-critical.** Любые изменения политик/триггеров/RPC — **через subagent-ревью безопасности**.
- `lib/supabase/admin.ts` — **обходит RLS**. Каждый роут, который его использует, **обязан сам** проверить роль/доступ вызывающего (`requireRole()`).
- Глобальные аккаунты (`referrer`, `ceo`) имеют `clinic_id = NULL`; членство — в `referral_access` / `ceo_access`.
- Направитель правит запись в **двух** случаях: он автор (`created_by`) **ИЛИ** админ указал его направителем (`referrer_id`) — миграция 0057. **Не возвращать гард, блокирующий второй случай** — это осознанное решение.
- DB-гарды поверх RLS (defense-in-depth): `guard_status_change_referrer`, `guard_call_status_change` (0048), `guard_priority_change` (0046), `guard_waitlist_room` (0051).

### 6.4. Триггеры при массовых операциях

`trg_not_during_incident` висит **и на UPDATE** (`room_id`, `scheduled_at`, `scheduled_date`, `scheduled_time`, `duration_min`, `status`). Поэтому массовый UPDATE записей в сломанном кабинете **упадёт**. Обход для сида/миграций данных:

```sql
alter table public.queue_entries disable trigger trg_not_during_incident;
-- ... UPDATE ...
alter table public.queue_entries enable trigger trg_not_during_incident;
```

`trg_no_overlap` при этом **оставлять включённым** — он повторно провалидирует данные.

Хорошая новость: `check_not_during_incident` пропускает терминальные статусы (`cancelled`/`no_show`/`not_held`), поэтому **отменить пострадавшего пациента во время простоя можно**.

### 6.5. Realtime

Использовать **только** `lib/useRealtimeRefetch.ts`. Все клиентские `reload`-функции **обязательно** оборачивать в `try/catch` — транзиентный «Failed to fetch» (рефреш токена, смена сессии, сетевой блип) иначе валится в Next error overlay.

### 6.6. Миграции

Прод на **0060**; в репозитории готовы **0061** (`referral_rooms_guard`), **0062** (`room_busy_slots_detail`) и **0063** (`no_past_slots`) — применить вручную по порядку, после них следующая новая = **0064**. Применяются **вручную** через Supabase SQL Editor (автораннера нет). Всегда проверять максимальный существующий номер. Держать идемпотентными (`do $$ … exception when duplicate_object …$$`, `create … if not exists`, `drop … if exists`). Обновлять `supabase/types.ts` при смене схемы. **SQL применять к проду ДО мерджа `dev → main`** — деплой миграции не гоняет.

### 6.7. Ловушки тестирования ролей

- **`/referral` пускает админа** в режиме превью портала (одна клиника, все кабинеты), и сайдбар всё равно подписан «Лікар-направник». **Визуально неотличимо от настоящего направителя** — легко «проверить» портал, не выходя из админа. Проверять по имени внизу слева.
- **Dev и prod смотрят в ОДИН проект Supabase.** Очистка базы затрагивает и прод.
- У Игоря несколько профилей Chrome: смена роли долетает до вкладки агента, только если логиниться **в том же профиле**.

## 7. Как тестировать

### Подготовка данных

Запустить `supabase/seed/seed_test_7days.sql` в **Supabase → SQL Editor** (на предупреждение — «Run and enable RLS»; оно про backup-таблицы `_bak_*`). Скрипт data-driven, сам находит центры/кабинеты/админов/направителя. Даёт ~131 запись на 7 дней по всем центрам с полным набором сценариев. Подробности — `docs/audit/TEST_SEED_SCENARIOS.md`.

**Успешный прогон сида — уже тест:** вставки идут через реальные триггеры (`check_no_overlap`, `check_not_during_incident`, `set_scheduled_at`, `sync_cito_from_priority`). Нет `OVERLAP` → защита от овербукинга жива.

### Критичные флоу

**Новая запись (5 мин):**
Открыть «Новий запис» → выбрать область → убедиться: сетка 4×6, счётчик «вміщується ще N» правдоподобен (не сотня), выбрать слот со сдвигом (напр. `11:05`) → зелёным подсветились начало и конец, баннер показывает `11:05–12:05 + буфер до 12:10`. Сохранить → запись появилась на доске с этим временем.

**Овербукинг:** переоткрыть запись на тот же кабинет/дату → пятиминутки занятого интервала красные, причём **точно по границе** (если запись с 11:05 — то 11:00 свободна, а 11:05 занята).

**Перенос `in_progress`:** взять пациента «В кабінеті» → «Перенести» → в сетке его **собственный** слот показан свободным (self-exclusion через `p_exclude`) → перенести → статус сбросился в `scheduled`, `in_progress_at` обнулился, появился бейдж «🔁 Перенесено з …».

**Накладення (коллизия):** завести пациента А в кабинет с опозданием (или взять того, кто уже давно `in_progress`) так, чтобы `фактический старт + длительность + буфер` перевалил за слот следующего пациента Б. У Б в строке — красный бейдж «⚠ Накладення»; раскрыть → панель: «Кабінет звільниться о 11:25 … наїзд 25 хв» и кнопка «🗓 Перенести на 11:25» (время должно быть **первым, где Б влезает целиком**, а не «слот + дельта»). Проверить: перенос в один клик работает, у Б появляется бейдж «🔁 Перенесено з …»; «В обзвін» кидает Б в колл-лист. Если до конца графика Б уже не влезает — кнопки переноса нет, только обзвон/вручную. Если наезд поглощается буфером — вместо панели серый бейдж «+N хв».

**Realtime кросс-вкладочно:** открыть доску в двух вкладках на одну дату → в первой перенести запись → вторая **без ручного refresh** должна пересортироваться и показать новое время.

**Перерывы даты:** «Режим роботи» на дату → кабинету «Інші години» → добавить перерыв 13:00–14:00 → сохранить → в сетке этого кабинета на эту дату 13:00–14:00 закрыто **серой штриховкой** (не красным — красный только «зайнято»), **и закрыты слоты перед ним**, откуда исследование заедет в перерыв — они **оранжевые** («не вміщується»), тултип называет перерыв. В легенде появляется строка «перерва».

**Закрытый кабинет:** override «Зачинено» на дату → записи в нём получают бейдж «✎ Перезапис» и всплывают в панели «Обзвін через простій».

### Роли

Игорь логинит роль, агент проверяет (**агент не вводит пароли**). Реальный направитель с двумя центрами — логин **`Mariya2`**. ## 9. Решения, история и отвергнутые варианты

> **Зачем этот раздел.** Память агента **не переезжает** в новую сессию — она живёт вне репозитория. Всё, что не записано здесь, будет потеряно, и следующий агент начнёт заново предлагать то, что уже забраковали. Ниже — только то, чего **не видно из кода**.

### 9.1. Отвергнутые варианты (не предлагать заново)

**Визуализация 5-минутных слотов.** Прошла три итерации, две Игорь забраковал:

1. ❌ **Аккордеон** — 30-мин блоки со счётчиком, раскрывающиеся в 6 пятиминуток. Отвергнут.
2. ❌ **Барабан в стиле iPhone** — колесо со scroll-snap. Отвергнут («скролинг не снизу, а в маленьком модальном окне»).
3. ✅ **Финал:** плоская сетка — **4 получасовых слота в ряд, каждый разбит на 6 пятиминуток**, всё видно сразу, без скролла и без раскрытий.

Не «улучшать» это обратно в аккордеон или колесо.

**Гард на правку записи направителем.** Когда-то обсуждался запрет направителю править записи, где его указал админ. Это **реверсировано** миграцией 0057 — направитель правит и такие записи. Не возвращать.

**Счётчик слотов.** «N вільних» (число свободных стартовых позиций) — **осознанно убран**: позиции перекрываются и кратно завышают ёмкость. Заменён на `countFit()` → «вміщується ще N». Не откатывать «для простоты».

### 9.2. Решения и их причины

- **Буфер — ПОСЛЕ исследования.** Занятость кабинета = `duration_min + buffer_time_min` (переукладка/дезинфекция/поглощение задержек). Дефолт 5, варианты 0/5/10/15. В будущем должен стать per-service значением из прайса.
- **`check_not_during_incident` буфер НЕ учитывает** (только чистую длительность) — осознанное расхождение с `check_no_overlap`, не «баг».
- **Зелёные границы** в сетке = первая (`start`) и последняя (`start + dur − 5`) пятиминутки исследования, а не граница `start + dur`.
- **`profiles_referrer_linked_read` / `profiles_ceo_linked_read`** несут role-guard (`role='referrer'` / `role='ceo'`) как **осознанную границу изоляции** — админ не должен читать полный профиль и `invite_token` чужой роли только по факту гранта. **Не снимать этот guard.**
- **Перерывы даты перекрывают базовые.** Если у кабинета есть override на дату — перерывы берутся **только** из него (пусто = без перерывов). Модель «override полностью описывает этот день».
- **Аварийная остановка** не заводит свою сущность — это инцидент с `reason='emergency'`.

### 9.3. Как мы работаем (разделение труда)

- **Git, деплой и миграции — Игорь.** Локально / в Supabase SQL Editor. Агент пишет код и готовит SQL, но не коммитит и не деплоит сам. Перед мерджем `dev → main` — явное согласие.
- **Пароли агент не вводит.** Для браузерных тестов Игорь логинит нужную роль, агент смотрит.
- **Миграции применяются к проду ДО мерджа** — деплой их не гоняет.
- **Изменения RLS/политик/триггеров — через subagent-ревью безопасности.**
- **Linux-песочница агента ненадёжна:** bash-mount может отдавать усечённые/устаревшие копии файлов, `tsc`/`build` дают ложные ошибки. **File-инструменты (Read/Edit/Write) — истина**, `npm run typecheck` + `build` у Игоря — авторитетны.
- Общение с Игорем — по-русски, UI-копирайт — украинский.

### 9.4. Незакрытое наблюдение (честно)

Во время тестирования сидовый инцидент однажды оказался `resolved`, хотя при `auto_unblock = false` sweep в `loadIncidents` снять его не мог (он требует `auto_unblock !== false`). **Воспроизвести не удалось** — два контрольных теста (инцидент через UI и через SQL) прошли штатно, кабинет блокировался корректно. Не выдаю за баг. Если повторится — копать `resolveIncident` (`app/queue/actions.ts`) и путь снятия блокировки: инцидент, который молча перестаёт блокировать аппарат, — это риск записать пациента на сломанный томограф.
