# RadFlow — Кросс-модальный кейс пациента (design doc)

**Статус:** черновик дизайна (код не тронут). **Дата:** 2026-07-16.
**Автор проблемы:** ревью «пункт 7 — нет сквозного сценария нескольких модальностей для одного пациента».
**Следующая свободная миграция на момент написания:** `0091` (прод-БД на `0090`).

> Перед применением ЛЮБОЙ миграции/RLS/RPC/триггера из этого дока — **обязательный
> subagent-ревью безопасности** (канон HANDOVER §6.3). Числа миграций сверять по коду
> (максимальный номер + 1), а не по этому файлу — он отражает момент написания.

---

## 1. Контекст и цель

Сегодня единица очереди — `queue_entries`: один пациент × один кабинет × одна
модальность (инвариант закреплён триггером `check_studies_match_room`, 0088).
Это правильно и остаётся. Но реальный клинический маршрут часто **кросс-модальный**:

- Мамографія → УЗД молочних залоз;
- КТ → УЗД (уточнення);
- Рентген → повторне дослідження на іншому апараті.

Персонал вынужден заводить **несколько независимых записей** вручную. Между ними
нет связи: общего пациента/кейса, общего направления, порядка визитов, зависимости
«спершу маммографія, потім УЗД», общей отмены/переноса.

**Цель:** ввести слой **над** записями — «кейс» (эпизод обслуживания), группирующий
N связанных `queue_entries` разных модальностей, с общей идентичностью, порядком,
(опц.) зависимостями и групповыми операциями. **Без** слияния модальностей в один
entry и **без** нарушения 0088.

### 1.1. Подтверждение пробела по коду (2026-07-16)

- `queue_entries.Row` (`supabase/types.ts`) не содержит ни одной группирующей колонки:
  есть лишь `referrer_id` (человек-направитель, не кейс), `reschedule_origin`
  (снимок для бейджа «перенесено з»), `created_by`.
- Таблиц `patients` / `cases` / `visits` / `referrals` в схеме **нет**: личность
  пациента денормализована в каждый `queue_entry`. То есть «общий пациент» сегодня
  тоже не представим — кейс станет первой реляционной связкой пациента между записями.

---

## 2. Не-цели (что НЕ делаем этой фичей)

- **Не** мержим разные модальности в один `queue_entry` — 0088 остаётся стеной.
- **Не** вводим полноценный мастер-реестр пациентов с дедупликацией по всей клинике
  на первых фазах (это опциональный P3; см. §9).
- **Не** трогаем анти-овербукинг, буферы, wall-модель времени, политику задержки —
  кейс их переиспользует, а не заменяет.
- **Не** делаем медицинскую логику «правильных» цепочек (какое исследование за каким
  клинически должно идти) — порядок/зависимость задаёт оператор.

---

## 3. Ключевые инварианты и обратная совместимость

1. **`queue_entries.case_id` — nullable.** Запись без кейса = сегодняшнее поведение.
   Ни одна существующая запись не мигрирует принудительно (backfill не нужен).
2. **Кейс не отменяет per-entry гарды.** Групповые RPC вызывают ту же логику, что и
   одиночные (статус-матрица 0069/0079, анти-овербукинг, простои, перерывы, прошлое,
   график 0084, права вызова 0085).
3. **Порядок блокировок — единственный** (канон §6.0.9): сначала строки
   `queue_entries` (`for update`, детерминированный `order by`), потом advisory-lock
   кабинета (его берёт `check_no_overlap` в триггере). Групповые RPC обязаны его
   соблюдать по ВСЕМ записям кейса разом.
4. **Каждая новая колонка `queue_entries` требует `grant update (col) … to
   authenticated`** (канон 0070) — иначе UI молча получит `42501`.
5. **Статусные мутации — только через RPC** (канон 0070): групповая отмена/перенос —
   новые RPC, не `.update()` из клиента.
6. **Время — только `wallNow(tz)` / `wallDayKey(tz)` / `wallToday0(tz)`** (§6.1).

## 4. Модель данных

### 4.1. Таблица `patient_cases`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | `uuid pk default gen_random_uuid()` | — |
| `clinic_id` | `uuid not null → clinics(id)` | тенант (RLS-ключ) |
| `referrer_id` | `uuid null → profiles(id)` | общее направление кейса (человек) |
| `created_by` | `uuid null → profiles(id)` | автор |
| `status` | `case_status not null default 'open'` | `open` / `completed` / `cancelled` |
| `sequential` | `boolean not null default false` | P3: жёсткая зависимость шагов |
| `note` | `text null` | клиническое примечание/показание |
| **Снимок пациента** | | до появления `patient_id` (P3) — денормализовано, как в `queue_entries` |
| `patient_name` | `text not null` | |
| `patient_phone` | `text null` | |
| `patient_dob` | `date null` | |
| `patient_sex` | `text null` | |
| `patient_email` | `text null` | |
| `created_at` | `timestamptz not null default now()` | |
| `updated_at` | `timestamptz not null default now()` | |

Индексы: `(clinic_id)`, `(clinic_id, status)`, `(referrer_id)`.

> **Почему снимок, а не сразу `patients`-таблица:** текущая модель денормализует
> пациента на `queue_entries`. Кейс наследует ту же модель (снимок копируется в
> порождаемые записи). Мастер-запись пациента с дедупом (`patient_id` на кейсе и
> записях) — отдельный P3, чтобы не раздувать P0 миграцией пациентов.

### 4.2. Правки `queue_entries`

| Колонка | Тип | Назначение |
|---|---|---|
| `case_id` | `uuid null → patient_cases(id) on delete set null` | принадлежность кейсу |
| `case_step` | `smallint null` | порядок шага в кейсе (1,2,3…); `null` вне кейса |
| `depends_on` | `uuid null → queue_entries(id)` | **P3**: жёсткая зависимость |

- `on delete set null` (не cascade): удаление кейса **не** удаляет записи — только
  разрывает группировку. На практике кейс не хард-делитим, а `status='cancelled'`
  (журналируемость, как везде в проекте).
- Индекс `(case_id)` частичный `where case_id is not null`.

### 4.3. Enum `case_status`

`open` → пока хоть один шаг активен/запланирован; `completed` → все шаги `done`;
`cancelled` → кейс снят. Переход `open→completed` считает сервер/триггер по шагам
(а не клиент).

## 5. Миграции

### 5.1. `0091` — P0: модель кейса (не меняет поведение)

Скелет (идемпотентный; **до применения — subagent-ревью**):

```sql
-- 0091: patient_cases + queue_entries.case_id/case_step + RLS + grants.
-- Аддитивно: case_id NULL = сегодняшнее поведение. Поведение записей не меняется.

-- enum case_status (idempotent)
do $$ begin
  create type public.case_status as enum ('open','completed','cancelled');
exception when duplicate_object then null; end $$;

create table if not exists public.patient_cases (
  id            uuid primary key default gen_random_uuid(),
  clinic_id     uuid not null references public.clinics(id),
  referrer_id   uuid references public.profiles(id),
  created_by    uuid references public.profiles(id),
  status        public.case_status not null default 'open',
  sequential    boolean not null default false,
  note          text,
  patient_name  text not null,
  patient_phone text,
  patient_dob   date,
  patient_sex   text,
  patient_email text,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

create index if not exists idx_cases_clinic        on public.patient_cases(clinic_id);
create index if not exists idx_cases_clinic_status on public.patient_cases(clinic_id, status);
create index if not exists idx_cases_referrer      on public.patient_cases(referrer_id);

alter table public.queue_entries
  add column if not exists case_id   uuid references public.patient_cases(id) on delete set null,
  add column if not exists case_step smallint;

create index if not exists idx_qe_case on public.queue_entries(case_id) where case_id is not null;

-- 0070-канон: новые колонки queue_entries требуют явного колоночного grant.
grant update (case_id, case_step) on public.queue_entries to authenticated;

-- RLS (см. §6) — политики patient_cases.
alter table public.patient_cases enable row level security;
-- ... policies ...

-- realtime (по образцу 0086, если экран кейса живой):
-- alter publication supabase_realtime add table public.patient_cases;  -- при необходимости
-- alter table public.patient_cases replica identity full;

-- Хвост-проверка:
--   select has_column_privilege('authenticated','public.queue_entries','case_id','update');   -- t
--   select count(*) from public.patient_cases;                                                 -- 0
```

### 5.2. `0092+` — P1/P2: RPC групповых операций

- `cancel_case_rpc(p_case_id uuid)` — атомарная отмена (§7.1).
- `reschedule_case_rpc(...)` — перенос по preview+apply (§7.2), по образцу
  `queue_apply_delay_plan_rpc` (0080/0081): всё-или-ничего, детерминированный порядок,
  stale-сверка снимка.
- Триггер/функция пересчёта `patient_cases.status` из статусов шагов.

### 5.3. `0093+` — P3: зависимости и (опц.) мастер-пациент

- `queue_entries.depends_on` + BEFORE-триггер: запрет старта/`done` шага, пока
  предшественник не `done` (только при `patient_cases.sequential = true`).
- (Опц.) таблица `patients` + `patient_id` на кейсе и записях; дедуп по phone/dob.

## 6. RLS (`patient_cases`)

Зеркалит правила `queue_entries` (переиспользовать существующие хелперы
`auth_clinic_id()`, `auth_is_admin()`, `auth_is_desk()`, `auth_is_referrer()`):

- **Персонал центра** (`auth_clinic_id() = clinic_id`): SELECT/INSERT/UPDATE.
  DELETE — не давать (кейс снимается статусом, не удаляется; журналируемость).
- **Направитель**: SELECT/UPDATE кейса, где он `referrer_id` **ИЛИ** `created_by`
  (зеркало 0057 «автор ИЛИ указан направителем» — не вводить гард, блокирующий второй
  случай). Глобальный аккаунт (`clinic_id IS NULL`) → членство через `referral_access`.
- Роль-разделение по 0073: `registrar`/`radiologist` ≠ `admin` там, где это уже
  различается для записей.

> Любая политика/функция здесь — **через subagent-ревью** (в этой линейке ревью ловило
> дыры серьёзнее исходных практически каждый раз).

## 7. RPC / серверные действия

### 7.1. Создание кейса

Server Action `createCase(...)` (граница со схемой `zod`, канон §6.1.1): создаёт
`patient_cases` + N `queue_entries` (по одному на шаг/модальность), проставляя
`case_id`, `case_step` и **копию снимка пациента** в каждую запись. Каждая вставка
проходит **штатные** триггеры (0088 тип↔кабинет, анти-овербукинг, простои, график) —
кейс их не обходит. Если хоть один шаг не проходит — весь кейс откатывается (одна
транзакция или компенсация).

### 7.2. Групповая отмена — `cancel_case_rpc(p_case_id)`

`SECURITY DEFINER`, `set search_path = public`. Порядок:

1. Авторизация: `auth_is_desk()` центра кейса (отмена — desk, ср. 0085); чужой
   `clinic_id` не проходит.
2. `select id from queue_entries where case_id = p_case_id for update order by id`
   — блокировка строк ПЕРВОЙ, детерминированный порядок (канон §6.0.9).
3. Для каждой записи в отменяемом состоянии (`scheduled`/`waiting`) → `cancelled`,
   соблюдая матрицу переходов (0069/0079). Записи уже `done`/`in_progress` —
   пропускать (или решение владельца, см. §12).
4. `patient_cases.status = 'cancelled'`; аудит без PII (0053).
5. Вернуть число отменённых. Транзиентные `40P01/55P03/57014` → код `stale`
   («спробуйте ще раз»), как в `isRetryableLockError`.

### 7.3. Групповой перенос — `reschedule_case_rpc` (P2)

Сложнее: каждому шагу нужен свой слот. Не «одна дельта на всех». Взять паттерн
`queue_apply_delay_plan_rpc` (0080/0081): **preview** (посчитать план новых слотов
для каждого шага с учётом графика/буферов/`firstFittingSlot`) → **явное
подтверждение оператора** → **apply** всё-или-ничего с stale-сверкой снимка статусов.
Сдвиги применять от позднейшего к раннему (иначе наезд на несдвинутого соседа).

## 8. UX-флоу

- **Мастер «Пакет досліджень» (кросс-модальний).** В `BookingModal`-подобном флоу:
  добавить N исследований разных модальностей → на каждое выбирается свой кабинет
  (той же модальности, 0088) и слот → «Створити кейс». Порождает кейс + N записей.
  Реюз `SlotPicker`, `firstFittingSlot`, каталогов `lib/studies.ts`.
- **Экран кейса.** Список шагов (модальность · кабінет · час · статус), порядок,
  общий пациент/направитель, кнопки **«Скасувати кейс»** / **«Перенести кейс»**.
  Бейдж «наступний крок» при мягкой зависимости.
- **Доска очереди.** Бейдж-маркер кейса на записи (напр. «🔗 Кейс 2/3») + переход в
  экран кейса. Сортировка доски не меняется (по времени, §2.6).
- **Лист очікування / портал направителя.** Case-aware — позже (P2): кандидат может
  быть шагом кейса; направитель видит свои кейсы (RLS §6). Учесть уже исправленный
  rooms-realtime и пагинацию листа (см. ревью п.6).

UI-копирайт — украинский; коммуникация/этот док — русский.

## 10. Взаимодействия и риски

- **0088 не трогаем** — кейс над записями, инвариант тип↔кабинет остаётся per-entry.
- **Конкурентность:** групповые RPC = много строк под блокировкой → строго
  единый порядок захвата (строки → advisory), иначе дедлок со статусными RPC (§6.0.9).
- **Каскады/журналируемость:** `on delete set null` + отмена статусом, а не delete
  (как неизменяемые журналы 0053/0055 — FK на них сознательно нет).
- **Realtime:** если экран кейса живой — подписка на `patient_cases` (+ `replica
  identity full`, образец 0086), и не забыть, что `queue_entries`-события уже приходят.
- **RLS-регресс:** новая таблица — новая поверхность утечки PII; политики строго по
  `clinic_id` + правило 0057 для направителя; **subagent-ревью обязателен**.
- **Миграция данных пациентов (P3)** — самый рискованный кусок; выносим в отдельную
  фазу с precheck, как `0064_PRECHECK`.
- **Тесты:** новые чистые хелперы (`lib/case.ts` — статус кейса из шагов, порядок,
  готовность зависимого шага) покрыть `vitest` (как `tests/*`); RPC/RLS — прогон на
  сиде + subagent parity-ревью (SQL ↔ TS).

## 11. Тестирование (план)

- **vitest**: `caseStatusFromSteps()`, `nextRunnableStep()`, порядок шагов,
  `dependencyReady()` — чистая логика `lib/*`.
- **Сид**: сценарий кейса Мамографія→УЗД на сиде; успешный прогон = тест (вставки идут
  через реальные триггеры).
- **Живой (Claude-in-Chrome)**: создать кейс на 2–3 модальности → шаги на доске →
  групповая отмена снимает все активные шаги → перенос кейса переставляет слоты →
  зависимость блокирует старт шага B до `done` шага A.

## 12. Открытые вопросы (решения владельца)

1. **`done`/`in_progress` шаги при отмене кейса** — пропускать или запрещать отмену
   кейса с уже выполненными шагами? (Предложение: пропускать выполненные, отменять
   только активные, кейс → `cancelled` если не осталось активных.)
2. **Зависимость по умолчанию** — кейсы по умолчанию `sequential=false` (мягкая
   подсказка) или `true` (жёсткий блок)? (Предложение: `false`, жёсткость — опция.)
3. **Один направитель на кейс или на шаг?** (Предложение: на кейс, с возможностью
   переопределить на шаге — как сейчас `referrer_id` на записи.)
4. **Мастер-пациент (P3)** — нужен ли дедуп по phone/dob сейчас, или снимка на кейсе
   достаточно на обозримую перспективу?
5. **Цена/оплата кейса** — суммарная стоимость пакета показывать на экране кейса?
   (Реюз `studiesTotalPrice`; цены новых модальностей пока `0` — см. отдельный TODO.)

**Итог:** пробел реальный и аддитивно закрываемый слоем «кейс» над `queue_entries`,
без нарушения 0088 и текущих канонов. Рекомендованный вход — **P0 (`0091`)**: чистая
модель + RLS, ноль изменений поведения, после subagent-ревью.
