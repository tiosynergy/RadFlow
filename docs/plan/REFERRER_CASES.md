# Кейси для направника — повний паритет з адміном (план)

**Дата:** 2026-07-20 · **Статус:** ✅ РЕАЛІЗОВАНО (сесія 4: міграція `0118_referrer_cases.sql`
верифікована в откаті SMOKE_OK; smoke `referrer_cases_smoke.sql`; тулчейн 231/231; ревʼю SHIP).
Відкриті питання §6 вирішені власником: (1) лише свої кейси; (2) скасування поки жоден крок не
стартував (`in_progress/done/no_show/not_held` блокують); (3) свій кейс-бар у NewReferral.
Не реалізовано свідомо: редагування вже доданого кроку в кейс-барі (лише прибрати/додати знову).
Лишилось: накатка 0118 власником + живий тест під СПРАВЖНІМ направником.
**Рішення власника:** направник формує кросс-модальні кейси «як адміністратор» —
повний паритет: створення кейса з кроками, додавання кроку, організація кейса з
існуючого запису, скасування СВОГО кейса.

## 1. Що блокує сьогодні (перевірено по коду/прод-БД)

Всі кейс-RPC — SECURITY DEFINER з ЯВНИМ гейтом проти направника:

| RPC | Гейт сьогодні | Остання редакція |
|---|---|---|
| `create_case_rpc` | `auth_is_referrer()` → FORBIDDEN «кейс створює персонал центру» | 0106 |
| `add_case_step_rpc` | те саме («кроки кейса додає персонал») | 0106 |
| `case_from_entry_rpc` | те саме («кейс організовує персонал») | 0106 |
| `cancel_case_rpc` | лише admin/registrar | 0106 |

Плюс модель прав УСЕРЕДИНІ RPC — на `auth_clinic_id()` (у глобального направника
NULL). А от RLS patient_cases, як зʼясувалось, ГОТОВА (див. §3) — блокують саме RPC.

## 2. Модель прав (міграція 0118)

Спільний принцип: **«персонал центру АБО направник у межах його грантів»**, з
анти-oracle (чуже/неіснуюче = один FORBIDDEN).

- **Клініка:** направник → `auth_can_refer(v_clinic)` (замість `v_clinic = auth_clinic_id()`).
  `v_clinic` береться з параметра/запису, НЕ з профілю.
- **Кабінети кроків:** КОЖЕН крок — `auth_referrer_can_book_room(room_id)` (хелпер уже
  є, 0111; враховує `room_ids` направника і канон NULL=усі, гард 0061).
- **Власність:** направник оперує лише СВОЇМИ кейсами. ✅ Схема ВЖЕ готова (0091):
  `patient_cases.created_by` І `referrer_id` існують; критерій — `created_by = auth.uid()
  or referrer_id = auth.uid()` (як у наявній RLS). add_case_step / case_from_entry /
  cancel — тільки для своїх; чужий кейс = FORBIDDEN (як «не знайдено», анти-oracle).
- **cancel_case_rpc для направника:** тільки свій кейс і тільки поки ЖОДЕН крок не
  `in_progress`/`done` (правило уточнити на старті сесії; адмінська гілка без змін).
- **Незмінне:** кроки кейса — лише в межах графіка (0106); порядок локів
  `patient_cases → queue_entries → advisory` (0106/0109); пересічення кроків (0096/0099);
  розрахунок статусу (0109). Ці інваріанти НЕ чіпати — тільки гейти прав.

## 3. RLS — ✅ ВЖЕ ГОТОВА (0091, перевірено 2026-07-20)

Схема patient_cases ІЗ САМОГО ПОЧАТКУ проєктувалась під направника:
- `cases_select_referrer`: `created_by = auth.uid() OR referrer_id = auth.uid()` — є.
- INSERT-політика направника: `(created_by = uid OR referrer_id = uid) AND
  auth_can_refer(clinic_id)` — є (рядок 146 міграції 0091).
Тобто блокують ЛИШЕ гейти в RPC (`auth_is_referrer() → FORBIDDEN`) — RLS чіпати
не треба (лише перевірити smoke-ом). `queue_entries` направник читає свої за
існуючими політиками — перевірити, що кроки його кейса під них потрапляють.

## 4. Клієнт

- **ReferralPortal**: кейс-бар як у BookingModal (`onCreateCase`/`onAddCaseStep`/
  `caseSiblings`): «＋ У кейс» накопичує кроки різних модальностей (тільки доступні
  йому кабінети), «Створити кейс (N)»; для існуючого запису — «Організувати кейс»;
  список СВОЇХ кейсів + «Додати крок» + «Скасувати кейс» (поки не стартував).
  Зв'язка з бэклогом [[radflow-referrer-board]] (доска направника) — кейси показувати
  там же.
- **Server Actions**: referral-версії createCase/addCaseStep/caseFromEntry/cancelCase
  в actions портала (клієнт RLS-bound; авторизація в RPC). Реюз zod-схем із
  app/queue/actions (sCase тощо) — винести спільне в lib, НЕ дублювати.
- Ліміти: та сама валідація складу (zStudiesRequired), fail-closed каталог-гейт
  (closedRegionGate, 0112/0113), SERVICE_CLOSED-маппінг.

## 5. Верифікація (обовʼязково)

- Smoke із RLS-імперсонацією (патерн services_referrer_scope_smoke.sql):
  a) направник створює кейс у СВОЄМУ центрі у СВОЇ кабінети → OK;
  b) чужий центр → FORBIDDEN; c) кабінет поза room_ids → FORBIDDEN;
  d) чужий кейс (add_step/cancel) → FORBIDDEN; e) cancel після старту кроку → FORBIDDEN;
  f) персонал — поведінка без регресій (створення/кроки/скасування як було).
- Ревью субагентом (RLS/RPC — канон), tsc/lint/vitest, живий тест у Chrome
  (адмінське превʼю портала — ловушка: перевіряти під СПРАВЖНІМ направником,
  див. [[radflow-test-seed]]).

## 6. Відкриті питання (вирішити на старті сесії реалізації)

1. Чи бачить направник кейси, які центр створив по ЙОГО пацієнтах (не ним)?
   (План: ні — тільки свої; центр бачить усі.)
2. Правила скасування направником: до першого `in_progress` кроку чи тільки поки
   всі `scheduled`?
3. Реюз BookingModal у порталі vs дублювання кейс-бару в ReferralPortal
   (портал зараз — окрема форма; оцінити вартість реюзу на старті).
