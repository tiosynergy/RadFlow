> **Статус: план к реализации, код не написан.** Решения владельца: (1) услуги, созданные или
> импортированные для конкретного кабінета, принадлежат **только ему** («база данных услуг
> аппарата»); (2) базовый каталог — общий: AI‑импорт сам распознаёт модальности, и базовые услуги
> видны **всем** аппаратам соответствующей модальности; (3) модель — **nullable `room_id` в

## 1. Модель данных

- `services.room_id uuid NULL references rooms(id) on delete cascade`
  - `NULL` → **базовая** услуга центра: видна всем кабінетам своей модальности (наследование).
  - `= X` → услуга **кабінета X**: видна и бронируется только в нём.
- Кабінет «видит»: `(room_id IS NULL AND modality = room.modality) OR room_id = room.id`.
- `service_room_overrides` (0108) **остаётся** как механизм переозначить цену/время/скрыть
  **базовую** услугу в кабінете. Для room‑owned услуг оверрайды не нужны (цена и так своя).
  Гард `check_service_room_override` дополняется: запретить оверрайд на услугу с
  `room_id IS NOT NULL` (бессмысленно) — или разрешить только `room_id IS NULL`.
- Уникальность (0107 `services_clinic_mod_name_uniq (clinic_id, modality, lower(name))`)
  **пересобрать**:
  - `uniq (clinic_id, modality, lower(name)) WHERE room_id IS NULL` — база без дублей;
  - `uniq (clinic_id, room_id, modality, lower(name)) WHERE room_id IS NOT NULL` — в пределах
    кабінета без дублей; одинаковое имя в базе и в кабінете — ДОПУСТИМО (кабінетная переопределяет
    по смыслу отображения, см. §4 UI).
- Гард‑триггер (новый): `services.room_id` → `rooms.clinic_id = services.clinic_id` и
  `rooms.modality = services.modality` (симметрично гарду 0108).

**DB‑триггеры, зеркалящие TS (критично, правило проекта):**
- `check_studies_active_catalog` — валидирует состав исследований записи по активному каталогу.
  Должен принимать услугу, если она базовая ИЛИ принадлежит комнате записи. Запись без комнаты /
  перенос в другую комнату: room‑услуга чужой комнаты → отклонить (или каскадный вопрос — см. §6 Q2).
- `catalog_est_sum` ↔ `lib/catalog.ts` — суммы/длительности должны брать цену room‑услуги.
- Синхрон + smoke обязательны (правило HANDOVER).

## 3. Миграция 0120 (новая редакция, ЗАМЕНЯЕТ файл «база+оверрайд»)

Один файл `0120_services_room_owned.sql` (идемпотентный):
1. `alter table services add column if not exists room_id uuid null references rooms(id) on delete cascade;`
2. Пересборка уникальных индексов (drop старый 0107‑й, два новых partial — см. §1).
3. Гард‑триггер `check_service_room` (clinic+modality room↔service).
4. Дополнение `check_service_room_override`: только на базовые услуги.
5. Обновление `check_studies_active_catalog` (room‑видимость) — ДИФФ с `pg_get_functiondef` прод‑БД!
6. `services_import_rpc(p_rows jsonb, p_room_id uuid default null)`:
   - `p_room_id IS NULL` → база, канон 0119 бит‑в‑бит (upsert по partial‑индексу base).
   - `p_room_id = X` → **вставка/апдейт только room‑owned услуг кабінета X**
     (`on conflict (clinic_id, room_id, modality, lower(name))`), модальность ≠ кабінета → skip;
     БАЗА НЕ ТРОГАЕТСЯ вовсе. Оптимистичная блокировка 0119 применяется в границах room‑набора.
   - смена сигнатуры → drop(jsonb) + drop(jsonb,uuid) + create + re‑grant authenticated.
7. RLS: services уже clinic‑scoped; room_id не меняет границу изоляции (clinic та же) — политики
   не трогаем, но перепроверить referrer‑политики чтения услуг (портал).
**Применяет владелец вручную в SQL Editor. Ревью субагентом обязательно (RPC+триггеры).**

## 4. UI/UX (`ServicesEditor` + `ImportPriceModal` — поверх уже сделанных правок сессии 10)

- Режим кабінета показывает ДВЕ группы: «Послуги кабінета» (room_id=X, полноценный CRUD) и
  «Базові (успадковано)» (room_id IS NULL той же модальности; оверрайды 0108 как раньше).
- «＋ Додати» в кабінете → создаёт услугу с `room_id=X` (createService получает roomId; вместо
  пары createService+setRoomServiceOverride из прошлой итерации).
- «⇪ Імпорт прайса» в кабінете → уже фильтрует по модальности кабінета (сделано);
  меняется только серверный вызов — тот же `importServices(rows, roomId)` → RPC пишет room‑owned.
- База: AI‑импорт без изменений (все модальности, автораспознавание) → услуги базовые →
  автоматически «появляются» во всех кабінетах модальности (наследование = требование владельца).
- Бейджи в списке кабінета: «Кабінетна» vs «Базове»/«Змінено» (существующие).
