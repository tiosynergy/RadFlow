# Каталог услуг, цен и длительностей: n8n + AI + RadFlow

**Дата:** 2026-07-19  
**Статус:** архитектурный план, без внедрения  
**Цель:** создать управляемый каталог услуг, цен и длительностей для каждой клиники и каждого кабинета, интегрированный с очередью, листом ожидания, кросс-модальными кейсами, ролями и отчётностью RadFlow.

## 1. Целевой результат

RadFlow остаётся единственным источником истины по опубликованным услугам, ценам, длительностям и настройкам кабинетов. n8n и AI не меняют рабочие таблицы напрямую: они принимают источники, извлекают данные и готовят черновики. Публикацию выполняет только авторизованный администратор через защищённый RPC RadFlow.

```text
Файл / URL / ручной ввод
        ↓
n8n intake + хранение исходника
        ↓
Извлечение таблиц, текста и OCR
        ↓
AI-нормализация в строгий JSON
        ↓
Проверки и сопоставление в RadFlow
        ↓
Черновик изменений для администратора
        ↓
Атомарная публикация версии каталога
        ↓
Услуги → кабинеты → запись → очередь → кейсы → CEO-отчётность
        ↓
event_outbox → n8n → уведомления и журнал доставки
```

## 2. Принципы проектирования

1. **Multi-tenant isolation.** Все сущности каталога привязаны к `clinic_id`; RLS является обязательным рубежом изоляции.
2. **AI только предлагает.** Модель не публикует цены, длительности или изменения расписания самостоятельно.
3. **Версионность.** Изменения публикуются набором (`change set`), а не по одной строке без истории.
4. **Неизменяемые snapshots.** Запись в очереди хранит услугу, цену и длительность на момент бронирования. Новый прайс не меняет историю.
5. **DB-инварианты.** Совместимость «услуга ↔ модальность ↔ кабинет ↔ клиника» проверяется БД, а не только UI.
6. **Надёжная интеграция.** n8n получает события только через transactional outbox с идемпотентностью, retry и dead-letter состоянием.
7. **Минимизация данных.** В AI не передаются ПИИ пациентов и данные очереди; ему доступны только данные прайс-листа и справочника услуг.

## 3. Модель данных

### 3.1. Услуги клиники

`clinic_services`

| Поле | Назначение |
|---|---|
| `id` | Идентификатор услуги |
| `clinic_id` | Владелец услуги, tenant boundary |
| `code` | Стабильный внутренний код |
| `name` | Наименование услуги |
| `description` | Описание для персонала/портала |
| `modality` | `MRI`, `CT`, `US`, `XRAY`, `MAMMO`, `OTHER` |
| `study_types` | Связь с типами исследований RadFlow |
| `default_duration_min` | Типовая длительность процедуры |
| `default_buffer_min` | Типовой буфер |
| `base_price` | Базовая цена клиники |
| `currency` | Валюта |
| `status` | `draft`, `active`, `archived` |
| `source_version_id` | Версия импорта/каталога |
| `created_at`, `updated_at` | Аудит времени |

### 3.2. Настройка услуги для кабинета

`room_service_profiles`

| Поле | Назначение |
|---|---|
| `room_id` | Кабинет |
| `service_id` | Услуга клиники |
| `enabled` | Доступна ли услуга в кабинете |
| `duration_min` | Переопределение длительности для аппарата |
| `buffer_min` | Переопределение буфера |
| `price` | Переопределение цены |
| `slot_step_min` | Шаг отображения слотов, обычно 5 минут |
| `updated_by`, `updated_at` | Аудит изменения |

Приоритет настроек:

```text
room_service_profiles
        ↓
clinic_services
        ↓
clinic_modality_defaults
        ↓
глобальный шаблон RadFlow
```

### 3.3. Дефолты модальностей

`clinic_modality_defaults`

| Поле | Назначение |
|---|---|
| `clinic_id` | Клиника |
| `modality` | Модальность |
| `default_duration_min` | Типовая длительность |
| `default_buffer_min` | Буфер |
| `default_slot_step_min` | Шаг сетки |
| `default_services_template_version` | Версия шаблона услуг |

При старте нового кабинета RadFlow по его модальности создаёт набор `room_service_profiles` из активного шаблона клиники. Администратор затем может изменить цену, длительность и доступность отдельных услуг в кабинете.

### 3.4. Импорт, AI-черновики и версии

`catalog_imports`

- `id`, `clinic_id`;
- `source_type`: `excel`, `doc`, `pdf`, `url`, `manual`;
- `source_url`, `storage_path`, `source_hash`;
- `status`: `received`, `extracted`, `normalized`, `review_required`, `published`, `rejected`, `failed`;
- `created_by`, `started_at`, `completed_at`, `error_summary`.

`catalog_import_items`

- исходная строка, страница или HTML-фрагмент;
- AI-результат в JSON;
- нормализованное название;
- предполагаемая модальность, цена, валюта, длительность;
- `confidence`;
- `match_status`: `new`, `matched`, `ambiguous`, `invalid`;
- связь с существующей услугой;
- решение и комментарий администратора.

`catalog_versions` и `catalog_change_sets`

- версия опубликованного каталога;
- автор публикации;
- список добавлений, изменений, архивирований;
- причина, исходный импорт и timestamp;
- возможность безопасного отката новой версии без переписывания истории очереди.

## 4. Входящие сценарии

### 4.1. Excel, DOC и PDF

1. Администратор загружает файл в RadFlow.
2. Файл сохраняется в Supabase Storage, создаётся `catalog_import`.
3. n8n получает событие и извлекает таблицы/текст.
4. Для сканированных PDF запускается OCR.
5. AI формирует строго валидируемый JSON-черновик услуг.
6. RadFlow сопоставляет строки с существующими услугами и создаёт change set.
7. Администратор принимает, правит или отклоняет каждую строку.

### 4.2. Ссылка на сайт

1. Администратор указывает URL страницы услуг или прайс-листа.
2. n8n получает HTML, сохраняет snapshot и `source_hash`.
3. При повторной синхронизации создаётся diff, а не выполняется автоматическая перезапись каталога.
4. Если страница недоступна, предыдущая опубликованная версия остаётся действующей.

### 4.3. Ручное управление

Администратор может вручную:

- создать, архивировать или активировать услугу;
- изменить цену, длительность и буфер;
- включить услугу только в определённых кабинетах;
- сопоставить услугу с типом исследования;
- принять или отклонить AI-предложение;
- опубликовать или откатить change set.

Ручная правка создаёт новую версию каталога. Очередной импорт не должен перезаписывать её без явного подтверждения.

## 5. Контракт AI

AI используется только для извлечения и нормализации. Он не получает данные пациентов и не имеет доступа к рабочим таблицам очереди.

Пример контракта ответа:

```json
{
  "service_name": "МРТ головного мозга",
  "modality": "MRI",
  "study_types": ["МРТ"],
  "price": 3200,
  "currency": "UAH",
  "duration_min": 30,
  "confidence": 0.94,
  "source_fragment": "МРТ головного мозку — 3200 грн"
}
```

В обязательную ручную проверку отправляются строки, у которых:

- `confidence < 0.85`;
- не определена модальность;
- неизвестный тип исследования;
- цена или длительность равна нулю;
- конфликт с действующей услугой;
- одна услуга привязана к нескольким несовместимым модальностям.

## 6. Интеграция с User Flows RadFlow

### 6.1. Создание и перенос записи

Пользователь выбирает только активные услуги:

- своей клиники;
- совместимые с кабинетом и его модальностью;
- разрешённые его ролью и грантом доступа;
- совместимые с выбранными исследованиями.

В `queue_entries` сохраняется snapshot:

- `service_id`;
- `service_name_snapshot`;
- `price_snapshot`;
- `currency_snapshot`;
- `duration_snapshot`;
- `buffer_snapshot`;
- `catalog_version_id`.

`room_busy_slots`, slot picker, CAS, проверка графика, инциденты и collision logic используют snapshot длительности записи, а не новую настройку услуги из каталога.

Изменение услуги влияет только на новые записи. Массовый пересчёт будущих записей возможен лишь отдельным подтверждённым действием администратора с полной проверкой конфликтов.

### 6.2. Лист ожидания

`waitlist_entries` получает:

- `requested_service_ids`;
- предполагаемую длительность и буфер;
- версию каталога на момент добавления.

Подбор кандидата учитывает услугу, модальность, кабинет, длительность, желаемое окно, приоритет и фактическую доступность слота.

### 6.3. Кросс-модальные кейсы

Один `patient_case` состоит из нескольких `queue_entries`:

- один шаг — один кабинет и одна модальность;
- каждая услуга относится к конкретному шагу;
- MRI + УЗД — два разных слота в одном кейсе;
- цена и длительность каждого шага сохраняются отдельным snapshot;
- стоимость кейса — сумма snapshot цен его шагов.

Изменение прайса не должно менять цену уже созданного кейса или завершённого исследования.

### 6.4. Роли

| Роль | Возможности |
|---|---|
| Администратор | Импорт, ручное редактирование, публикация версий, настройка кабинетов, длительностей и цен |
| Регистратор | Выбор опубликованных услуг при записи, без изменения каталога |
| Радиолог | Просмотр назначенной услуги; предложение изменить типовую длительность, требующее утверждения администратора |
| Направитель | Только разрешённые услуги/модальности/кабинеты; публичная или договорная цена по политике клиники |
| CEO | Только аналитика и история цен, без изменения операционного каталога |

## 7. Надёжная интеграция n8n

n8n не получает прямые привилегии на запись в `clinic_services`, `room_service_profiles`, `queue_entries` или `patient_cases`.

```text
n8n → защищённый API/RPC RadFlow → import draft
RadFlow → event_outbox → n8n
```

Для каждого outbox-события необходимы:

- `event_id`;
- `clinic_id`;
- `event_type`;
- `payload_version`;
- `idempotency_key`;
- HMAC-подпись;
- `attempt_count`;
- `lease_until`;
- `last_error`;
- dead-letter статус.

События:

- `catalog.import.received`;
- `catalog.ai.normalized`;
- `catalog.review.required`;
- `catalog.version.published`;
- `catalog.service.changed`;
- `room.service-profile.changed`;
- `waitlist.candidate.matched`;
- `queue.booking.created`;
- `case.completed`.

Повторная доставка события не должна повторно изменять каталог. Нужны retry с backoff, lease для воркера и отдельный экран dead-letter ошибок.

## 8. DB-инварианты и безопасность

Обязательные гарантии БД:

1. Услуга, кабинет и профиль кабинета принадлежат одной клинике.
2. Модальность услуги соответствует модальности кабинета, если кабинет не `OTHER`.
3. Активная услуга не может быть удалена при наличии будущих записей; допустимо только архивирование.
4. Snapshot цены/длительности записи нельзя изменить прямым PostgREST PATCH.
5. Публикация каталога идёт только через `SECURITY DEFINER` RPC с явной авторизацией администратора.
6. AI-импорт не может публиковать каталог сам.
7. Направитель не видит внутренние цены, кабинеты и услуги вне гранта.
8. Все изменения каталога и настроек кабинета попадают в audit log.

## 9. План реализации

### Этап 1. Фундамент данных

1. Утвердить словарь `service code`, модальностей, валют и единиц длительности.
2. Создать таблицы каталога, профилей кабинетов, импортов, версий и change sets.
3. Добавить RLS, column-level privileges, DB-инварианты и audit log.
4. Обновить `supabase/types.ts`.
5. Подготовить SQL-smoke для tenant isolation, grants и совместимости услуги с кабинетом.

### Этап 2. Ручной каталог и старт кабинета

1. Экран администратора «Услуги и цены».
2. Экран настройки услуги в конкретном кабинете.
3. RPC и UI-инициализация дефолтных услуг при создании кабинета.
4. Версии, diff и безопасный откат публикации.
5. Проверка всех ролей и ограничений направителя.

### Этап 3. Очередь, лист ожидания и кейсы

1. Добавить выбор услуги в `BookingModal`, `ReferralPortal`, `WaitlistModal`.
2. Сохранять snapshots в `queue_entries`.
3. Интегрировать длительность услуги в slot picker, `room_busy_slots` и collision logic.
4. Добавить услуги в шаги кросс-модального кейса.
5. Добавить услуги и спрос в лист ожидания.

### Этап 4. n8n + AI intake

1. Защищённый endpoint приёма файлов/URL.
2. Supabase Storage, source hash и жизненный цикл импорта.
3. n8n-потоки Excel, DOC, PDF/OCR и URL.
4. AI extraction через строгую JSON schema.
5. Экран review: текущие значения, предлагаемые значения, confidence, источник и конфликт.
6. Публикация только после подтверждения администратора.

### Этап 5. Отчётность и автоматизация

1. CEO-аналитика по центру, кабинету, модальности и услуге.
2. Сравнение плановой и фактической длительности.
3. Автоматическое предложение кандидатов waitlist при освобождении слота.
4. Уведомления о смене прайса, конфликтах и failed imports.
5. Dead-letter dashboard для n8n.

## 10. Обязательный acceptance checklist

- Excel с несколькими листами, дублями и разными валютами.
- PDF-скан с OCR и ручной проверкой низкой confidence.
- URL, у которого изменилась цена после предыдущей синхронизации.
- Услуга неподходящей модальности для выбранного кабинета.
- Разные цены/длительности одной услуги в двух кабинетах.
- Изменение каталога при уже существующих записях и кейсах.
- Кейс MRI + УЗД с разными ценами и длительностями.
- Направитель с ограничением по модальности и кабинету.
- Два администратора, одновременно публикующие каталог.
- Повторная доставка n8n-события.
- Недоступность n8n, AI или сайта-источника.
- CEO-отчёт до и после изменения цены.
- Проверка, что snapshots исторических записей не изменились.
