RadFlow Integration API v1

Посібник інтегратора RIS/PACS · версія 1 · серпень 2026

RadFlow керує потоком пацієнтів у кабінетах МРТ/КТ: розклад, черга, фактичний стан кабінету. Цей API дає партнерській системі два робочі напрямки: читати розклад і записи та повідомляти факти руху пацієнта, щоб черга рухалась без участі реєстратора.

Межа продукту — головне, що варто знати одразу. RadFlow не є медичним продуктом: він не зберігає й не обробляє медичні дані. Канал не передає назовні й не приймає всередину персональні та клінічні відомості — ПІБ, телефон, дату народження, показання, протипоказання, висновки, зображення. Тіло вхідної події закрите переліком із чотирьох дозволених полів: усе інше відхиляється з 400. Пацієнта ваша система зіставляє на своєму боці за entry_id або accession.

Доступ

Ключ видає власник RadFlow. Ви отримуєте три речі: токен (секрет), базовий URL і цей документ.

Authorization: Bearer rfk_<48 hex>
  • Ключ прив'язаний до однієї клініки — доступ до чужих даних неможливий технічно, фільтр стоїть на сервері, а не в параметрах запиту.
  • Скоупи: appointments:read, slots:read, events:write. Бракує скоупа — 403.
  • Ліміт: 240 запитів за хвилину на ключ, далі 429.
  • Відкликання ключа миттєве: наступний запит отримає 401.
  • Усі відповіді — application/json; charset=utf-8, без кешування.

Перевірка доступу однією командою:

curl -H "Authorization: Bearer $RADFLOW_TOKEN" \
     https://rad-flow-tau.vercel.app/api/integrations/v1/rooms

Довідники

GET /api/integrations/v1/rooms

Кабінети клініки та її часова зона. Звідси беруться room_id для решти запитів. Вимкнені кабінети не віддаються (у них не можна записувати); ?include_inactive=1 покаже їх із active:false.

{
  "timezone": "Europe/Kiev",
  "paging": { "limit": 200, "returned": 2, "has_more": false },
  "rooms": [{ "room_id": "741157ae-…", "name": "Кабінет МРТ", "modality": "MRI",
              "apparatus_model": "Siemens Magnetom", "active": true }]
}

Часова зона повертається саме тут, бо всі часи у /slots — «стінні» (HH:MM за годинником клініки). Без зони їх не можна перетворити в абсолютний момент часу.

GET /api/integrations/v1/services

Каталог послуг зі стабільним кодом code — саме він призначений для HL7 AIS / FHIR serviceType і переживає перейменування послуги.

ПараметрФорматОпис
room_iduuid або base Що реально доступне в кабінеті: власні послуги кабінету + базові послуги тієї самої модальності. base — лише базові послуги клініки
include_inactive1Показати неактивні
limit1..500 (дефолт 200)Разом із paging.has_more

Порожній список — не помилка. Каталог і черга в RadFlow не зчеплені: реєстратор заводить запис із довільним переліком досліджень, навіть коли послуги в довіднику не заведені. Тому не блокуйте запис через порожній довідник — використовуйте code там, де він є. duration_min може бути null. Ціни не віддаються навмисно.

Розклад і вільні вікна

GET /api/integrations/v1/slots

Параметри: room_id (обов'язковий), date_from, date_to (YYYY-MM-DD, діапазон до 31 дня; дефолт — сьогодні + 13 днів). Відповідь по днях: робоче вікно, перерви, зайнятість і вільні інтервали (вікно мінус перерви мінус зайнятість).

{
  "room_id": "741157ae-…", "modality": "MRI", "timezone": "Europe/Kiev",
  "days": [{
    "date": "2026-08-12", "open": true,
    "window": { "start": "08:00", "end": "18:00" },
    "breaks": [{ "start": "13:00", "end": "14:00" }],
    "busy":   [{ "start": "10:30", "end": "11:05" }],
    "free":   [{ "start": "08:00", "end": "10:30" },
               { "start": "11:05", "end": "13:00" },
               { "start": "14:00", "end": "18:00" }]
  }]
}

open:false — кабінет цього дня не працює. Причини недоступності (інцидент, простій, ремонт) не розкриваються: назовні йде лише факт зайнятості.

{
  "appointments": [{
    "entry_id": "b1fbf2dc-…", "clinic_id": "c0aaaf36-…", "room_id": "741157ae-…",
    "status": "scheduled", "call_status": "confirmed",
    "scheduled_at": "2026-08-12T07:30:00+00:00",
    "scheduled_date": "2026-08-12", "scheduled_time": "10:30",
    "duration_min": 30, "buffer_time_min": 5,
    "priority_level": "planned", "cito": false, "has_contrast": true,
    "off_schedule": false, "case_id": null, "case_step": null,
    "created_at": "…", "updated_at": "…",
    "studies": [{ "type": "МРТ", "region": "Колінний суглоб", "contrast": true }]
  }],

}

Рекомендований цикл синку: запит із збереженим курсором → обробка сторінки → якщо has_more, повторити з paging.next → зберегти курсор останнього рядка. Сторінка завжди віддає повний поточний стан запису, тому обробка ідемпотентна: застосовуйте рядок, лише якщо його updated_at новіший за збережений для цього entry_id.

Події виконання (ваша система → RadFlow)

POST /api/integrations/v1/appointments/{entry_id}/events

{
  "event": "arrived",
  "source_event_id": "RIS-2026-08-12-000431",
  "at": "2026-08-12T10:31:00+03:00",
  "accession": "ACC-123"
}
ПолеОбов'язковеПравила
eventтак arrived → «Очікує», started → «Триває», finished → «Виконано»
source_event_idтак Ключ ідемпотентності, унікальний у межах клініки. Друковані ASCII, до 200 символів; керуючі символи відхиляються
atні ISO-8601 з часовою зоною (без зони — 400). Фактичний час події; для started лягає у відлік роботи кабінету
accessionні Accession number вашої системи; прив'язується до запису

Відповідь містить result, поточний і попередній статус, а також accession_bound, якщо передавали accession.

resultHTTPЩо сталося
applied200Статус змінено
duplicate200Цей source_event_id уже приймали — повтор безпечний
noop200Запис уже в цьому або пізнішому стані (застаріла подія)
conflict409Запис у стані поза ланцюжком (скасовано, неявка, не відбулося) — подія його не воскрешає
busy, rejected_busy409У кабінеті вже інший пацієнт
reused409Той самий source_event_id під іншу подію або інший запис — подія не застосована
rejected422Доменний гард (графік, перетин, заборонений перехід)
not_found404Запису немає або він іншої клініки

Втрачена подія не блокує наступну. Якщо ви надішлете finished, коли запис ще «Заплановано», RadFlow сам проведе його через «Очікує» і «Триває». Рух назад (подія нижча за поточний стан) — це noop, а не помилка.

Повтор із тим самим source_event_id безпечний. Дедуплікація на боці RadFlow: подія не застосується двічі. Але той самий ключ під іншу подію дасть reused — не використовуйте наскрізний лічильник, який може збігтися з чужим.

not_found не «з'їдає» ключ. Якщо ваша подія випередила появу запису в RadFlow, надішліть її пізніше з тим самим source_event_id — вона застосується.

Політика повторів

  • Повторювати (з backoff): 409, 429, 5xx — стан заважає зараз або збій тимчасовий.
  • Не повторювати: 400, 404, 413, 422 — це контракт або стан, який повтор не змінить. 404 варто повторити один раз пізніше, якщо запис ще міг не з'явитися.

Зворотний канал: вебхуки (RadFlow → ваша система)

Налаштовується на вимогу: один https-ендпоінт на клініку. Кожна зміна запису породжує POST із повним поточним станом (state-based, не diff).

ПодіяКоли
integration.appointment.createdзапис створено
integration.appointment.rescheduledзмінено час або кабінет
integration.appointment.cancelledскасовано / не відбулося
integration.appointment.noshowнеявка
integration.appointment.updatedінші зміни експортованих полів
integration.appointment.deletedзапис видалено

Вимоги до приймача — частина контракту:

  1. Дедуплікація за Idempotency-Key (заголовок і поле): доставка at-least-once, повтори законні.
  2. Порядок не гарантований. Застосовуйте подію, лише якщо її (updated_at, seq) новіша за збережену для цього entry_id. Поле seq існує саме тому, що дві зміни в одній транзакції мають однаковий updated_at.
  3. Перевірка підпису X-RadFlow-Signature: sha256=<hex> — HMAC-SHA256 від сирого тіла секретом вебхука, порівняння в константний час. Запити без валідного підпису відкидати.
  4. Відповідь 2xx протягом 3 секунд = прийнято; інакше повтор із backoff (30 с → … → 1 год, до 10 спроб, далі dead-letter).

Тексти помилок бази назовні не виходять: у відповіді — стабільний машинний reason (room_busy, stale, bad_request, domain_guard, illegal_transition, server_error) і прапорець retryable. Орієнтуйтесь на них, а не на текст.

Порядок підключення

  1. Отримати токен захищеним каналом і перевірити доступ запитом до /rooms (очікується 200 і список кабінетів).
  2. Забрати довідники: /rooms, /services. Зберегти room_id і code у себе.
  3. Налаштувати інкрементальний синк /appointments за keyset-курсором.
  4. Увімкнути надсилання подій. Почати з одного тестового запису й переконатись у послідовності applied → duplicate → noop.
  5. За потреби — узгодити з клінікою зворотні вебхуки й отримати секрет підпису.

Чого канал не робить. Через API не можна створити запис, перенести його, змінити пацієнта, послугу чи кабінет — планування лишається за реєстратором RadFlow. Ззовні рухається лише статус виконання вже наявного запису. Кожна така зміна видима адміністратору клініки в журналі дій із зазначенням назви вашої інтеграції як джерела.
