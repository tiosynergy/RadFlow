## 1. Что такое RadFlow

RadFlow — multi-tenant SaaS для **интеллектуального управления очередью** в центрах лучевой и функциональной диагностики (МРТ, КТ, УЗД, Рентген, Мамографія). Вся очередь, расписание, приоритеты, инциденты и пересчёт живут внутри RadFlow; Excel используется только для разовой загрузки справочников. Система — единственный источник правды по очереди клиники.

Каждая клиника (tenant) изолирована на уровне БД (PostgreSQL RLS по `clinic_id`). Несколько ролей работают над одной очередью одновременно, изменения распространяются в реальном времени.

## 2. Архитектура

| Слой | Решение |
|------|---------|
| Приложение | Next.js 15 (App Router), React 19, TypeScript, Tailwind |
| Данные/Auth | Supabase: PostgreSQL + Row Level Security + Auth |
| Реальное время | Supabase Realtime (`postgres_changes`) через единый хук `lib/useRealtimeRefetch.ts`: `setAuth` перед подпиской, потабличный дебаунс событий, поллинг с backoff **только при разрыве сокета**, плюс обновление по `visibility/focus` |
| Мутации | Server Actions (`app/queue/actions.ts`, `"use server"`) — статус/отмена/завершение/обзвон/инциденты/перенос/бронь/направление/графики. Серверная сессия + единая обработка ошибок, `clinic_id` выводится на сервере; RLS остаётся defense-in-depth. Переходы статуса — **CAS-оптимистичная блокировка** (`expectedFrom`: обновление проходит только если статус в БД совпадает с ожидаемым — защита от гонок при параллельной работе ролей). Классификация ошибок БД по **SQLSTATE** (`classifyError`) |
| Привилегии | Сервер-роуты (`app/api/*`) и Server Actions проверяют роль/доступ через единый `requireRole()`-хелпер, при необходимости используют service-role клиент (`lib/supabase/admin.ts`) |
| Клиенты Supabase | Все типизированы `<Database>` (`@supabase/ssr@0.12`): `client.ts` (браузер, anon), `server.ts` (SSR, anon+cookies), `admin.ts` (service-role), `middleware.ts` (рефреш сессии) |
| Таймзона | **Универсальная** (пользователи по всему миру): у каждой клиники своя IANA-`clinics.timezone`; сравнения «зараз vs слот» на сервере считаются по ней, клиент — через `wallNow(tz)`/`setClinicTz` (`lib/incidents.ts`). Модель «настінний-час-як-UTC» (0035) без изменений — TZ нужна лишь чтобы получить «текущий настінний момент зоны клиники» |
| Доставка событий (Stage 2) | Транзакционный **outbox** (`event_outbox` + HMAC + idempotency-key, миграция 0055) для надёжной отправки в n8n |
| Хостинг | Vercel (авто-деплой из `main`; **Hobby-план** — cron-джобы только суточные); миграции применяются вручную в Supabase |

Дальше серверные страницы разводят по роли.

## 3. Роли и доступ

Enum `user_role`: `admin`, `radiologist`, `registrar`, `referrer`, `ceo`.

| Роль | Доступ | Стартовый экран |
|------|--------|-----------------|
| **admin** | Полный: настройка клиники (включая каталог послуг/прайс и резервне копіювання), доска, call-list, лист очікування, инциденты, персонал, направители, CEO-дашборд, **журнал дій** (`/journal`, §4.16), пошук (`/search`) | `/queue` |
| **registrar** | Регистратура: доска очереди, call-list, лист очікування, пошук (`/search`). Журнал дій и настройки центра — нет | `/queue` |
| **radiologist** | Только «Моя черга» по назначенным кабинетам (нужен `approved=true` + ≥1 кабинет) | `/radiologist` |
| **referrer** | Глобальный аккаунт направляющего врача (`clinic_id = NULL`), доступ к центрам через `referral_access` | `/referral` |
| **ceo** | CEO-дашборд по аналитике; **глобальный кросс-клиничный аккаунт** — членство в центрах через `ceo_access`, грант выдаётся поверх любой роли (роль не меняется) | `/ceo` |

> **Глобальные аккаунты** (`referrer`, `ceo`) имеют `clinic_id = NULL`; их членство в клиниках хранится в access-таблицах (`referral_access`, `ceo_access`) — строка на пару (пользователь, клиника) со статусом. Один пользователь может держать роль И дополнительный CEO-грант (напр. радиолог, который также CEO) — роль при этом не меняется. Security-definer хелперы изоляции: `auth_referrer_clinics()`, `auth_can_refer()`, `auth_ceo_clinics()`, `auth_is_ceo_of()`.

## 4. Модули и сценарии

### 4.1. Регистрация клиники и онбординг

- **`/register`** — администратор регистрирует клинику: `supabase.auth.signUp` с метаданными (login, phone, clinic_name). Триггер `handle_new_user` создаёт клинику и профиль-администратора. Валидация пароля: ≥8 символов, ≥1 заглавная, ≥1 цифра. (Соц-кнопки — демонстрационные заглушки.)
- **`/setup`** (Setup Wizard, admin) — реквизиты центра (название, **город из справочника КАТОТТГ** — `CitySelect` + RPC `search_cities`, ~29.7 тыс. населённых пунктов; адрес, телефоны, email), данные администратора, и **оборудование/кабинеты** с графиком работы по дням: индивидуальные часы + **несколько перерывов** (на весь тиждень и/или свои для каждого дня — `rooms.schedule.breaks[]`, редактор с добавлением/удалением и валидацией интервалов; старый одиночный обед мигрируется автоматически). Сохранение: инкрементальный upsert/delete кабинетов **по id** (не delete-all — чтобы не осиротить записи и доступы радиологов). После настройки выставляется `clinics.configured_at`; до этого все рабочие экраны редиректят на `/setup`. Кнопка **«Зберегти»** доступна на всех вкладках мастера (общий `save()` пишет профиль+оборудование; вкладки-менеджеры Радіологи/Направники/CEO сохраняют действия сразу). Выход — единственная кнопка **«Вийти»** (возврат на `/queue`) с предупреждением о несохранённых изменениях (`dirty`).

### 4.2. Аутентификация и приглашения

- **`/login`** — вход по **логину или email** + паролю. Если введён логин (без `@`), email резолвится через RPC `email_for_login`, затем `signInWithPassword`. Параметр `?redirect=` санитизирован (только внутренние пути).
- **Флоу приглашения сотрудника (radiologist/referrer/ceo):** администратор создаёт аккаунт (service-role, без пароля, `password_set=false`, генерируется **одноразовый `invite_token`**) → передаёт человеку персональную ссылку `/set-password?token=…`.
- **`/set-password`** + `/api/account/set-password`: `GET` резолвит токен в логин/ПИБ (показывает, для какого аккаунта вход), `POST` задаёт пароль — **только при валидном токене и `password_set=false`**; после успеха `password_set=true`, а `invite_token` гасится (миграция 0032, CRIT-1: токен подтверждает владение, переиспользование ссылки исключено).
- **Сброс пароля админом** (`POST /api/staff/password`): авторизует радиолога по `clinic_id`, CEO — по активному `ceo_access`, направителя — по активному `referral_access`; генерирует новый одноразовый токен для повторной установки.

### 4.3. Доска очереди (`/queue`, `QueueBoard.tsx`) — admin/registrar

Главный экран. Возможности:

- **Статусы записи** (`queue_status`): `scheduled` (В черзі) → `waiting` (Очікує) → `in_progress` (В кабінеті) → `done` (Виконано); терминальные `no_show` (Неявка), `not_held` (Не відбулося), `cancelled` (Скасовано). Производный визуальный статус «⚠ Уточнити» — когда время прошло, а пациент не продвинут (`needsClarification`). **Авто-порядок:** просроченные `scheduled` автоматически помечаются в БД (`clarify_at`) и опускаются вниз очереди — доски вызывают RPC `sink_overdue_scheduled` (по своей клинике) на каждом reload; есть и headless-бэкстоп `/api/queue/sink-overdue` → `sink_overdue_scheduled_all` (защищён `CRON_SECRET`, для ручного/n8n-вызова).
- **Прогресс-степпер** в строке: клик по шагу меняет статус через общий guard `setStatusGuarded` (переход в `in_progress` проходит проверки: **запись сегодняшнего дня** — нельзя «завести» пациента из другого дня в кабинет сейчас (`wrong_day`); кабинет не в простое, не закрыт по графику, не занят другим пациентом; **фактическое окно** «зараз + тривалість + буфер» не налазит на следующий активный запис кабинета — `lateCallClash` в `lib/queueStatus.ts`; и само исследование «зараз + тривалість» помещается **до конца рабочего графика кабинета**). Единый источник правил — `computeCallBlock()` (коды `wrong_day`/`room_blocked`/`room_closed`/`room_busy`/`room_stuck`/`stuck_unknown`/`sched_overrun`/`next_day`/`clash`; `next_day` — окно вызова уходит за полночь, а доска грузит ровно одни сутки → подтверждение, не блок). Если вызов невозможен — кнопка «Викликати в кабінет» **неактивна заранее** с инлайн-причиной (не только тост по клику; `startBlockReason` из `inProgressBlockReason`). Те же guard'ы синхронизированы у радиолога.
- **Слоты по графику кабинета** (`lib/schedule.ts` + `lib/slots.ts`): эффективный график = дефолт (Пн–Сб 08–18) или override (праздники/особые часы/закрытие). **Шаг выбора слота — 5 мин** (`SLOT_STEP`); клинические длительности исследований не менялись. Единый компонент `components/SlotPicker.tsx`: в строке 4 получасовых слота, каждый разбит на 6 пятиминуток (00/05/10/15/20/25), строк столько, чтобы покрыть график. Цвета пятиминуток: **красная заливка** — идёт само исследование; **красная штриховка** — буфер после него (кабинет ещё занят уборкой/переукладкой) — так видно, когда исследование реально заканчивается; **оранжевые** — не вмещается (`tight`); **серая штриховка** — перерыв кабинета (`.slot.brk`); прошедшие — приглушены. При выборе слота **зелёные границы** — начало и конец планируемого исследования, **зелёная штриховка** — его буфер (когда кабинет освободится). Чипы «Зайнятий час» показывают `13:25–14:35 +5 хв`; **тултип занятой пятиминутки** (`lib/slotBusy.ts`) показывает интервал, а для **админа и радиолога** — ещё статус, ФИО пациента и перечень исследований (гейт в RPC, миграция 0062). Сетка **живая**: `useRoomBusy` подписан на `queue_entries`/`incidents` через `useRealtimeRefetch`, и если выбранный слот заняли, пока модалка открыта, выбор снимается с предупреждением «Слот щойно зайняли». Если занятость не загрузилась — сетка **не показывается** вовсе (пустой день выглядел бы как «всё свободно»); при выборе слота **зелёным** подсвечиваются пятиминутки начала и конца планируемого исследования. В шапке — **«вміщується ще N»** (`countFit`: жадная укладка с учётом длительности и буфера — реальная ёмкость дня, а не число стартовых позиций, которые перекрываются).
  **Важно:** БД от шага сетки не зависит — `check_no_overlap` работает на `tstzrange`, а `room_busy_slots` отдаёт сырые интервалы. Переход 30 → 5 мин **миграций не потребовал**, запрет двойной брони сохраняется.
- **Перерывы кабинета** вычитаются из сетки — слот, чьё исследование пересекает перерыв, недоступен. В сетке это **два разных состояния**: слот **внутри** перерыва → `break` (серая штриховка, тултип «Перерва в роботі кабінету · 13:00–14:00»), слот рабочий, но исследование **заедет** в перерыв → `tight` (оранжевый, «не вміщується … перетне перерву 13:00–14:00»). Хелперы `inBreak()` / `breakClash()` в `lib/schedule.ts`. Источник перерывов даёт `effectiveRoomBreaks(date, roomId, roomSchedule, override)`: если на эту **дату** есть override кабинета — перерывы берутся из него (пусто = без перерывов), иначе базовые из `rooms.schedule.breaks[]` (Setup Wizard). Enforcement во всех сетках слотов (запись/перенос/портал направителя) и в ограничении длительности `StudyEditModal`.
- **Запись пациента** (`BookingModal`): ПИБ, дата рождения, пол, вес, возраст, телефон, email; тип (МРТ/КТ), контраст, противопоказания, CITO; область исследования из справочника (`lib/studies.ts`), длительность, **буферное время** (5/10/15 хв, дефолт 5 — занятость кабинета после исследования) и цена; несколько исследований; врач-направитель (+`AddDoctorModal`). Перед вставкой — повторная проверка коллизии слота. Пишет `studies` и `studies_original` (для последующего diff).
- **Редактирование исследований** (`StudyEditModal`): тип фиксируется кабинетом, суммарная длительность ограничена окном до следующей записи / конца графика / **ближайшего перерыва даты** (`effectiveRoomBreaks`) / **ближайшего простоя кабинета** (U-15, с48: `incidentDurNotice` в `lib/incidents.ts` — зеркало серверного `check_not_during_incident`, который проверяет ВЕСЬ интервал исследования и висит на `update of … duration_min`). Если старт записи уже внутри окна простоя, длительность не спасает вообще: экран показывает баннер «🔧 Кабінет у простої … до HH:MM», «Зберегти» неактивна, сетка красит окно простоя, а совет — перенести запись (кнопка переноса рядом с той, из которой открыто окно). Если простой впереди — он называется как граница: «Доступно у слоті: N хв (до простою о HH:MM)». **Выход за график** (после закрытия / в перерыв) персонал может подтвердить галочкой «Підтверджую роботу поза графіком» (grace 120 мин, U-20); простой этой галочкой НЕ снимается — сервер отклоняет его отдельным триггером. Направителю галочка не показывается никогда (правило 0077 проверяет роль раньше согласия) — вместо неё честный отказ. У каждого исследования — чекбокс **«Контраст»** (МРТ и КТ): даёт +15 мин (`CONTRAST_DUR`) к длительности и доплату (`CONTRAST_SURCHARGE`) к цене. Контраст читается из записи и пишется обратно вместе с `price`; сервер выводит `has_contrast` из `studies`. Буфер (0/5/10/15) правится тут же. Доступен админу/регистратору (доска, колл-лист) и направителю (портал).
- **Перенос** (`RescheduleModal`): кабинеты той же модальности, выбор даты/слота, статус сбрасывается в `scheduled`, опциональное поле **«Причина»**. Перенос записи, которая **уже идёт** (`in_progress`), **разрешён**: исследование останавливается (status → `scheduled`, `in_progress_at` обнуляется — чтобы запись не «занимала» кабинет по старой метке старта), переносится **та же запись** (не копия), в снимке фиксируется `from_status='in_progress'`. `no_show`/`not_held` — тоже переносимы. Сетка слотов гейтится состоянием загрузки (не мигает «все свободно» до ответа `room_busy_slots`). При переносе пишется снимок **`reschedule_origin`** (jsonb: откуда — дата/час/кабінет/центр/статус + причина); на новом слоте в раскрытой строке — бейдж «🔁 Перенесено з …».
- **Накладення (коллизия очереди)** (`collisionFor` в `lib/queueStatus.ts` + `components/CollisionPanel.tsx`): идущее исследование затянулось и наезжает на следующую запись кабинета. Занятость считается от **фактического** старта (`in_progress_at`, 0060) и не может «закончиться в прошлом» (если «Завершити» не нажали, пациент всё ещё в кабинете). Две зоны: **drift** — кабинет отстаёт от плана, но до слота Б успевает → тихий серый бейдж «+N хв», решать нечего (буфер для этого и есть); **clash** — не успевает → красный бейдж «⚠ Накладення» + **панель решения** в раскрытой строке. Панель считается только у **ближайшей** активной записи кабинета; записи в «Запізненні» пропускаются — у них своя панель. Действия: **«Перенести на HH:MM»** (`firstFittingSlot` в `lib/slots.ts` — первый слот, куда запись влезает целиком: длительность+буфер, мимо чужой занятости, перерывов, простоев и конца графика → **каскад не возникает по построению**), **параллельный кабинет** той же модальности (показывается, только если освободится раньше), **«В обзвін»** (`call_status='to_recall'` → колл-лист), **«Змінити вручну»** (`RescheduleModal`). Продуктовые правила (решение владельца): двигаем **только следующую запись**, а не хвост дня; **за конец графика никого не выталкиваем** — кто не влезает до закрытия, идёт в обзвон. Миграций не потребовалось.
- **Жизненный цикл статусов** (те же правила синхронно на доске и у радиолога): откат «Виконано» → **«↩ В чергу»** (в `scheduled`, без автозапуска); прямая отметка **«✓ Виконано»** в панели решення для просроченных записей (start+тривалість ≤ зараз — вернуть ошибочно снятое завершение); кнопки **«✕ Неявка»/«✕ Не відбулося»** неактивны **до времени начала исследования** и активируются постфактум («Скасувати запис» доступна всегда).
- **Редактирование данных пациента** (`PatientEditModal`, клик по имени): обязательные поля те же, что при новой записи — ПІБ, Телефон, Дата народження, Стать; правит данные + примітку + приоритет (admin / направитель-владелец). `StudyEditModal` показывает мягкое предупреждение, если запись сегодня и по факту (старт уже прошёл) исследование+буфер перекроют следующую запись.
- **Инциденты** (`BreakdownModal`, `lib/incidents.ts`): две сущности — 🔧 **Поломка** (обычно «сейчас», `active`) и ⚙️ **ТО** (планируется, `planned`). Блокировка до `blocked_until` или «до восстановления». Флаг `auto_unblock` определяет судьбу записей после окна. Просроченные инциденты снимаются. Пострадавшие записи попадают в панель переноса и в call-list. **Форма редактирования длительности тоже знает о простоях** (U-15, с48) — до с48 не знала вообще и обещала время, которое сервер отклонял. ⚠️ Тонкость, стоившая дефекта: серверный гард фильтрует инциденты по **статусу** (`active`/`planned`), а не по тому, прошло ли `blocked_until`; статус снимает крон `resolve-expired-incidents` раз в 5 минут. Поэтому формам, которые **пишут** `queue_entries`, нужен фид без клиентского фильтра `incidentExpired` (в `QueueBoard` это `writeIncidentsFeed`), а «заблокирован ли кабинет ПРЯМО СЕЙЧАС» (вызовы, карточки, баннеры) считается по `liveIncidents`. Одна и та же таблица отвечает на два разных вопроса. Если кабинет заблокирован аварийной остановкой, `BreakdownModal` показывает баннер «🛑 Аварійна зупинка» с кнопкой «Розблокувати».
- **Аварійна зупинка** (кнопка-тумблер внизу «Швидкі дії», `EmergencyModal`, серверные `emergencyStop`/`resolveEmergency`): блокирует работу одного/нескольких/всех кабинетов до з'ясування обставин (инцидент `reason='emergency'`, «до восстановления»). На виде «Усі кабінети» — модалка с выбором кабинетов (по умолчанию ничего не выбрано); на конкретном кабинете — мгновенный тумблер этого кабинета через подтверждение. Пострадавших **этого дня** (активные записи) метит `call_status='to_recall'` (всплывают в Колл-листе), пациента `in_progress` → `not_held`, шлёт событие в **n8n** (`N8N_WEBHOOK_URL`, событие `emergency_stop` со списком пострадавших — best-effort). Остановленные кабинеты подсвечиваются красным в сайдбаре. Запись направителю в остановленный кабинет блокируется существующим механизмом инцидентов.
- **Направитель записи**: в строке показывается «Напр.: {имя}» — берётся из аккаунта направителя (`referrer_id` → `profiles.full_name`, фолбэк на текстовое поле `doctor`).
- **Атрибуция правок исследований**: если состав исследований изменён относительно `studies_original`, у метки «Дослідження» выводится «змінено {клінікою|направником}» по автору последней правки (`studies_changed_by`, миграция 0052) — клиника и направитель видят изменения друг друга, синхронно (realtime). «⚠ Протипоказання» показывается на уровне метки «Дослідження» во всех досках.
- **Завершение** (`CompletionModal`): «Успішно» → `done` либо «Не відбулось» → `not_held` с обязательной причиной.
- **Запізнення** (derived, `lib/queueStatus.ts` → `isLate`/`LATE_META`): пациент не пришёл (статус `scheduled`) и от начала слота прошло больше `buffer_time_min`. В БД статус не меняется — вычисляется на лету и виден всем ролям (доска, радиолог, портал направителя). Прямой вызов в кабинет **блокируется** (кнопка + степпер + guard `setStatusGuarded`); в карточке — панель решения: «↩ Все ж прийшов» (возврат в живую очередь), «🗓 Перенести», «⏳ В лист очікування» (пациент копируется в лист, запись автоматически становится `not_held` — слот освобождается), «✕ Не відбулося». Отдельная карточка-счётчик «Запізнення» в StatsBar (кликабельный фильтр); «Не відбулося» остаётся чистым терминальным итогом. Та же формула пойдёт в n8n/AI-автоматизацию (Stage 2).
- **Приоритет пациента** (`priority_level`): обязательный выбор при записи (CITO / Терміново / Планово). **Порядок доски (решение владельца 2026-07-11): статус → просроченные вниз → ВРЕМЯ → приоритет (тай-брейк на одинаковое время).** Раньше приоритет стоял выше времени — доска не читалась как расписание дня, и перенос записи визуально «не двигал» строку. Теперь CITO/Терміново — это **бейдж** (плюс баннер CITO вверху), а не подъём наверх. То же правило синхронно у радиолога и в выборе «Наступний у черзі». Менять приоритет существующей записи может админ (инлайн в строке + в модалке пациента) и направитель-владелец (портал); реестратор/радиолог — только просмотр (enforced в `setQueuePriority` + DB-триггер `guard_priority_change`). Бейджи: CITO (красный), Терміново (оранжевый), Планово — без бейджа.
- **Связь с листом очікування** (§4.6): после отмены/відмови всплывает подсказка «Слот звільнився» с подходящими кандидатами из листа; из панели «Скасовані + Неявка» пациента можно отправить «⏳ В лист очікування».
- **Realtime**: подписка на `queue_entries`, `incidents`, `schedule_overrides` через `useRealtimeRefetch` (поллинг только при разрыве сокета), перезапрос при смене дня; живые таймеры. Все мутации доски — через Server Actions.
- **Режим роботи на дату** (`ScheduleEditModal`, `schedule_overrides`): закрыть всю клинику (свято/выходной) или задать по каждому кабинету «Працює / Інші години / Зачинено». В режиме «Інші години» — редактор **перерывов на эту дату** (добавить/удалить, валидация начало < конец); хранятся в `schedule_overrides.rooms[roomId].breaks[]` (JSONB, миграции не нужны) и вычитаются из сеток слотов через `effectiveRoomBreaks`. Записи в закрытом кабинете становятся «пострадавшими»: бейдж «✎ Перезапис» и панель «Обзвін через простій» с переносом в один клик.
- Фильтры по статусу (карточки StatsBar), поиск, мини-календарь с отметками особого графика.

### 4.4. Кабинет радиолога (`/radiologist`, `RadiologistBoard.tsx`)

Личный экран радиолога у аппарата. Видит исследования **только назначенных кабинетов** (`radiologist_rooms`); требует `approved=true`. **С 0136/0137 это правило держит БД, а не только UI** (RF-01 внешнего аудита): `queue_entries` и `waitlist_entries` радиолог читает только по своим кабинетам, `patient_cases` — только если у кейса есть шаг в его кабинете, запись в вейтлист и кейсы ему запрещена; RLS + BEFORE-триггеры `a00_*` ловят и прямой PostgREST, и любой SECURITY DEFINER RPC. Администратор видит все кабинеты. Тот же поток статусов и те же guard-проверки вызова, что на доске. Карточки кабинетов с текущим пациентом и **живым таймером** (метка входа `in_progress_at`, не сбрасывается при правках записи), кнопка «Викликати наступного» (CITO в приоритете), завершение процедуры, заметки радиолога. Опоздавшие (derived «Запізнення») помечаются бейджем, их прямой вызов заблокирован — решение за регистратурой. **Логика вызова синхронизирована с админ-доской**: `inProgressBlockReason` радиолога включает проверку конца рабочего графика кабинета + `lateCallClash`, кнопки «Викликати в кабінет»/«Викликати наступного» неактивны заранее с причиной. Доступны «↩ В чергу» для «Виконано» и гейтинг «Неявка»/«Не відбулося» до времени старта (как на доске). В сайдбаре — только «Моя черга» (пункт «Дошка черги» убран: для радиолога `/queue` редиректит обратно на `/radiologist`). Синхронизация с основной очередью в реальном времени.

### 4.5. Call List (`/call-list`, `CallListBoard.tsx`) — admin/registrar

Список обзвона на выбранную дату (по умолчанию завтра). Только `scheduled`/`waiting`. Статусы звонка (`call_status`): `not_called`, `confirmed`, `to_recall`, `no_answer`, `declined` — с приоритетной сортировкой, фильтр-пиллами и поиском. Заметки к звонку, кнопки набора (`tel:`), «Всіх підтверджено», экспорт CSV. Отдельная секция **обзвона пострадавших от простоя** и секция **«Запізнення сьогодні»** (независимо от выбранной даты): обзвон опоздавших сверх буфера — перенос на слот, в лист очікування (запись → `not_held`), передзвонити, відмова. Отказ (`declined`) скасовує запис (как на доске) — после отказа всплывает подсказка кандидатов из листа очікування на освободившийся слот (§4.6). Realtime-синхронизация.

### 4.6. Лист очікування (`/waitlist`, `WaitlistBoard.tsx`) — admin/registrar (+вкладка у направителя)

Пациенты, ожидающие свободного окна (слота); ссылка в сайдбаре под Колл-листом с **live-счётчиком** (realtime). Отдельная таблица `waitlist_entries` — сущность спроектирована машинно-читаемой под будущую автоматизацию n8n/AI (Stage 2).

- **Запись листа**: данные пациента (инлайн, как в очереди), состав исследований (`studies` jsonb, основное + дополнительные), `duration_min` + `buffer_time_min`, `modality` (выводится из исследований на сервере), `priority_level` (тот же enum), **бажане вікно** для подбора слота: `desired_date_from/to` (date) + `desired_time_from/to` (time; UI-пресеты Ранок 08–12 / День 12–16 / Вечір 16–20 / Будь-який — `TIME_PRESETS` в `lib/waitlist.ts`), заметка. Связи с очередью: `source_entry_id` (добавлен из существующей записи) и `scheduled_entry_id` (созданная бронь при переносе).
- **Жизненный цикл** (`waitlist_status`): `waiting` → `scheduled` (перенесён в слот) / `cancelled` (снят, можно вернуть) / `expired` (окно прошло; ставит будущая автоматизация). Вкладки Очікують/Записані/Зняті, поиск, счётчики; сортировка waiting: cito → urgent → planned, затем по давности.
- **Перенос в слот**: кнопка «Записати» открывает стандартную `BookingModal` с полным предзаполнением (`BookingPrefill`); после успеха строка автоматически получает `scheduled` + ссылку на бронь. **Подсказка кандидатов**: после отмены/відмови на доске или в call-list всплывает «Слот звільнився» (`WaitlistCandidatesModal`) с подходящими пациентами (матчинг `waitlistMatchesSlot`: дата в диапазоне, время в окне, модальность кабинета; слоты в прошлом не предлагаются) — запись в один клик, освободившийся кабинет/дата/время уже предвыбраны в форме.
- **Обратное направление**: «⏳ В лист очікування» из панели «Скасовані + Неявка» на доске копирует пациента в лист (`addEntryToWaitlist`); дубль блокируется unique-индексом (`waitlist_source_waiting_uniq`).
- **Карточка — место принятия решения**: раскрытие строки показывает детали; смена приоритета (admin / направитель-владелец — те же правила, что в очереди: app-check + DB-триггер `guard_priority_change` на таблице листа), «✎ Редагувати» — полное редактирование пациента/исследований (включая тип и мультиисследования)/окна/заметки (`WaitlistModal` в режиме edit; серверный `updateWaitlistEntry` с allowlist полей), запись в слот, снятие.
- **Опциональная привязка к кабинету** (`waitlist_entries.room_id`, миграция 0051): запись листа можно жёстко привязать к конкретному аппарату (селектор «Кабінет» в `WaitlistModal`, админ-флоу) — тогда подбор кандидатов ограничен этим кабинетом; пусто = любой кабинет нужной модальности (как раньше). Мультитенант-целостность гарантирует триггер `guard_waitlist_room` (кабинет принадлежит центру строки).
- **Фильтр по кабинету** из сайдбара — через модальность выбранного кабинета; баннер с «Зняти фільтр».
- **Направитель** — вкладка «Лист очікування» в портале: только свои пациенты (`created_by`), добавление с обязательным выбором центра (server-check активного `referral_access`), редактирование/приоритет/снятие своих записей.
- **RLS** — зеркало политик очереди: персонал — все строки своего центра; направитель — только свои в авторизованных центрах; CEO — read-only авторизованных центров. Realtime (`REPLICA IDENTITY FULL`, публикация) — мгновенная синхронизация листа между всеми ролями. Мутации — Server Actions (`app/waitlist/actions.ts`).

### 4.7. Портал направляющего врача (`/referral`, `ReferralPortal.tsx`)

Глобальный аккаунт врача с доступом к нескольким центрам через `referral_access`. **Интерфейс перестроен под доску администратора**: левый сайдбар (`ReferrerSidebar`) со списком своих центров и их **авторизованным** оборудованием (кабинеты фильтруются по `referral_access.room_ids` — как форма записи и БД-гейт; клик по кабинету/центру = быстрый фильтр доски «Мої направлення», клик «Мої направлення» сбрасывает на все) + навигация «Швидкі дії» (Нове направлення / Мої направлення / Лист очікування / Мої центри / Мій профіль); контент в раскладке `.app`/`.main`.

- **Нове направлення**: выбор центра (только активные), модальность ограничена кабинетами центра и подмножеством `room_ids` из гранта; тип/область/длительность; занятость кабинета — через **обезличенный** RPC `room_busy_slots` (без ПИИ чужих пациентов); сетка слотов; вставка записи (RLS `queue_write_referrer` гарантирует `created_by = auth.uid()` и наличие доступа).
- **Мої направлення** (`ReferrerBoard.tsx`): доска-очередь в стиле админской (те же классы `qrow`/`stats`) — переключатель центров + агрегат «Всі центри», stat-карточки-фильтры статусов (Усі/Очікує/В роботі/Виконано/Не відбулося/Неявка/Скасовано), фильтр по кабинету/дате (выпадающий список кабинетов ограничен `room_ids` гранта), поиск. **Статус исследования и статус обзвона — только чтение** (направитель видит, но не меняет; UI + DB-гарды 0048). В раскрытой строке — действия в месте решения по своим записям: **направитель правит запись в двух случаях — (1) он её автор (`created_by`), либо (2) администратор указал его направителем (`referrer_id`)** (RLS-политика `queue_write_referrer` + миграция 0057). Действия: перенос, редагування дослідження (в рамках авторизованных центров/оборудования), данные пациента, приоритет, примітки, скасування; чужие записи центра — только просмотр. Diff исследований с **атрибуцией автора** правки («змінено клінікою/направником» по `studies_changed_by`, миграция 0052 — обе стороны видят изменения друг друга, синхронно), «⚠ Протипоказання» на уровне метки «Дослідження», бейдж «🔁 Перенесено з …». Календарь справа — общий компонент `MiniCalendar` (как у админа), фильтры-статусы в одну строку. Сетки слотов переноса/редактора берут занятость через обезличенный `room_busy_slots` (с `p_exclude`, миграция 0050) — уже не RLS-слепы к чужим записям.
- **Лист очікування**: свои пациенты, ожидающие свободного окна в центрах (см. §4.6) — добавление с выбором центра, редактирование, приоритет, снятие.
- **Мої центри**: поиск центров (`search_clinics`), запрос доступа, приём/отклонение приглашений, отзыв доступа.
- Realtime по своим записям и грантам через `useRealtimeRefetch`. Создание/перенос/отмена направлений — через Server Actions (`createReferralBooking` на сервере проверяет активный `referral_access` и допустимый кабинет).

### 4.13. Кросс-модальний кейс — кілька кабінетів/модальностей за один візит (`patient_cases`)

«Кейс» — коли одному пацієнту за **один візит** потрібні **РІЗНІ кабінети/модальності** (напр. МРТ + УЗД), і записи мають бути узгоджені між собою (пацієнт не може бути у двох кабінетах одночасно). Два дослідження в ОДНОМУ кабінеті — це звичайна мультизапис (кілька `studies` в одному записі черги), **не** кейс.

- **Сутність**: таблиця `patient_cases` (снимок пацієнта + `status` enum `case_status`, прапорець `sequential`, `referrer_id`/`created_by`, нотатка). Записи черги-«кроки» посилаються на неї через `queue_entries.case_id` + `case_step` (порядок кроку). RLS по `clinic_id`; realtime — по фільтру `case_id=eq.<uuid>` (усі ролі бачать зміни кейса миттєво).
- **Створення** (`create_case_rpc`): ≥2 кроки з **різними** `room_id`. Промоушн однієї наявної записи черги в кейс — `case_from_entry_rpc` («🔗 Організувати кейс» у ⋯-меню запису без `case_id`, `status='open'`): існуючий запис стає кроком 1, додається крок 2.
- **Редагування** — `CaseModal` (місце прийняття рішення по кейсу): покроково «🩻 Дослідження» / «🗓 Перенести» / «＋ Додати крок»; час слота показано діапазоном (початок–кінець). Додавання кроку/модальності — той самий `BookingModal`, що й нова запис, у режимі add-to-case: сітка підсвічує **cyan-штриховкою** (`casebusy`) час, зайнятий іншими кроками кейса, і блокує кабінет, уже присутній у кейсі. `add_case_step_rpc` / `cancel_case_rpc`.
- **Інваріанти в БД** (тригери `SECURITY DEFINER`, останній рубіж поверх server-гардів): `check_case_clinic_match` (усі кроки одного центру), `check_case_distinct_room` (кабінети кроків різні — `CASE_SAME_ROOM`, `23505`), `check_case_no_time_overlap` (пацієнт не в двох кабінетах одночасно — напіввідкритий `tsrange '[)'`, дотик вікон ≠ перетин), плюс попарний `CASE_PATIENT_OVERLAP` (`23P01`) у `create_case_rpc`. ⚠️ Тригери `check_case_*` сортуються алфавітно **до** `trg_a_set_scheduled_at` (0035), тож рахують вікна з `scheduled_date+scheduled_time` напряму (а `scheduled_time` — колонка `text`, тому вікно будується text-конкатенацією timestamp, hotfix 0099).
- **Server Actions** — `app/queue/actions.ts`: `createCase` / `caseFromEntry` / `addCaseStep` / `cancelCase`; мапінг доменних помилок (`CASE_SAME_ROOM` / `CASE_PATIENT_OVERLAP`) у чисті тости.

### 4.14. Каталог послуг та цін (Stage 2, `/services` + `services`/`service_room_overrides`)

Кожен центр веде **свій каталог послуг**: назва, модальність, тривалість, ціна, доплата за контраст, активність. Модель — **центр = база (`services`, 0107) + шар переозначень ПО КАБІНЕТУ (`service_room_overrides`, 0108)**: кабінет без override успадковує базу; override задає свою ціну/тривалість/контраст або **ховає** послугу в цьому кабінеті (`active=false`).

- **Редактор** — екран `/services` (admin) і вбудований у крок Майстра «Послуги та прайс» `ServicesEditor` (режими «Базовий каталог» / «Кабінет N»). Server Actions `app/services/actions.ts` (+ `setRoomServiceOverride`/`clearRoomServiceOverride`).
- **Резолвер `lib/catalog.ts buildCatalog(services, overridesToMap(roomOverrides))`** — ЄДИНА точка читання каталогу у формах запису (`regionsFor`/`regionInfo`/`studyDur`/`studyPrice` з тими ж сигнатурами, що статичні в `lib/studies`, + `roomId` для override). **Модальність без жодної послуги → фолбэк на статику** (легасі-центр); модальність налаштована, але всі позиції вимкнені → напрям закрито (форми не дадуть створити запис). Ціна фіксується знімком у `queue_entries.studies[].price` у момент запису.
- **Realtime (0111):** `services`/`service_room_overrides` у публікації → правка каталогу адміном одразу оновлює відкриті форми/дошки; вибрана закрита область/контраст знімається у модалці.
- **Захист цілісності (0112/0113):** прикладний гейт `firstClosedService` (у Server Actions) + **DB-рубіж** `check_studies_active_catalog` на `queue_entries`/`waitlist_entries` (останній рубіж проти прямого Data API: не можна записати пацієнта на вимкнену/приховану послугу; grandfather лише при незмінному кабінеті — перенос у кабінет зі скритою послугою закрито).
- **CEO-дохід по каталогу (0114):** `ceo_kpi_studies.catalog_est_sum` оцінює позиції без знімка ціни за каталогом центру («чистий каталог»: активна послуга з `price>0`, +контраст; інакше 0).
- **Фаза 3 (реалізовано):** імпорт прайсів із файлів (`.xlsx` / `.csv` — детермінований розбір; `.pdf` / `.docx` — AI) та з URL через n8n → передперегляд → upsert у `services` через SECURITY DEFINER RPC. Ліміт файла 4 МБ; фото прайса не приймаються (прибрано 2026-07-29). План — `docs/plan/SERVICES_CATALOG.md`.

### 4.15. Резервне дзеркало черги в Google Calendar (0160/0161)

Один закритий secondary-календар Google **на клініку** з останньою успішно синхронізованою чергою — аварійне читання на випадок недоступності RadFlow. Дані течуть ЛИШЕ RadFlow → Google; зворотної синхронізації немає і не буде (вона обійшла б CAS, гарди БД і ролі). Це **не** бекап БД і **не** другий master. RPO ≈ 2–5 хв (тик планувальника), вікно «вчора … +7 днів», ретеншн подій 14 днів, heartbeat-подія «копія актуальна на HH:MM» зверху дня. Деталі — `docs/GOOGLE_CALENDAR_BACKUP.md`.

- **БД:** `google_calendar_connections` (PK `clinic_id`, 1 рядок = 1 центр) + `google_oauth_states` (одноразовий state, sha256 + PKCE, TTL 10 хв, single-use). **Refresh-токен — у Vault** (скоуп `gcal:`), у `public`-таблицях його немає ніколи; видалення підключення тягне видалення секрета тригером.
- **CHECK-інваріанти fail-closed:** `gcal_status_chk` — рівно пʼять статусів (`not_connected`, `connected_no_calendar`, `ready`, `reauth_required`, `access_lost`); `gcal_enabled_invariant_chk` — `enabled` можливий ЛИШЕ при `status='ready'` + календар + секрет + `access_role in ('writer','owner')`; `gcal_last_error_chk` — вісім кодів помилки.
- **Планувальник:** pg_cron `gcal-backup-sync` кожні 2 хв → `net.http_post` на `/api/integrations/google-calendar/sync-all` із Bearer `CRON_SECRET` (секрет у Vault, у тілі джоба його немає). Клієнтських токенів немає взагалі.
- **UI:** `/setup` → секція «Резервне копіювання» (`GoogleCalendarBackupSettings.tsx`), лише admin. Роутів вісім: `start`, `callback`, `calendars`, `select`, `enable`, `status`, `disconnect`, `sync-all`.
- ⚠️ **Названа властивість, через яку дзеркало вмирає щотижня (I-7, с69).** Поки OAuth-застосунок у Google має статус **`Testing`**, refresh-токен живе **рівно 7 діб** — заміряно двічі по `important_events` (26.08 12:55:54 → `reauth_required` 02.09 12:56:03; 27.08 11:16:36 → 03.09 11:18:01). Лікує лише публікація consent screen — пункт **П-3** у [`ToDo_Production.md`](audit/ToDo_Production.md).
- ⚠️ **І клас дефекту, який на цьому знайшли.** Перевірка №13 фільтрувала `where g.enabled`, а `gcal_enabled_invariant_chk` ЗОБОВʼЯЗУЄ будь-який шлях відмови зняти `enabled` — тобто несправність сама прибирала рядок із поля зору сторожа, і дзеркало пролежало мертвим 11,5 доби при `ok:true`. Закрито міграцією **0194** (друга гілка №13, без часового порогу — рішення власника Р69-3). Питання, яке тепер ставиться до КОЖНОГО гарда: **чи може поле, за яким він фільтрує, пережити саму несправність, яку він стежить?**

### 4.16. Журнал важливих подій (`/journal`) і позначки непрочитаного

Дві різні сутності з однієї родини: **журнал** (що сталося в центрі) і **позначки** (що з цього ще не бачив конкретний користувач).

- **`/journal`** — «Журнал дій», **лише адміністратор центру** (радіолога веде на `/radiologist`, направника на `/referral`, решту на `/queue`); SSR готує лише довідники фільтрів, область даних рахує `/api/journal` із сесії. Таблиця `important_events`: `event_type` формату `домен.подія` (regex + ≤ 64 символів), вісім типів сутностей, актор із роллю (включно з `system`).
- ⚠️ **PII у журнал не пускає БД, а не домовленість:** CHECK `important_events_no_pii_chk` забороняє ключі `patient_name`/`patient_phone`/`patient_email`/`patient_dob`/`studies`/`note`/… у `details`. Той самий CHECK стоїть на позначках (`ucm_no_pii_chk`).
- **Позначки** (`user_change_markers`, 0131–0134 + 0138): рядок на пару «отримувач × поверхня» — десять поверхонь (`queue`, `waitlist`, `services`, `schedule`, `rooms`, `referrals`, `cases`, `staff`, `centers`, `incidents`), `severity` `info`/`important`/`critical`, `field_scope` з одинадцяти значень, `subject_date` (крапки на календарі). `ucm_actor_not_recipient_chk` — власна дія НІКОЛИ не позначає тебе самого. Правило аудиторії 0138: «немає поверхні для ack — немає позначки». Семантика гасіння — заморозка знімка (`lib/ackVisibility.ts`, `lib/useUnreadChanges.tsx`, `components/UnreadDot.tsx`); деталі — `docs/UNREAD_CHANGES.md`.
- **Стоп-кран без міграції:** `update public.change_marker_settings set enabled = false;`
- **Ретеншн:** pg_cron `prune-important-events` (180 днів) і `prune-change-markers` (погашені позначки).

### 4.17. Інтеграції з RIS/PACS: API v1, FHIR R4, вебхуки

Читальний контракт для зовнішніх систем плюс канал статусів виконання. **Режим A (за замовчуванням): персональних даних пацієнта назовні не йде** — лише операційні поля (час, кабінет, послуга, статуси); матчинг пацієнта на боці RIS за непрозорим `entry_id`/accession. Контракти — `docs/integration-api-v1.md`, `docs/integration-fhir-r4.md`; рунбук ключів — `docs/integration-keys-runbook.md`.

- **Ключі** (`integration_keys`): `Authorization: Bearer rfk_<48hex>`, у БД лише sha256 (`^[0-9a-f]{64}$`), ключ прибитий до ОДНОГО центру, скоупи ⊆ `slots:read`/`appointments:read`/`events:write` (порожні = ключ без прав, fail-closed), `export_mode` A/B, ліміт 240 запитів/хв, відкликання = `revoked_at` + `active=false`, **не** `delete`. Deny-all RLS: таблицю бачить лише серверний шар. Видача — `node scripts/integration-admin.mjs key:create`, секрет показується один раз.
- **API v1:** `GET /api/integrations/v1/{slots,appointments,rooms,services}` + `POST /api/integrations/v1/appointments/[id]/events`. Інкрементальний синк — keyset-курсор `updated_since` + `after_id`; offset-пагінації немає НАВМИСНО (рухливий `updated_at` губив би рядки).
- **FHIR R4** — **read-only фасад** над тими самими таблицями: `/fhir/R4/metadata` (CapabilityStatement), `Location`, `HealthcareService`, `Schedule`, `Slot`, `Appointment` (read + search). Ресурс `Patient` фасад не публікує взагалі. Розбіжність між двома каналами була б дефектом, а не варіантом. ⚠️ Відкрите: **I-6** — `406` немає, `Accept`/`_format` ігноруються (блокер формальної сертифікації, не безпеки).
- **Вхід і посилання:** `inbound_events` — ідемпотентність RIS→RadFlow, дедуп `(clinic_id, source_event_id)`, append-only, сирого payload немає (лише sha256); `external_refs` — зовнішні ідентифікатори (accession) ↔ сутності RadFlow, поліморфні, лише upsert.
- **Вихід:** `integration_webhooks` (ендпоінт центру для подій `integration.*`, кожен POST підписано HMAC-SHA256) доставляється через транзакційний `event_outbox` і pg_cron `outbox-deliver` (щохвилини). Вимикання = `enabled=false`, не `delete`.

### 4.18. Універсальний пошук (`/search`)

Один пошук для всіх пʼяти ролей по **всій історії та майбутніх записах** черги й листа очікування, плюс швидка фільтрація вже завантаженого дня без мережі. Етап 1 — **детермінований, без LLM** (архітектура готова до AI, але LangChain/OpenAI не підключені й не підключаються без окремого рішення власника). ⚠️ **Область даних рахує СЕРВЕР із сесії** (`resolveSearchScope` у `POST /api/search`), а не SSR-пропси сторінки: підміна пропсів область не розширює. `requireRole(null)` + ліміт 60 запитів/хв на користувача (`rl_check`). Деталі — `docs/SEARCH.md`.

### 4.19. Видалення клініки на запит адміністратора

`clinic_deletion_requests` — заявка з `token_hash`, знімком `counts` і `expires_at`. Виконання — **лише** RPC `clinic_deletion_execute` з токеном із листа (`/api/clinic/delete-request` → `/api/clinic/delete-confirm`). Виконані рядки лишаються **вічним слідом**, а не зникають разом із центром.

### 4.20. Нічне обслуговування і сторож інваріантів

**`public.invariants_check(boolean)`** — одна plpgsql-функція (~134 КБ) із **25** названими перевірками: від цілісності леджера (№7 `ledger_md5`) і простроченої синхронізації дзеркала (№13) до дайджестів політик (№16), тригерів (№17), **тіл функцій** (№19 — 40 підписей), грантів (№22), форми схеми (№23), auth-акаунтів без профілю (№24) і **власного тіла сторожа** (№25 `guard_self_pin` — звірка з піном у коментарі до функції; до 0198 тіло сторожа не тримало НІЩО). Нічний прогін пише РЕЗУЛЬТАТ у `maintenance_runs`: `cron.job_run_details` показує лише факт виконання SQL, а не його висновок.

Десять активних задач pg_cron (замір 14.09; реєстр — `docs/ops-cron.md`, це **живий** документ, прибитий тестами):

| джоб | розклад (UTC) | що робить |
|---|---|---|
| `outbox-deliver` | щохвилини | доставка `event_outbox` → вебхуки / n8n |
| `gcal-backup-sync` | кожні 2 хв | синк дзеркала черги в Google Calendar |
| `sink-overdue` | кожні 5 хв | `sink_overdue_scheduled_all()` — просрочені `scheduled` вниз черги |
| `resolve-expired-incidents` | кожні 5 хв | знімає простої, у яких минув `blocked_until` |
| `prune-rate-limits` | щогодини | чистка `rate_limits` (старше доби) |
| `prune-important-events` | 03:20 | ретеншн журналу (180 днів) |
| `prune-change-markers` | 03:25 | чистка погашених позначок |
| `prune-outbox` | 03:30 | `outbox_retention_daily()` |
| `audit-retention` | 03:40 | `audit_log_retention_daily()` |
| `invariants` | 03:50 | `invariants_check()` — сторож |

⚠️ **`resolve-expired-incidents` — не косметика.** Серверні гарди фільтрують простої за СТАТУСОМ, а не за тим, чи минув `blocked_until`; статус знімає саме цей джоб. Тому форми, що ПИШУТЬ у `queue_entries`, читають фід без клієнтського фільтра «протух», а «чи заблокований кабінет ПРЯМО ЗАРАЗ» рахується окремо (§4.3).

## 5. Статусы и справочники

- **`queue_status`**: `scheduled`, `waiting`, `in_progress`, `done`, `no_show`, `not_held`, `cancelled`, **`needs_reschedule`** (политика задержки очереди, 0078–0081 — метка «требует переноса»; замер `pg_enum` 14.09 — до этой правки метки в документе не было).
- **`call_status`**: `not_called`, `to_recall`, `no_answer`, `confirmed`, `declined`.
- **`modality`**: `MRI`, `CT`, `US` (УЗД), `XRAY` (Рентген), `MAMMO` (Мамографія), `OTHER`. Реестр (код↔укр.метка↔цвет↔каталог областей) — `lib/studies.ts` (`MODALITIES`, `BOOKABLE_MODALITIES` = все кроме OTHER). Booking-флоу работает на N модальностей. Инвариант «тип исследования ↔ модальность кабинета» держат триггеры `check_studies_match_room` (queue, 0088) и `check_waitlist_consistency` (лист ожидания, 0090).
- **`referral_access_status`**: `pending_clinic`, `pending_referrer`, `active`, `revoked`, `declined`.
- **`referral_policy`**: `direct` (запись сразу), `confirm` (требует подтверждения).
- **`patient_priority`** (enum): `cito` (екстрено/CITO), `urgent` (терміново), `planned` (планово). Обязателен при новой записи; порядок очереди: cito → urgent → planned. Машинно-читаемые коды для n8n/AI (`lib/priority.ts`).
- **`waitlist_status`** (enum): `waiting` (очікує вікна), `scheduled` (перенесено у слот), `cancelled` (знято), `expired` (вікно минуло). Машинно-читаемые коды для n8n/AI (`lib/waitlist.ts`).
- **`case_status`** (enum): `open` (кейс активний), `completed` (усі кроки виконано), `cancelled` (скасовано). Стан кросс-модального кейса (`patient_cases`, §4.13).
- **`ceo_access_status`**: `active`, `revoked`.
- **`incidents.status`** (text): `active`, `planned`, `resolved`.
- **`google_calendar_connections.status`** (text + CHECK `gcal_status_chk`, §4.15): `not_connected`, `connected_no_calendar`, `ready`, `reauth_required`, `access_lost`. Коды ошибки (`last_error_code`): `reauth_required`, `access_lost`, `rate_limited`, `google_unavailable`, `network`, `partial_snapshot`, `config_missing`, `sync_failed`.
- **`clinics.timezone`** (text + CHECK `clinics_timezone_chk`, миграция **0192**): `Europe/Kyiv`, `Europe/Kiev`, `UTC`. ⚠️ `Europe/Kiev` — legacy-алиас, он живёт в проде и держит фазу 2 таймзон (см. §8).
- **`clinics.queue_delay_policy`** (text + CHECK): `manual`, `cascade_shift`, `reschedule_conflicts`; рядом `overlap_threshold_min` (5…120, кратно 5) и `max_cascade_patients` (1…100) — политика задержки очереди (0078–0081).
- **Позначки непрочитаного** (§4.16): `severity` `info`/`important`/`critical`; десять поверхностей `surface_key`; одиннадцать `field_scope`. **`integration_keys.scopes`** ⊆ `slots:read`, `appointments:read`, `events:write`; `export_mode` `A`/`B` (§4.17).

**Ключевые ограничения и логика:**

- `check_no_overlap` (триггер + advisory-lock) — запрет двойной брони по времени; занятость слота считается как `duration_min + buffer_time_min` (буфер после исследования); `cancelled/no_show/not_held` освобождают слот. Для записи `in_progress` занятость кабинета считается по **фактическому** окну старта (`in_progress_at + тривалість + буфер`), а не по плановому слоту (миграция 0060 — `room_busy_slots`/`check_no_overlap`; TZ-валидация зоны через `pg_timezone_names`). Проверка простоя (`check_not_during_incident`) буфер НЕ учитывает — по чистой длительности.
- Частичный unique-индекс — один `in_progress` на кабинет; один `active`-инцидент на кабинет.
- `check_not_during_incident` — запрет записи в окно простоя.
- **Гарды направителя** (миграция 0048, триггеры `guard_call_status_change` / `guard_status_change_referrer`): пользователь `role='referrer'` не может менять `call_status`, а `status` — только `scheduled`/`cancelled` из `scheduled`/`waiting` (перенос/отмена своей записи; нельзя продвигать «В роботі/Виконано/Неявка»). Админ/персонал/service-role не затронуты. Вместе с `guard_priority_change` (0046) и `guard_referrer_doctor` (0036) — защита на уровне БД поверх RLS.
- `auth_clinic_id()`, `auth_is_admin()`, `auth_is_referrer()`, `auth_referrer_clinics()`, `auth_can_refer()`, `auth_ceo_clinics()`, `auth_is_ceo_of()` — security-definer хелперы для RLS.
- RLS-чтение профилей для глобальных пользователей — отдельными permissive-политиками (`profiles_referrer_linked_read` / `profiles_ceo_linked_read`), каждая с role-guard (`role='referrer'` / `role='ceo'`) как осознанная граница изоляции (админу нельзя прочитать полный профиль/`invite_token` чужой роли только по факту гранта).
