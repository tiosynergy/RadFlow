# Ключи интеграций: выдача, передача, отзыв

Инструкция для владельца RadFlow. Все команды выполняются **локально**, из корня
проекта, в обычном терминале (PowerShell, VS Code). Нужен `.env.local` с
`NEXT_PUBLIC_SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` — сервисный ключ никуда,
кроме самого Supabase, не уходит.

Админ-UI для ключей нет и не планируется: выдача редкая, а единственный канал
проще держать под контролем, чем экран в интерфейсе.

---

## 1. Выдать доступ партнёру

```powershell
cd D:\RadFlowDev
node scripts/integration-admin.mjs partner:onboard `
  --clinic <uuid клиники> `
  --name "RIS Мед-Експерт"
```

Одна команда делает всё: создаёт ключ со скоупами
`appointments:read, slots:read, events:write`, режим A, и печатает **два
раздельных блока**.

| Блок | Что с ним делать |
|---|---|
| `=== СЕКРЕТИ ===` | Токен уходит **в буфер обмена**, на экране только маска. Сразу вставить в менеджер паролей |
| `=== ПАМ'ЯТКА ПАРТНЕРУ ===` | Скопировать с экрана и переслать. Секретов в ней нет |

Если у партнёра уже есть адрес для обратных вебхуков, добавьте
`--url https://адрес.партнёра/hook` — команда заодно заведёт вебхук и покажет
секрет подписи (он печатается на экран: в буфер класть нельзя, затёр бы токен).

Полезные ключи:

- `--base https://другой-домен` — если проверяете против превью-деплоя;
- `--scopes appointments:read,slots:read` — доступ только на чтение, без
  права двигать статусы;
- `--show` — напечатать токен на экран (когда вставлять из буфера некуда);
- `--allow-redirect` — разрешить вывод в файл или пайп. **Только для
  автоматизации**, вручную не использовать.

Имя из `--name` попадает в журнал действий клиники как источник изменений —
пишите так, чтобы администратор понял, кто двигал запись: «RIS Мед-Експерт», а
не «test1».

---

## 2. Передать партнёру

Партнёру нужны ровно три вещи:

1. **Токен** `rfk_…` — отдельным защищённым каналом;
2. **Базовый URL** — `https://rad-flow-tau.vercel.app`;
3. **Документ** — `RadFlow-Integration-API-v1.pdf` или памятка из вывода команды.

**Токен и документ отправляются разными сообщениями.** Не потому, что документ
секретный, а потому что письмо с полезным содержимым пересылают дальше, цитируют
и складывают в задачи — и токен едет вместе с ним.

Годится: менеджер паролей с общей записью, мессенджер со сквозным шифрованием,
телефонный звонок для второй половины строки. Не годится: письмо вместе с
памяткой, тикет, задача в трекере, чат с ботами, скриншот терминала.

---

## 3. Проверить, что канал работает

Сразу после выдачи, до того как партнёр начнёт настройку:

```powershell
$env:RADFLOW_TOKEN="вставить_токен_из_менеджера_паролей"
node scripts/integration-live-check.mjs --base https://rad-flow-tau.vercel.app
```

Режим только чтения: 41 проверка (REST v1 + FHIR-фасад), ничего не меняет.
Ожидается `LIVE_OK`.

Две из них (с42) сверяют **содержание** `/slots` с БД: `busy` за самый
занятый день кабинета должен совпадать с объединением строк
`room_busy_slots` под `service_role`. Для этого нужен
`SUPABASE_SERVICE_ROLE_KEY` в `.env.local` — то есть запуск с машины
владельца; без ключа зонд печатает `skip` (не `ok`). Именно эту проверку не
хватало в с36: `39/39 LIVE_OK` при том, что `/slots` отдавал занятое как
свободное (C-2 аудита 23.08, закрыто 0156).

### ⚠️ Буфер обмена затирается копированием самой инструкции

`partner:onboard` кладёт токен в буфер и предупреждает «вставьте сразу».
Неочевидная часть: буфер перезаписывает **любое** копирование — в том числе
когда вы выделяете и копируете команды из этого файла, чтобы вставить их в
консоль. `Get-Clipboard` тогда вернёт текст команд вместо токена, а токен
будет потерян безвозвратно (в базе только sha256).

Порядок, который это переживает:

1. выполнить `partner:onboard`;
2. **набрать руками**, не копируя: `$env:RADFLOW_TOKEN = Get-Clipboard`;
3. убедиться, не показывая секрет: `$env:RADFLOW_TOKEN.Length` → `52`;
4. дальше копировать что угодно — токен уже в переменной.

Потеряли — не страшно: `key:revoke --id <uuid>` и выпустить заново.
Перевыпуск ничего не стоит, а вот попытки «вспомнить» токен стоят инцидента.

После прогона уберите переменную: `Remove-Item Env:\RADFLOW_TOKEN`.

### Отдельный ключ для проверки

Если проверяете канал до передачи партнёру — заводите **отдельный** ключ с
именем вида «LIVE-CHECK» и отзывайте его сразу после прогона. Партнёрский
ключ при этом остаётся с пустым `last_used_at`, и первое его срабатывание
будет означать, что подключился именно партнёр, а не вы. Этот признак
теряется навсегда, если прогнать проверку партнёрским ключом.

Полная проверка с движением статусов требует тестовой записи:

```powershell
node scripts/integration-live-check.mjs `
  --base https://rad-flow-tau.vercel.app `
  --entry <uuid тестовой записи> --yes
```

Заведите запись на будущую дату с именем вида «ТЕСТ ІНТЕГРАЦІЇ», прогоните
проверку и отмените её: скрипт доводит запись до статуса «Виконано».

## 4. Посмотреть, что выдано

```powershell
node scripts/integration-admin.mjs list --clinic <uuid клиники>
```

Показывает все ключи клиники: id, префикс, имя, скоупы, активен или отозван,
и **когда ключом пользовались в последний раз**. Последняя колонка — самая
полезная: `(не використовувався)` у ключа недельной давности означает, что
партнёр до интеграции так и не дошёл, а не что всё работает молча.

---

## 5. Отозвать

```powershell
node scripts/integration-admin.mjs key:revoke --id <uuid ключа>
```

Действует мгновенно: следующий запрос партнёра получит `401`. Уже переданные
данные это не отменяет и статусы, проставленные через API, не откатывает — это
обычные переходы очереди, сделанные легально.

Вебхук отключается отдельно:

```powershell
node scripts/integration-admin.mjs webhook:disable --clinic <uuid клиники>
```

---

## 6. Плановая ротация (без простоя у партнёра)

Порядок именно такой — иначе интеграция ляжет между шагами:

1. выпустить **новый** ключ (`partner:onboard`, имя с пометкой даты);
2. передать партнёру, дождаться подтверждения, что он переключился;
3. убедиться по `list`, что у нового ключа появилось «останнє звернення»;
4. только теперь отозвать старый.

Оба ключа какое-то время живут одновременно — это нормально и безопаснее, чем
окно недоступности.

## 7. Если токен утёк

Утечка — это не только публикация. Токен считается скомпрометированным, если он
попал в переписку, в тикет, в скриншот, в лог, в репозиторий или в чат с ИИ.

**Порядок действий:**

1. Отозвать ключ **немедленно** — до разбирательств, до уточнений:
   `key:revoke --id <uuid>`.
2. Проверить `list`: пользовались ли ключом и когда. Колонка «останнє звернення»
   покажет, успел ли кто-то им воспользоваться.
3. Если ключ успел поработать — посмотреть, что он делал:
   ```sql
   select source_event_id, event_type, result, processed_at
   from inbound_events
   where integration_key_id = '<uuid ключа>'
   order by id desc limit 50;
   ```
4. Выпустить новый и передать партнёру заново.

Перевыпуск ничего не стоит и ничего не ломает: данные, уже полученные партнёром,
остаются у него, статусы в RadFlow не откатываются. Колебаться незачем —
отзывайте сразу.

**Если токен попал в git публичного репозитория**, отзыв обязателен и
достаточен. Чистить историю бессмысленно: GitHub отдаёт объекты по хешу коммита
даже после force-push, а страницу мог забрать индекс или чужой форк. Защита
здесь одна — мёртвый ключ.

## Три предохранителя в CLI

Они появились не из теории. 11.08.2026 токен за один день трижды прошёл через
посторонний канал: сначала вывод команды сохранили в `Integration_KEY.txt`
рядом с проектом и файл уехал в публичный репозиторий, потом вывод дважды
вставили в переписку. Все ключи были отозваны, ни один не успел сработать.

1. **Токен уходит в буфер обмена**, а не на экран. Переслать то, чего на экране
   нет, невозможно — это работает без участия человека, в отличие от
   предупреждений.
2. **Перенаправленный вывод обрывается**. `node … > file.txt` завершается кодом
   3 ещё до печати секрета и подсказывает отозвать уже созданный ключ.
3. **`.gitignore` ловит дампы по имени** — `*KEY*.txt`, `*secret*.txt`,
   `*token*.txt`, `integration-key*`, `webhook-secret*`.

Все три обходятся сознательно (`--show`, `--allow-redirect`, `git add -f`).
Это допустимо, когда вы понимаете, зачем; но по умолчанию правильный путь —
буфер обмена и менеджер паролей.

## Что хранится в базе

Токена в базе **нет** — только `sha256` от него и первые 12 символов для
опознания в списке. Восстановить потерянный токен невозможно ни из базы, ни из
логов: единственный путь — отозвать и выпустить новый.

Секрет подписи вебхука хранится открытым текстом (иначе нечем подписывать
исходящие запросы) в таблице с deny-all RLS: доступ к нему есть только у
серверного кода.
