## Разрешённые звуковые события

### 1. Пациент готов к вызову

Короткий спокойный сигнал только при реальном переходе:

`scheduled → waiting`

Семантика RadFlow: пациент уже пришёл и ожидает вызова.

Получатели:

- `admin` — записи текущей клиники;
- `registrar` — записи текущей клиники;
- `radiologist` — только записи назначенных ему кабинетов.

Ограничения:

- только записи сегодняшнего дня по таймзоне клиники;
- не воспроизводить для направителя и CEO;
- не воспроизводить при создании новой записи со статусом `scheduled`;
- не воспроизводить при первой загрузке, смене даты, refresh, focus или reconnect;
- если пользователь сам только что перевёл пациента в `waiting` через оптимистичное обновление текущей доски, повторный realtime-refetch не должен дать звук.

### 2. Критическое вмешательство

Отдельный, более заметный, но короткий сигнал при одном из событий:

- новый инцидент стал фактически активным;
- плановый инцидент дошёл до `started_at` и стал активным;
- запись впервые перешла в `needs_reschedule`;
- для направителя: его собственная запись впервые перешла в `needs_reschedule` или `not_held`.

Получатели:

- `admin` и `registrar` — активные инциденты своей клиники и записи своей клиники в `needs_reschedule`;
- `radiologist` — только инциденты и записи назначенных ему кабинетов;
- `referrer` — только собственные направления, перешедшие в `needs_reschedule` или `not_held`;
- `ceo` — никаких звуков.

`breakdown`, `maintenance` и `emergency` используют один критический звук. Не создавай отдельный звук для аварийной остановки.

Инцидент со статусом `planned` не должен звучать до фактического начала. Используй существующие функции времени из `lib/incidents.ts`, включая таймзону клиники.

## Что не озвучивать

Звуков не должно быть для:

- создания обычной записи в очереди;
- `in_progress`;
- `done`;
- `cancelled`;
- `no_show`;
- обычного переноса;
- добавления или изменения waitlist;
- `call_status`;
- производных состояний `Запізнення` и `Уточнити`;
- завершения или снятия инцидента;
- изменения кабинета, графика, каталога или цены;
- загрузки и обновления CEO-дашборда.

`Запізнення` и `Уточнити` вычисляются по времени и обновляются таймерами. Их озвучивание создало бы повторные и трудно дедуплицируемые сигналы — сознательно не реализовывать.

## Управление звуком

Добавь один переиспользуемый переключатель звука для ролей, которые могут получать события:

- admin/registrar — в существующий `Sidebar`;
- radiologist — в сайдбар рабочего места радиолога;
- referrer — в `ReferrerSidebar`;
- CEO — переключатель не показывать.

Украинский UI:

- `Увімкнути звукові сповіщення`;
- `Вимкнути звукові сповіщення`;
- при необходимости: `Браузер заблокував звук — натисніть ще раз`.

Требования:

- по умолчанию звук выключен;
- включается только явным кликом пользователя;
- при включении проигрывается короткий preview;
- настройка сохраняется локально в браузере, например versioned-ключом `rf-sound-v1`;
- в localStorage хранится только настройка, без ID записей, кабинетов, клиник или пациентов;
- если `AudioContext` заблокирован, UI не должен показывать ложное состояние «включено»;
- визуальные статусы остаются основным источником информации;
- не использовать Browser Notifications API;
- не добавлять настройку громкости в MVP.

## Архитектура

Реализуй отдельно:

1. чистый классификатор переходов очереди;
2. классификатор активных инцидентов;
3. Web Audio-движок с двумя семантическими командами;
4. React-хук, который сравнивает предыдущий успешный snapshot с новым;
5. переключатель пользовательской настройки;
6. дедупликацию между вкладками.

Компоненты досок не должны знать частоты, длительности или устройство `AudioContext`.

Семантический API может выглядеть примерно так:

- `playPatientReady()`;
- `playCriticalAttention()`.

Предпочтительно использовать Web Audio API и генерировать короткие тоны программно. Не добавляй внешние аудиофайлы и библиотеку только ради двух звуков.

Характер звуков:

- `patientReady` — спокойный одиночный или двойной сигнал длительностью до 400 мс;
- `criticalAttention` — отчётливый двух- или трёхчастный сигнал общей длительностью не более одной секунды;
- без резких высоких частот;
- ошибки аудио не должны влиять на работу очереди.

## Интеграция с realtime

Текущий `useRealtimeRefetch` передаёт не payload, а вызывает загрузчик. Поэтому определяй события сравнением успешных snapshots.

Обязательные правила:

- первый успешный snapshot становится baseline без звука;
- при смене clinic/date/role/room scope baseline сбрасывается;
- ошибка загрузки не должна очищать baseline;
- сравнивать только записи, существовавшие в предыдущем snapshot;
- для сигнала готовности проверять строго `previous.status === "scheduled"` и `next.status === "waiting"`;
- для критического статуса проверять первый переход в `needs_reschedule` или разрешённый для направителя `not_held`;
- incident classifier должен учитывать `id`, статус, `started_at`, `blocked_until`, `auto_unblock` и существующие `incidentActiveAt`/`incidentExpired`;
- снятие инцидента не звучит;
- если одновременно появились несколько одинаковых событий, проиграть один звук;
- если одновременно есть обычное и критическое событие, проиграть только критическое;
- burst-окно ориентировочно 300–500 мс;
- пока вкладка скрыта, звук не воспроизводить; при возвращении синхронизировать baseline без проигрывания накопленной истории;
- polling, focus refetch и reconnect не должны повторять уже известное событие.

Не изменяй `useRealtimeRefetch` глобально, если безопаснее разместить snapshot-логику поверх него в конкретных досках или общем специализированном хуке.

## Несколько вкладок

Одна бизнес-операция должна дать не более одного звука во всём браузере, даже если открыты две вкладки RadFlow.

Используй `BroadcastChannel` с безопасным fallback. Координация должна быть эфемерной:

- не сохранять ID пациентов или записей в localStorage;
- не передавать ФИО, телефон, исследования или другие медицинские данные;
- можно передавать только тип события и неперсональный/хешированный dedupe-key;
- отсутствие поддержки `BroadcastChannel` не должно ломать приложение.

## Ролевые границы

Не расширяй доступ к данным ради звука:

- не меняй RLS;
- не добавляй CEO доступ к `incidents`;
- не создавай новые SECURITY DEFINER RPC;
- не добавляй DB migration;
- не создавай отдельную realtime-подписку шире существующего RLS-scope;
- radiologist должен слышать только назначенные кабинеты;
- referrer — только собственные направления;
- tenant-изоляция по `clinic_id` обязательна.

Если выяснится, что событие нельзя надёжно определить в текущем доступном scope, не расширяй права. Опиши ограничение в отчёте.

## Тесты

Проект не имеет полноценного компонентного jsdom-стека. Не добавляй тяжёлую тестовую инфраструктуру только ради этой функции. Вынеси критическую логику в чистые функции и покрой Vitest.

Минимальные тесты:

- первый snapshot молчит;
- `scheduled → waiting` даёт `patientReady`;
- новая запись сразу в `waiting` не звучит;
- `waiting → in_progress` и `in_progress → done` молчат;
- переход в `needs_reschedule` даёт critical;
- повторный одинаковый snapshot молчит;
- referrer получает critical для собственного `not_held`;
- staff не получает отдельный звук для обычного `not_held`;
- новый фактически активный incident даёт critical;
- planned incident до `started_at` молчит;
- planned incident при наступлении `started_at` звучит один раз;
- resolved/expired incident молчит;
- несколько событий одного типа агрегируются;
- critical имеет приоритет над patientReady;
- смена scope сбрасывает baseline без звука;
- выключенная настройка блокирует воспроизведение;
- скрытая вкладка не проигрывает накопленную историю;
- ошибки/отсутствие Web Audio и BroadcastChannel обрабатываются безопасно.

Запусти:

- `npm run typecheck`;
- `npm run lint`;
- `npm test`;
- `npm run build`, если менялся CSS или глобальная оболочка UI.

Не исправляй несвязанные предупреждения и не перезаписывай существующие изменения владельца.

## Ручная проверка

В безопасной локальной или тестовой среде проверь:

1. открыть доску с существующей очередью — тишина;
2. включить звук — один preview;
3. из второй сессии перевести сегодняшнюю запись `scheduled → waiting` — один спокойный сигнал;
4. открыть две вкладки — сигнал звучит только в одной;
5. создать тестовый активный инцидент — один критический сигнал;
6. снять инцидент — тишина;
7. выполнить refresh/reconnect/focus — старые события не звучат;
8. выключить звук — все события молчат;
9. у направителя перевести собственное направление в `needs_reschedule` — один critical;
10. проверить, что storage и console не содержат персональных данных.

Не создавай тестовых пациентов или инциденты в production.

## Критерии готовности

Задача завершена, когда:

- в продукте ровно два звуковых профиля;
- звучат только описанные события;
- initial load, refresh, polling, focus и reconnect не создают ложных сигналов;
- несколько вкладок не дублируют звук;
- ролевой и tenant-scope соблюдён;
- звук включается только явным действием;
- миграция БД и изменение RLS не потребовались;
- проверки проекта проходят;
- production не изменён.
