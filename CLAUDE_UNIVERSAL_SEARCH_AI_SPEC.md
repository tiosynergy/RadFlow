## Роль исполнителя

Ты — Claude Code Cowork, оркестратор и Full Task разработчик SaaS-продукта RadFlow.

Работай непосредственно с локальным проектом:

```text
D:\RadFlowDev
```

Сначала полностью прочитай `AGENTS.md`, затем изучи фактическую реализацию ролей, RLS-политик, очередей, листа ожидания, кейсов пациента и существующих фильтров. Не полагайся только на это ТЗ: если документация расходится с кодом или миграциями, источником истины являются актуальный код, схема БД и действующие политики доступа.

## 1. Цель задачи

Реализовать единый, быстрый и безопасный поиск по пациентам и исследованиям для всех ролей RadFlow:

- `admin`;
- `registrar`;
- `radiologist`;
- `referrer`;
- `ceo`.

Функция должна объединить поиск, который сейчас фрагментирован между доской очереди, рабочим местом радиолога, направлениями, обзвоном и листом ожидания.

При этом:

1. каждая роль видит только разрешённый ей объём данных;
2. поиск первой версии работает детерминированно, без LLM;
3. архитектура и единый типизированный контракт фильтров сразу готовятся к дальнейшему подключению LangChain, AI-ассистента и умного поиска;
4. медицинские и персональные данные не должны попадать в URL, клиентские журналы, аналитику или внешнюю AI-модель без отдельного разрешения и утверждённой политики обработки данных.

## 2. Обязательный результат текущего этапа

В рамках этой задачи необходимо полностью реализовать **этап 1 — детерминированный универсальный поиск**.

Не подключай LangChain, OpenAI API, embeddings или векторную БД в текущем этапе без отдельного прямого поручения. Вместо этого:

- создай общий типизированный контракт поисковых фильтров;
- отдели UI от поискового адаптера;
- подготовь безопасную точку расширения для AI-парсера;
- добавь архитектурный документ для этапов AI-интеграции;
- при необходимости поставь будущую AI-функцию за выключенным feature flag.

Задача не считается выполненной, если создан только макет интерфейса или только клиентская фильтрация уже загруженного дня.

## 3. Текущее состояние продукта, которое нужно учитывать

В RadFlow уже существуют:

- `queue_entries` — записи очереди и история приёмов;
- `queue_entries.studies` — JSONB-массив исследований;
- `patient_cases` — кейсы, объединяющие несколько записей пациента;
- лист ожидания;
- кабинеты, клиники, направления и назначенные радиологу кабинеты;
- отдельные клиентские фильтры в `QueueBoard`, `RadiologistBoard`, `ReferrerBoard`, `CallListBoard`;
- серверный поиск в `WaitlistBoard`;
- RLS и дополнительные ограничения ролей;
- украинские подписи интерфейса.

Проблемы текущего состояния:

- основной поиск ограничен уже загруженными на клиент записями или выбранным днём;
- отсутствует единый поиск по историческим и будущим записям;
- фильтры разных ролей ведут себя неодинаково;
- нет общего контракта, который сможет использовать будущий AI-ассистент;
- клиентская фильтрация не масштабируется на большую историю;
- существующая RLS-политика очереди может быть шире бизнес-правил конкретного экрана, например для радиолога, поэтому одной RLS недостаточно для формирования поисковой области.

## 4. Основные принципы

1. **Одна функция для всех ролей, разные области доступа.** Доступность страницы поиска не означает одинаковый набор данных.
2. **Server-side search.** Поиск по истории, пациентам и исследованиям выполняется на сервере или через безопасный RPC, а не фильтрацией полного набора в браузере.
3. **RLS — последний рубеж, а не единственная проверка.** Сервер обязан вычислять разрешённую область поиска по текущему пользователю и роли.
4. **Минимизация данных.** Результат содержит только поля, нужные для списка и разрешённого перехода.
5. **Никакого AI-generated SQL.** Ни сейчас, ни на будущем AI-этапе модель не формирует SQL, PostgREST-фильтры или имена таблиц.
6. **Один контракт фильтров.** UI, серверный поиск и будущий LangChain tool используют одну Zod-схему и один нормализатор.
7. **Нельзя объединять людей по имени или телефону.** В RadFlow нет гарантированного глобального идентификатора пациента. Результатом является запись очереди/листа ожидания; связанный кейс можно показывать через `case_id`.
8. **UI на украинском языке.** Техническая документация и комментарии могут быть на русском согласно правилам репозитория.

## 5. Матрица доступа ролей

Перед реализацией проверь фактические RLS-политики и серверные проверки. Зафиксируй итоговую матрицу в документации и тестах.

| Роль | Обязательная область поиска | Разрешённые действия из результата |
|---|---|---|
| `admin` | Записи очереди и лист ожидания своей клиники | Только уже разрешённые этой роли действия |
| `registrar` | Записи очереди и лист ожидания своей клиники | Переход к записи/кейсу и существующие разрешённые действия |
| `radiologist` | Только записи назначенных ему кабинетов; лист ожидания не показывать, если это явно не разрешено текущими правилами | Просмотр и переход к существующему рабочему месту, без расширения прав |
| `referrer` | Только собственные или назначенные ему направления в разрешённых центрах; лист ожидания — только если это уже разрешено RLS и бизнес-логикой | Просмотр и существующие действия направителя |
| `ceo` | Только клиники, разрешённые через действующий механизм CEO-доступа | Только чтение и переход в разрешённый read-only drill-down |

Обязательные ограничения:

- `clinic_id`, роль и `user_id` нельзя принимать от клиента как источник истины;
- список разрешённых клиник и кабинетов вычисляется на сервере из сессии;
- клиент может сузить область разрешёнными `clinicIds`/`roomIds`, но не расширить её;
- нельзя использовать `service_role` в клиенте или для обхода RLS;
- если используется `SECURITY DEFINER`, функция должна сама воспроизводить все tenant-, role- и room-проверки, иметь фиксированный `search_path`, минимальные grants и отдельный security review;
- любое изменение RPC, RLS или триггеров должно пройти предусмотренный `AGENTS.md` независимый adversarial review.

### 6.1 Обязательный быстрый поиск в очереди выбранного дня

Помимо отдельной страницы глобального поиска, на существующей странице очереди каждой роли должно остаться постоянно доступное компактное поле быстрого поиска.

Назначение этого поля — за несколько нажатий найти пациента **только среди записей выбранного дня**:

- по полной или частично введённой фамилии;
- по полному или постепенно/частично введённому номеру телефона.

Результат быстрого поиска — не отдельная поисковая выдача. Поле должно непосредственно фильтровать записи пациентов в текущей очереди, оставляя их в стандартном для этой роли отображении: те же строки, карточки, колонки, статусы, действия и визуальные обозначения, что и до ввода запроса.

Запрещено заменять очередь:

- выпадающим autocomplete-списком;
- отдельной таблицей результатов;
- модальным окном;
- переходом на страницу глобального поиска;
- упрощёнными карточками, в которых отсутствуют стандартные данные и действия очереди.

Рекомендуемый украинский placeholder:

```text
Пошук за прізвищем або телефоном…
```

Обязательное поведение:

1. Поиск применяется к полному разрешённому набору записей активного дня, а не только к видимой части списка.
2. Поиск работает у всех ролей на их варианте дневной очереди:
   - `admin` и `registrar` — основная очередь;
   - `radiologist` — очередь только назначенных кабинетов;
   - `referrer` — собственные/назначенные направления выбранного дня;
   - `ceo` — разрешённый read-only список выбранного дня или дневной drill-down.
3. Если у роли нет отдельной страницы с названием «Очередь», поле добавляется в эквивалентный дневной список записей, но не расширяет доступ роли.
4. Результат всегда ограничен текущими:
   - выбранной датой;
   - разрешёнными клиниками и кабинетами;
   - role/RLS scope;
   - активными фильтрами кабинета, статуса и другими фильтрами страницы.
5. Быстрый поиск комбинируется с остальными фильтрами через логическое `AND`.
6. Изменение строки не сбрасывает выбранную дату и остальные фильтры.
7. Очистка строки сразу возвращает исходную дневную очередь с сохранением остальных фильтров.
8. Отфильтрованные записи показываются прямо на месте полной очереди в её стандартном компоненте отображения.
9. Порядок записей всегда хронологический по времени приёма:
   - сверху — более ранние записи;
   - снизу — более поздние записи;
   - поиск не сортирует по релевантности и не поднимает совпадения вне порядка времени;
   - при одинаковом времени используется стабильный дополнительный порядок по существующему queue order, затем по `id`;
   - запись без корректного времени, если такая запись допустима моделью, размещается после записей со временем и не должна ломать сортировку.
10. Фильтрация не должна менять относительный порядок записей с разным временем.
11. Рядом с полем должна быть доступная кнопка очистки.
12. Строка не сохраняется в URL, browser storage, analytics или logs.

#### Поиск по фамилии

Поскольку имя пациента сейчас хранится единым полем, не пытайся миграцией автоматически разделять ФИО.

Для MVP:

- нормализовать регистр;
- удалить крайние и повторные пробелы;
- искать подстроку во всём `patient_name`;
- поддерживать частичный ввод с начала или из середины фамилии;
- поддерживать кириллицу;
- не выполнять fuzzy-слияние разных пациентов;
- при нескольких введённых словах нормализовать каждое слово и корректно искать их в ФИО.

Примеры:

```text
Ков       -> Коваль, Коваленко
вален     -> Коваленко
Ковал О   -> Коваленко Олена
```

#### Поиск по частичному телефону

Сравнение выполнять только по цифрам с использованием существующих правил `lib/phone.ts`.

```text
Ввод пользователя          Нормализованная строка
+380 (67) 123-45-67        380671234567
0671                       0671
12345                      12345
```

Запись подходит, если нормализованный телефон пациента содержит введённую последовательность цифр. Поиск должен работать при вводе:

- кода оператора;
- середины номера;
- последних цифр;
- номера с `+`, пробелами, скобками и дефисами.

В отличие от глобального поиска по истории, быстрый поиск ограничен одним днём и может безопасно реагировать уже на первый символ/цифру. Обновление результата должно быть визуально мгновенным:

- предпочтительно синхронная фильтрация уже полностью загруженного разрешённого дневного массива;
- если дневная очередь загружается частями, выполнить быстрый server-side запрос в рамках выбранного дня, чтобы не показывать ложный пустой результат;
- debounce не более 100–150 мс и только если он действительно нужен;
- не показывать глобальный loading overlay при каждом введённом символе.

Не отправлять сетевой запрос на каждый символ, если у клиента уже есть полный дневной набор данных.

## 7. Состав результата

Одна строка результата соответствует одной записи источника: `queue` или `waitlist`.

Минимально необходимые поля:

- `source`;
- `recordId`;
- `caseId`, если есть;
- `clinicId` и разрешённое к показу название клиники;
- `roomId` и название кабинета;
- дата и время;
- имя пациента;
- телефон в существующем маскированном/форматированном виде согласно правилам роли;
- исследования: `type`, `region`, признак контраста;
- статус;
- приоритет;
- направитель, только если поле разрешено роли;
- признак будущей/прошедшей записи;
- разрешённый route/action для открытия записи.

Не возвращать в общий список без необходимости:

- противопоказания;
- медицинские заметки;
- внутренние комментарии;
- email;
- полный профиль пациента;
- служебные поля аудита.

Расширенные данные загружаются только после разрешённого открытия существующей карточки.

## 8. Фильтры первой версии

### 8.1 Общие фильтры

- свободный текст: пациент или исследование;
- источник: очередь / лист ожидания;
- клиника — только из разрешённых пользователю;
- кабинет — только из разрешённых пользователю и выбранной клиники;
- период:
  - сегодня;
  - 7 дней;
  - 30 дней;
  - произвольные `dateFrom` / `dateTo`;
- статус;
- модальность: `MRI`, `CT`, `US`, `XRAY`, `MAMMO`, `OTHER`;
- название/область исследования;
- с контрастом / без контраста;
- приоритет;
- направитель — только для ролей, которым это разрешено и полезно.

### 8.2 Правила текстового поиска

Текстовая строка должна искать:

- имя пациента без учёта регистра;
- телефон по нормализованным цифрам;
- название и область исследования из `studies[].type` и `studies[].region`;
- при необходимости — разрешённое название услуги из существующего каталога.

Правила:

- удалить пробелы по краям и схлопнуть повторные пробелы;
- ограничить длину запроса;
- телефон нормализовать существующими утилитами `lib/phone.ts`;
- не запускать глобальный поиск по истории по 1 символу; это ограничение не относится к локальному быстрому поиску выбранного дня;
- для короткого запроса показывать украинскую подсказку;
- не интерпретировать имя/телефон как глобальный patient ID;
- не выполнять автоматическое fuzzy-объединение разных людей;
- сортировку по релевантности использовать только при непустой строке, иначе — по дате.

### 8.3 Предлагаемый общий контракт

Создай единственную Zod-схему, например `SearchRequestSchema`, и выведи из неё TypeScript-типы. Конкретные имена можно адаптировать к структуре проекта, но нельзя создавать отдельные несовместимые схемы для UI, RPC и будущего AI.

```ts
type SearchSource = "queue" | "waitlist";
type SearchSort = "relevance" | "date_desc" | "date_asc";

type SearchRequest = {
  term?: string;
  sources?: SearchSource[];
  clinicIds?: string[];
  roomIds?: string[];
  dateFrom?: string;
  dateTo?: string;
  queueStatuses?: string[];
  waitlistStatuses?: string[];
  modalities?: Array<"MRI" | "CT" | "US" | "XRAY" | "MAMMO" | "OTHER">;
  studyQuery?: string;
  contrast?: boolean;
  priorities?: string[];
  referrerIds?: string[];
  sort?: SearchSort;
  cursor?: string;
  limit?: number;
};
```

Нормализатор обязан:

- применять безопасные значения по умолчанию;
- ограничивать `limit` — рекомендуемо 25, максимум 100;
- ограничивать количество ID и enum-значений;
- проверять UUID;
- валидировать диапазон дат;
- запрещать чрезмерно широкий диапазон без уточняющего запроса;
- удалять фильтры, недоступные роли, либо возвращать контролируемую ошибку;
- формировать стабильный cursor;
- не принимать из AI или клиента произвольные имена колонок, операторы и sort expressions.

## 9. Серверная архитектура

Разделить реализацию на слои:

```text
Search UI
  -> server action / POST route
    -> auth + role scope resolver
      -> SearchRequestSchema + normalizer
        -> queue/waitlist search adapters
          -> Supabase/RPC under RLS
            -> normalized SearchResponse
```

Требования:

- GET с PII-параметрами не использовать;
- сессия проверяется на сервере;
- область доступа вычисляется до выполнения запроса;
- возвращать discriminated union успеха/ошибки, не выдавать пустой список при сетевой или серверной ошибке;
- использовать cursor pagination со стабильной сортировкой, включающей уникальный `id`;
- не делать обязательный дорогой `count(*)` для каждого ввода;
- клиентский debounce — ориентировочно 300–400 мс;
- отменять или игнорировать устаревшие ответы;
- исторический поиск в MVP не обязан иметь Realtime-подписку: достаточно повторного поиска и явного обновления;
- не загружать полную историю на клиент;
- UI не должен обращаться к таблицам поиска напрямую в обход серверного контракта.

`SearchResponse` должен содержать:

```ts
type SearchResponse = {
  items: SearchResultItem[];
  nextCursor: string | null;
  hasMore: boolean;
  appliedFilters: NormalizedSearchFilters;
};
```

## 10. Стратегия БД и производительность

До добавления миграции:

1. определить фактический следующий номер миграции, не полагаясь на устаревшие документы;
2. проверить объём и форму данных;
3. снять `EXPLAIN (ANALYZE, BUFFERS)` на production-like данных;
4. проверить доступность необходимых PostgreSQL extensions;
5. сравнить прямой PostgREST-запрос и строго типизированный RPC.

Предпочтительная архитектура — один серверный use case с отдельными адаптерами очереди и листа ожидания. Допустимы два узких RPC с объединением и сортировкой на сервере приложения, если это упрощает RLS и различающиеся статусы.

Для поиска исследований в JSONB:

- корректно искать по элементам `studies[]`, а не по случайному совпадению всего сериализованного JSON;
- сначала сузить область клиниками, кабинетами, датами и ролью;
- если `jsonb_array_elements` не укладывается в целевые показатели, добавить поддерживаемое поисковое поле/индекс;
- не добавлять сложные индексы без измерений;
- если используется денормализованный search document, обеспечить его синхронизацию и тесты для insert/update.

Для имени и телефона:

- оценить trigram/expression indexes;
- нормализовать телефон одинаково при записи и поиске;
- не менять исходные данные ради поиска;
- учитывать украинский и русский регистр, но не обещать транслитерацию без отдельного словаря и тестов.

Целевые показатели на production-like данных:

- p95 серверного ответа до 500 мс для обычного фильтрованного запроса;
- отсутствие полной выгрузки таблицы;
- отсутствие последовательного сканирования всей tenant-wide истории для стандартного поиска;
- стабильная пагинация без дублей и пропусков.

Если для выполнения нужны RPC, индексы, функции или триггеры:

- создать новую миграцию, не переписывать уже применённые;
- обновить сгенерированные типы БД;
- документировать ручное применение миграции;
- подготовить rollback/disable plan;
- провести security review согласно `AGENTS.md`.

## 11. UX-детали

Рекомендуемый вид результата:

```text
ПІБ пацієнта                  30.07.2026 · 14:20
+380 …                        МРТ · Головний мозок
Клініка / кабінет             Очікує · Високий пріоритет
```

Обязательные состояния:

- начальное: подсказка, по каким данным можно искать;
- загрузка: skeleton без мерцания предыдущего результата;
- пусто: «Нічого не знайдено» и предложение снять фильтры;
- ошибка: явное сообщение и кнопка повторить;
- нет доступа к источнику: источник отсутствует в UI, а не отображается пустым;
- пагинация: «Показати ще» или infinite list с доступной альтернативой;
- мобильная версия: фильтры открываются в drawer/sheet;
- desktop: фильтры могут быть боковой панелью;
- активный результат открывается клавишей Enter;
- после возврата со страницы записи допустимо восстановить состояние поиска только в памяти текущей вкладки, без устойчивого хранения PII.

## 12. Безопасность и приватность

Обязательные меры:

- все запросы выполняются от авторизованной пользовательской сессии;
- роль и tenant scope вычисляются сервером;
- RLS остаётся включённой;
- защита от поиска по чужой клинике и чужому кабинету проверяется интеграционными тестами;
- ограничение частоты запросов на пользователя/клинику;
- ограничение длины строки, числа фильтров и размера страницы;
- timeout для БД-запроса;
- отсутствие PII в URL, browser storage, telemetry, exception reporting и console;
- безопасные сообщения об ошибках без SQL и внутренних деталей;
- аудит не должен хранить сырую поисковую строку с ФИО/телефоном;
- CEO-режим остаётся read-only;
- поиск не создаёт новые write-возможности ни одной роли.

## 13. Подготовка к LangChain и умному поиску

### 13.1 Этап 2 — естественный язык в строгие фильтры

После отдельного согласования подключить LangChain только на сервере.

Пример запроса пользователя:

```text
Покажи КТ з контрастом на наступний тиждень у другому кабінеті
```

Ожидаемый результат AI — только объект, валидируемый общей `SearchRequestSchema`, например:

```json
{
  "dateFrom": "2026-08-03",
  "dateTo": "2026-08-09",
  "modalities": ["CT"],
  "contrast": true
}
```

Последовательность:

```text
natural-language text
  -> LangChain structured output
    -> SearchRequestSchema.safeParse()
      -> role-aware normalizer
        -> deterministic search service
```

Модель:

- не получает SQL;
- не выбирает таблицу;
- не задаёт tenant/user scope;
- не может отключить RLS;
- не вызывает Supabase напрямую;
- не получает результаты с данными пациентов на этапе parsing;
- не может создавать неизвестные фильтры;
- не выполняет write-операции.

Пользователь должен видеть, как запрос был интерпретирован: AI-результат превращается в обычные chips фильтров, которые можно исправить до или после поиска.

### 13.2 Маршрутизация PII

До утверждения zero-retention/DPA и политики обработки медицинских данных:

- AI-функция выключена feature flag;
- телефон, email, ID и точные идентифицирующие запросы обрабатываются локальным детерминированным поиском без LLM;
- записи пациентов и результаты поиска не отправляются модели;
- не создавать embeddings ФИО, телефонов, email, заметок или противопоказаний.

Семантический поиск на раннем этапе допустим только по данным без PII:

- каталог исследований;
- синонимы модальностей и областей тела;
- продуктовая документация;
- инструкции RadFlow.

### 13.3 Этап 3 — AI-ассистент

Первый AI-ассистент должен быть read-only и использовать allowlisted tools.

Минимальный tool:

```ts
searchRecords(filters: SearchRequest): Promise<RedactedSearchResponse>
```

Ограничения tool:

- Zod-схема;
- область роли вычисляется вне модели;
- максимум 20 записей на один tool call;
- ограничение количества вызовов за один ответ;
- timeout и rate limit;
- данные по умолчанию редактируются/минимизируются;
- никаких параметров `sql`, `table`, `select`, `role`, `userId`, `bypassRls`;
- никаких write tools в первой версии.

Для ответов по документации использовать контролируемый 2-step RAG. Agentic RAG добавлять только при доказанной необходимости. Поиск пациентов остаётся отдельным детерминированным tool и не смешивается с векторным поиском документации.

Защититься от:

- prompt injection;
- попытки расширить клинику/кабинет через текст;
- извлечения данных другого пациента;
- чрезмерного числа tool calls;
- утечки данных через traces;
- галлюцинации результата, которого нет в tool response.

## 15. План реализации для Claude Code

### Шаг 0. Discovery

- прочитать `AGENTS.md`;
- проверить ветку и незакоммиченные пользовательские изменения;

- реализовать нормализатор;

- реализовать адаптер листа ожидания;
- добавить cursor pagination;
- добавить измеренные индексы/RPC только при необходимости;
- обеспечить единое представление результатов;
- проверить ошибку отдельно от пустого результата.

### Шаг 3. Интерфейс

- добавить страницу и пункт навигации для каждой роли;
- реализовать строку поиска, фильтры, chips и reset;
- добавить во все дневные представления очереди быстрое поле поиска по частичной фамилии и частичному телефону;
- переиспользовать одну общую утилиту/хук быстрого поиска, не копировать отличающуюся логику по ролям;
- фильтровать существующий массив записей до передачи в стандартный renderer очереди, не создавать отдельный renderer поисковой выдачи;
- после применения всех фильтров гарантировать стабильную сортировку по времени приёма по возрастанию;
- реализовать responsive result list;
- связать результат с существующим разрешённым экраном;
- не дублировать существующие модалки и бизнес-действия.

### Шаг 4. Проверки безопасности

- RLS/role matrix tests;
- попытки подставить чужие `clinicIds`, `roomIds`, `referrerIds`;
- проверка отсутствия PII в URL/storage/logs;
- rate/limit validation;
- adversarial review RPC/RLS/trigger изменений.

- документировать общий tool contract;
- описать feature flags;
- описать PII-gate;

## 16. Обязательные тесты

### Unit

- нормализация текста;
- нормализация телефона;
- частичное совпадение фамилии с начала и из середины;
- частичное совпадение телефона по коду оператора, середине и последним цифрам;
- одинаковый результат для форматированного и неформатированного телефона;
- комбинация быстрого поиска с фильтрами выбранного дня;
- сортировка отфильтрованных записей по времени по возрастанию;
- стабильный порядок записей с одинаковым временем;
- записи без времени располагаются после записей с корректным временем;
- Zod validation;
- диапазоны дат;
- ограничения размера;
- cursor encode/decode;
- стабильная сортировка;
- фильтрация недоступных параметров;
- mapping строки результата.

### Integration / RLS

- admin не видит другую клинику;
- registrar не видит другую клинику;
- radiologist не видит неназначенный кабинет даже внутри своей клиники;
- referrer не видит чужое направление;
- CEO не видит клинику вне CEO-доступа;
- прямое добавление чужого `clinicId` не расширяет результат;
- лист ожидания доступен только разрешённым ролям;
- поиск по `studies[].type` и `studies[].region` работает;
- телефон находится в разных форматах ввода;
- пагинация не создаёт дублей и пропусков;
- ошибка БД не превращается в «нічого не знайдено».

### UI

- поиск доступен в навигации всех ролей;
- быстрое поле поиска присутствует в дневной очереди всех пяти ролей;
- постепенный ввод фамилии немедленно сужает только очередь выбранного дня;
- постепенный ввод цифр телефона немедленно сужает только очередь выбранного дня;
- очистка быстрого поиска возвращает дневной список и не сбрасывает дату/другие фильтры;
- быстрый поиск не показывает записи другого дня, клиники или неназначенного кабинета;
- поиск работает при вводе телефона с `+`, пробелами, скобками и дефисами;
- отфильтрованные пациенты остаются в стандартном отображении непосредственно внутри очереди;
- быстрый поиск не открывает autocomplete, модальное окно или отдельную страницу результатов;
- после каждого изменения строки более ранние записи находятся выше более поздних;
- недоступные источники и фильтры не показываются;
- chips соответствуют реально применённым фильтрам;
- reset очищает состояние;
- loading/empty/error визуально различимы;
- клавиатурный сценарий работает;
- мобильный layout не ломается;
- URL не содержит ФИО, телефон или текст запроса.

### Будущая AI-оценка

Подготовить, но не запускать в MVP, eval-набор украинских и русских запросов:

- корректные даты и относительные периоды;
- модальности и контраст;
- статусы;
- неоднозначные запросы;
- неподдерживаемые фильтры;
- prompt injection;
- попытка запросить другую клинику;
- запрос с телефоном/ФИО, который должен уйти в deterministic path;
- гарантия, что результатом parser является только допустимая схема, а не SQL.

## 17. Критерии приёмки

Задача принята, если одновременно выполнено следующее:

1. Все пять ролей имеют доступ к единой функции поиска.
2. Каждая роль получает только разрешённые записи.
3. Поиск работает по истории и будущим записям, а не только по загруженному дню.
4. Работает поиск пациента по имени и нормализованному телефону.
5. Работает поиск исследования по типу и области из `studies`.
6. Работают основные фильтры и их комбинации.
7. Используется серверная пагинация.
8. Ошибки не маскируются пустым результатом.
9. PII отсутствует в URL, storage, console и telemetry.
10. Нет расширения существующих прав ролей.
11. Общая Zod-схема пригодна для будущего LangChain structured output.
12. LangChain и внешний AI не активированы в MVP.
13. Тесты роли/tenant scope проходят.
14. TypeScript, lint, tests и production build проходят либо каждый оставшийся внешний blocker документирован с доказательством.
15. Изменения RPC/RLS/trigger получили обязательный review.
16. На дневной очереди всех ролей есть мгновенный поиск по полной/частичной фамилии.
17. На дневной очереди всех ролей есть мгновенный поиск по постепенно вводимой части телефона.
18. Быстрый поиск никогда не выходит за выбранный день и разрешённую роли область данных.
19. Быстрый поиск фильтрует стандартное отображение самой очереди, а не создаёт отдельную поисковую выдачу.
20. Отфильтрованные записи всегда расположены по времени приёма по возрастанию: ранние сверху, поздние снизу.

## 18. Что не входит в текущий MVP

- чат с пациентскими карточками;
- AI-generated SQL;
- AI-изменение записей;
- голосовой ассистент;
- embeddings персональных данных;
- автоматическое объединение дублей пациентов;
- новый master patient registry;
- перестройка существующей модели `patient_cases`;
- экспорт массового списка пациентов;
- ослабление RLS ради удобства поиска.
